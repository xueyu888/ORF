# 数据化测试代码生成约束

## 1. 目的

本文档用于约束如何根据 `数据化测试用例模板.md` 生成统一的数据化测试代码。

生成后的测试代码必须遵循统一状态模型：

```text
B -> Setup -> S0 -> Action -> S1 -> Clean -> B
```

生成后的测试用例代码只声明结构化数据，不手写执行流程，也不直接调用 Playwright、DB、API 或 Ory。

职责分层：

- case：由测试用例文档生成，只声明用例元信息、阶段、步骤和参数，描述“要做什么”。
- runner：统一执行 `B -> Setup -> S0 -> Action -> S1 -> Clean -> B`，负责流程顺序、异常处理和清理保证。
- operator：实现每个步骤的具体能力，按 `object` 分组注册，负责调用 Playwright、DB、API、Ory 或 Mock。
- reporter：记录执行结果，负责生成阶段结果、错误信息、截图附件和测试报告。

## 3. Case 生成约束

### 3.1 case 文件介绍

`xxx.case.ts` 由人工编写的测试用例文档生成，只声明数据：

```ts
export const mloginSuccessCase = {
  id: "auth.login.success",
  title: "普通成员可以使用正确邮箱和密码登录 ORF",
  model: STATE_CASE_MODEL,
  tags: ["auth", "login", "happy-path"],
  data: {
    email: "orf-login-e2e@orf.local",
    password: "OrfLoginE2E!2026",
  },
  B: {
    description: "xxx",
    assertions: [
      {
        id: "session.unauthenticated",
        title: "后端 session 未登录",
        source: {
          caseStepId: "B-1",
          method: "api",
        },
        object: "auth.session",
        operator: "unauthenticated",
      },
    ],
  },
  Setup: { description: "xxx", steps: [] },
  S0: { description: "xxx", assertions: [] },
  Action: { description: "xxx", steps: [] },
  S1: { description: "xxx", assertions: [] },
  Clean: { description: "xxx", steps: [] },
} satisfies StateCaseSpec<MloginCaseData>;
```

`case.ts` 中不得直接导入状态函数或动作函数。

### 3.2 文档到 case 的映射

从测试用例文档生成 `case.ts` 时，必须遵守：

- 文档中的 B、Setup、S0、Action、S1、Clean 分别映射为 `B`、`Setup`、`S0`、`Action`、`S1`、`Clean` 数据块。
- 文档中的每条具体动作或观测条目必须使用 `- [阶段-序号] [执行手段] 描述` 格式，例如 `- [Action-3] [playwright] 点击 Sign In 按钮`。
- `阶段-序号` 必须在当前用例文档内唯一，阶段前缀只能是 `B`、`Setup`、`S0`、`Action`、`S1`、`Clean`，序号从 1 开始按文档顺序递增。
- 文档中的每条 `[playwright]`、`[api]`、`[prisma]`、`[mock]` 条目至少生成一个 `StepSpec`；允许一条用例条目拆成多个实际 `StepSpec`，但不允许生成没有来源条目的孤立 `StepSpec`。
- 每个生成的 `StepSpec` 必须包含 `source`，其中 `source.caseStepId` 填写文档中的 `阶段-序号`，`source.method` 填写文档中的执行手段标签去掉方括号后的值。
- 当同一条用例条目被拆成多个实际步骤时，多个 `StepSpec` 使用相同的 `source.caseStepId` 和 `source.method`，并通过不同的 `id`、`title`、`object`、`operator` 区分实际执行内容。
- 技术性前置步骤也必须能追溯到用例条目。例如 S1 中要求断言某个提交接口响应成功，但实现上必须在点击按钮前注册响应捕获，则响应捕获步骤可以放在 `Action.steps` 中，`source.caseStepId` 仍指向该 S1 条目。
- `id` 和 `title` 从人类可读条目中提炼，保持报告可读。
- `object` 声明步骤作用对象或资源路径，例如 `page`、`page.url`、`auth.session`、`db.user`。
- `operator` 只声明动作或断言语义，例如 `enabled`、`match`、`authenticated`、`upsert`。
- `object + operator` 必须能在公共算子、领域算子或用例算子注册表中找到对应实现；没有合适算子时，按复用优先级新增。
- `data` 只放生成代码确实需要复用的稳定测试输入；不要因为生成结构需要，反向要求测试用例文档单独列数据字典。

### 3.3 case 的数据结构

`types.ts` 必须提供 `StateCaseSpec` 作为所有 `case.ts` 共享的数据化 schema：

```ts
export type StateCaseSpec<TData extends Record<string, unknown>> = {
  id: string;
  title: string;
  model: "B -> Setup -> S0 -> Action -> S1 -> Clean -> B";
  tags?: string[];
  data: TData;
  B: StateBlock;
  Setup: ActionBlock;
  S0: StateBlock;
  Action: ActionBlock;
  S1: StateBlock;
  Clean: ActionBlock;
};

export type StateBlock = {
  description: string;
  assertions: StepSpec[];
};

export type ActionBlock = {
  description: string;
  steps: StepSpec[];
};

export type StepSpec = {
  id: string;
  title: string;
  source?: StepSource;
  object: string;
  operator: string;
  params?: Record<string, unknown>;
};

export type StepSource = {
  caseStepId: string;
  method: "playwright" | "api" | "prisma" | "mock";
};
```

`source` 在类型上允许为空，是为了兼容历史 `case.ts`；新增或重生成的 `case.ts` 必须填写 `source`。

### 3.4 Step 约束

所有步骤必须使用统一格式：

```ts
{
  id: "fill.email",
  title: "输入邮箱",
  source: {
    caseStepId: "Action-1",
    method: "playwright",
  },
  object: "page",
  operator: "fill",
  params: {
    label: "Email",
    valueFrom: "data.email",
  },
}
```

约定：

- `source.caseStepId` 用于追溯到测试用例文档中的具体条目；不得写成当前 `case.ts` 内部序号。
- `source.method` 必须来自测试用例文档中的执行手段标签，不根据 `object` 或 `operator` 反推。
- `object` 是能力归属或资源路径，不表达动作；`page.enabled` 必须拆成 `object: "page"` 和 `operator: "enabled"`。
- 多级资源按对象路径保留，最后一段作为操作；例如 `auth.session.authenticated` 拆成 `object: "auth.session"` 和 `operator: "authenticated"`。
- `xxxFrom` 在 runner 中解析为 `xxx`。
- `data.xxx` 读取用例固定数据。
- `runtime.xxx` 读取前面步骤保存的运行时结果。
- `saveAs` 用于保存算子返回值到 `runtime`。

## 4. Runner 约束

### 4.1 runner 执行顺序

`runStateCase` 必须固定执行：

```text
B.assertions[]
Setup.steps[]
S0.assertions[]
Action.steps[]
S1.assertions[]
Clean.steps[]
B.assertions[]
```

Clean 必须在 `finally` 语义下执行；Clean 后必须重新执行 B，并在报告中记录为 `B after Clean`。

### 4.2 spec 接入

`xxx.spec.ts` 只接入 Playwright：

```ts
test(mloginSuccessCase.title, async ({ context, page }, testInfo) => {
  const ctx: TestContext = { context, page };

  await runStateCase(mloginSuccessCase, ctx, {
    operators: mergeOperatorRegistries(
      createCommonOperators<TestContext, MloginCaseData>(),
      mloginOperators,
    ),
    testInfo,
  });
});
```

`.spec.ts` 不得直接执行业务步骤。

## 5. Operator 约束

### 5.1 operator 分层

operator 按复用范围分层：

- 公共算子：放在 `testd/_operators/common.operators.ts`，只实现跨业务稳定复用的能力，例如 `page.goto`、`page.fill`、`page.enabled`、`page.url.match`、`browser.clear_state`、`auth.session.authenticated`、`api.capture_response`、`db.ready`。
- 领域算子：放在可复用领域目录或当前领域的 `xxx.operators.ts`，实现某类业务页面或资源的可复用能力，例如 `page.comment_panel.close`、`page.comment_composer.fill`。
- 用例算子：只服务当前用例、尚不确定复用价值的能力，先放在当前 `xxx.operators.ts`。

新增算子时优先查找并复用公共算子；第二个用例也需要同一能力时，应下沉到公共算子或领域算子，避免复制实现。

### 5.2 operator 注册表

`xxx.operators.ts` 只放当前用例或领域专属算子：

```ts
export const mloginOperators = {
  "ory.identity": {
    upsert: oryIdentityUpsert,
  },
  "db.member": {
    matches: dbMemberMatches,
  },
} satisfies OperatorRegistry<TestContext, MloginCaseData>;
```

spec 使用 `mergeOperatorRegistries` 组合公共算子和用例算子：

```ts
await runStateCase(mloginSuccessCase, ctx, {
  operators: mergeOperatorRegistries(
    createCommonOperators<TestContext, MloginCaseData>(),
    mloginOperators,
  ),
  testInfo,
});
```

runner 使用 `operators[step.object]?.[step.operator]` 查找实现。注册表不得重新把对象和操作压回一个字符串键。

当多个注册表提供同一个 `object.operator` 时，后面的注册表覆盖前面的注册表；只允许在确实需要为当前领域改写公共行为时覆盖。

### 5.3 operator 实现边界

operator 负责具体实现，可以调用：

```text
Playwright
DB helper
API helper
Ory helper
Mock helper
```

operator 不负责编排 B、Setup、S0、Action、S1、Clean 的整体流程。

公共 operator 必须尽量只依赖 `params`、`ctx` 和 `runtime`，不要直接读取某个具体 case 的 `data` 类型。需要用例数据时，在 case 中通过 `xxxFrom` 显式传入参数，例如 `emailFrom: "data.email"`。

### 5.4 context 和 helpers

`testd/_operators/common.context.ts` 和 `testd/_operators/common.helpers.ts` 放跨用例共享的基础类型、常量和底层能力，例如浏览器状态、session、健康检查、Ory Admin 基础访问和响应解析。

`xxx.context.ts` 放：

```text
TestContext
CaseData
当前用例或领域专属类型
```

`xxx.helpers.ts` 只放当前用例或领域专属底层能力：

```text
数据库读写
API 请求
领域预置测试数据
领域页面数据读取
关闭连接
```

helper 不表达测试流程，也不要复制公共 helper 中已有的能力。

## 6. Reporter 约束

### 6.1 报告产物

每次执行 Playwright 测试后必须自动生成报告：

```text
test-reports/
└── 2026年5月18日14时38分59秒/
    ├── summary.md
    └── result.json
```

### 6.2 阶段记录

runner 至少记录这些阶段：

```text
B
Setup
S0
Action
S1
Clean
B after Clean
```

每个阶段至少记录：

```text
阶段名
执行结果
耗时
错误信息
```

失败用例应保留失败阶段、错误信息、阶段结果和截图附件。

## 7. 一句话约束

测试用例是数据。

执行顺序归 runner。

具体能力归 operator。

结果留痕归 reporter。

# 数据化测试步骤语言规范

## 1. 核心思想

### 1.1 文档目标

本文档用于规范数据化测试用例中每个阶段内部的具体步骤语言。

数据化测试方法论已经规定测试整体模型为：

```text
B --Setup--> S0 --Action--> S1 --Clean--> B
```

本文档只回答一个问题：

> 在 B、Setup、S0、Action、S1、Clean 这些阶段中，每一句具体步骤应该如何描述？

也就是说，本文档关注的是测试步骤语言，而不是测试结构本身。

---

### 1.2 语言定位

数据化测试步骤语言不是代码，也不是完全自由的自然语言。

它是一种面向前端业务测试的受控中文描述语言。

它应该同时满足三类要求：

```text
人可以读懂
业务语义清楚
执行器可以稳定翻译
```

其中：

- 人可以读懂：测试、前端、后端、产品都能理解这一步在验证什么。
- 业务语义清楚：句子优先表达业务对象、业务动作、业务状态，而不是技术实现细节。
- 执行器可以稳定翻译：Codex、测试生成器或测试 helper 能根据句型生成 Playwright 操作、API 调用、Prisma 查询或 Mock 配置。

---

### 1.3 和普通自然语言的区别

普通自然语言允许省略主语、混用代词、合并多个意图、夹杂实现细节。

测试步骤语言不允许这样做。

测试步骤语言要求：

```text
主语明确
谓语稳定
宾语清楚
条件可识别
结果可断言
手段可标注
```

例如，下面的写法不够规范：

```text
确认这个已经申请了。
```

问题是：

```text
“这个”是谁？
“已经申请”是页面状态、接口状态，还是数据库状态？
由谁申请？
申请哪个目标？
状态是 pending、approved，还是其他？
```

更规范的写法是：

```text
[prisma] 应存在 普通成员 对 目标 的 pending 挑战申请。
[api] 目标 对当前成员 应为 已申请。
[playwright] 目标 的操作状态 应显示为 "已申请"。
```

一句话说不清时，可以拆成两句或三句。

---

### 1.4 核心原则

测试步骤语言遵循以下原则：

```text
业务优先
句型稳定
单句单意
主语明确
状态和动作分离
技术细节后置
阶段职责不混淆
```

#### 业务优先

优先描述业务语义，不优先描述实现方式。

推荐：

```text
[playwright] 点击 目标 的 "申请挑战" 操作。
```

不推荐：

```text
[playwright] 点击 .btn-primary:nth-child(2)。
```

#### 句型稳定

同一类意思使用同一类句型。

推荐：

```text
[prisma] 应存在 普通成员用户。
[prisma] 应不存在 普通成员 对 目标 的 pending 挑战申请。
```

不推荐：

```text
[prisma] 普通成员用户已经有了。
[prisma] 没有查到申请记录。
```

#### 单句单意

一句话只表达一个动作或一个断言。

推荐：

```text
[playwright] 打开 悬赏大厅。
[playwright] 悬赏大厅列表 应显示 目标。
[playwright] 目标 的 "申请挑战" 操作 应可点击。
```

不推荐：

```text
[playwright] 打开悬赏大厅后能看到目标并且申请挑战按钮可以点。
```

#### 状态和动作分离

动作句负责“做什么”。

状态句负责“应该是什么”。

推荐：

```text
[playwright] 点击 目标 的 "申请挑战" 操作。
[playwright] 提交挑战申请确认弹窗 应可见。
```

不推荐：

```text
[playwright] 点击按钮并看到弹窗。
```

#### 技术细节后置

主用例中优先使用业务名词。字段名、接口路径、数据库表名可以进入实现映射层，除非该字段本身就是本用例必须锁定的业务契约。

推荐：

```text
[api] 目标 对当前成员 应为 尚未申请。
```

不推荐：

```text
[api] GET /api/bounties.availableItems[0].hasCurrentApplication 应为 false。
```

## 2. 句子模型

### 2.1 基础句型

每个测试步骤建议使用以下基础结构：

```text
[执行手段] 情态词 + 主体 + 谓语 + 对象 + 条件/范围/结果。
```

其中：

| 成分 | 含义 | 示例 |
|---|---|---|
| 执行手段 | 通过什么方式执行或观测 | `[playwright]`、`[api]`、`[prisma]`、`[mock]` |
| 情态词 | 表示这是断言、动作、记录还是清理 | 应、应不、必须、可以、记录、选择、删除、恢复 |
| 主体 | 句子的主要业务对象 | 当前会话、普通成员、目标、挑战申请、页面、弹窗 |
| 谓语 | 主体发生什么或处于什么状态 | 存在、显示、可点击、为、属于、包含、创建、删除 |
| 对象 | 谓语作用的对象 | 目标、申请、按钮、状态、接口响应 |
| 条件/范围/结果 | 限定句子适用范围或预期结果 | 邮箱为、状态为、在悬赏大厅中、由本用例创建 |

示例：

```text
[prisma] 应存在 邮箱为 "orf-member-e2e@orf.local" 的普通成员用户。
```

拆解为：

```text
执行手段：[prisma]
情态词：应
谓语：存在
主体：普通成员用户
条件：邮箱为 "orf-member-e2e@orf.local"
```

再例如：

```text
[playwright] 悬赏大厅列表中 目标 的 "申请挑战" 操作 应可点击。
```

拆解为：

```text
执行手段：[playwright]
范围：悬赏大厅列表中
主体：目标 的 "申请挑战" 操作
谓语：应可点击
```

---

### 2.2 执行手段标签

步骤语言继承数据化测试方法论中的执行手段标签。

目前允许使用的标签为：

```text
[playwright]
[api]
[prisma]
[mock]
```

标签只说明这一句通过什么手段执行或观测，不改变句子的业务含义。

落入数据化用例文档并标记为已完成追溯验证时，每条具体步骤还必须在执行手段标签前带阶段编号：

```text
- [阶段-序号] [执行手段] 描述。
- [Action-1] [playwright] 点击 目标 的 "申请挑战" 操作。
- [S1-1] [api] 创建挑战申请请求 应成功。
```

本文下方只解释句型的独立示例可省略编号；正式用例文档不得省略。

例如：

```text
[playwright] 当前页面 应为 悬赏大厅。
[api] 当前会话 应为 已登录。
[prisma] 应存在 普通成员 对 目标 的 pending 挑战申请。
[mock] 支付网关 应返回 支付成功。
```

同一个业务事实可以通过多个手段观察。

例如“当前用户已登录”可以写成：

```text
[api] 当前会话 应为 已登录。
[playwright] 当前用户信息 应显示 普通成员。
```

这两句不是重复，而是从不同层面确认同一个业务状态。

---

### 2.3 不引入运行时标签

步骤语言不新增 `[runtime]` 标签。

运行时变量通过产生该变量的执行手段来标注。

推荐：

```text
[api] 选择 一个当前可申请的悬赏目标 作为 目标。
[api] 记录 目标 的 ID 作为 目标 ID。
[prisma] 记录 目标 的申请前流转状态 作为 原流转状态。
```

不推荐：

```text
[runtime] runtime.bountyTarget = xxx。
```

运行时变量是测试语言中的“命名对象”，不是一种执行手段。

---

### 2.4 标点和格式

为了便于阅读和生成代码，建议统一使用以下格式：

```text
每个步骤独立成行。
每个步骤以句号结束。
每个步骤只表达一个动作或一个断言。
字符串值使用英文双引号。
枚举值可以直接写原始值，例如 active、pending、member。
业务对象名称使用中文，例如 普通成员、目标、挑战申请。
```

示例：

```text
[prisma] 普通成员 的状态 应为 active。
[playwright] 当前用户显示 应为 "ORF Member E2E"。
[api] 挑战申请请求 应返回 成功。
```

## 3. 词类规范

### 3.1 名词：业务对象

名词用于表示测试中的业务对象、技术对象或运行时对象。

常见名词包括：

```text
普通成员
管理员
当前用户
当前会话
当前浏览器
浏览器上下文
登录态
团队
目标
悬赏目标
悬赏大厅
挑战申请
确认弹窗
操作按钮
接口响应
数据库记录
Mock 响应
```

名词应该稳定、明确、可复用。

推荐：

```text
普通成员
目标
挑战申请
当前会话
```

不推荐：

```text
这个用户
那条数据
它
这个按钮
```

除非上下文非常短且不会歧义，否则不要用“这个”“那个”“它”。

---

### 3.2 动词：操作行为

动词用于描述 Setup、Action、Clean 中真正执行的操作。

常见动作动词包括：

```text
打开
登录
退出
点击
填写
选择
勾选
切换
提交
确认
取消
读取
调用
监听
等待
选择
记录
创建
删除
恢复
清空
```

动作句应该明确“谁对什么做了什么”。

推荐：

```text
[playwright] 使用 普通成员账号 登录。
[playwright] 点击 目标 的 "申请挑战" 操作。
[api] 读取 悬赏大厅数据。
[prisma] 删除 本用例创建的挑战申请。
```

不推荐：

```text
[playwright] 登录一下。
[playwright] 点一下。
[prisma] 清一下数据。
```

---

### 3.3 状态谓语：断言状态

状态谓语用于 B、S0、S1 中描述系统应该满足的状态。

常见状态谓语包括：

```text
应存在
应不存在
应为
应不为
应属于
应不属于
应包含
应不包含
应可见
应不可见
应可点击
应不可点击
应可用
应不可用
应成功
应失败
应为空
应不为空
应保持
应变为
```

示例：

```text
[api] 当前会话 应为 未登录。
[prisma] 应存在 普通成员用户。
[prisma] 普通成员 的角色 应为 member。
[playwright] 目标 的 "申请挑战" 操作 应可点击。
[playwright] 页面 应不显示 错误提示。
```

---

### 3.4 限定词：缩小范围

限定词用于说明对象的范围、条件或来源。

常见限定方式包括：

```text
邮箱为 ... 的
状态为 ... 的
角色为 ... 的
属于 ... 的
由本用例创建的
申请前的
当前登录用户的
当前浏览器中的
悬赏大厅列表中的
目标对应的
```

示例：

```text
[prisma] 应存在 邮箱为 "orf-member-e2e@orf.local" 的普通成员用户。
[prisma] 应不存在 普通成员 对 目标 的 pending 挑战申请。
[prisma] 删除 由本用例创建的 pending 挑战申请。
[playwright] 悬赏大厅列表中的 目标 应可见。
```

限定词的作用是减少歧义。

如果一句话不加限定词会导致多个对象都符合，就必须加限定词。

---

## 4. 语句类型

### 4.1 状态断言句

状态断言句用于描述系统当前应该满足的状态。

主要用于：

```text
B
S0
S1
Clean 后的回归确认
```

#### 4.1.1 存在断言

句型：

```text
[手段] 应存在 对象。
[手段] 应不存在 对象。
```

示例：

```text
[prisma] 应存在 普通成员用户。
[api] 应存在 普通成员 的 Ory 身份。
[prisma] 应不存在 普通成员 对 目标 的 pending 挑战申请。
[playwright] 当前浏览器 应不存在 登录态。
```

存在断言不写成：

```text
exists = 1
exist = true
not null
```

这些属于实现层表达，不属于步骤语言主文。

---

#### 4.1.2 属性断言

句型：

```text
[手段] 对象 的 属性 应为 值。
[手段] 对象 的 属性 应不为 值。
```

示例：

```text
[prisma] 普通成员 的角色 应为 member。
[prisma] 普通成员 的状态 应为 active。
[playwright] 当前用户显示 应为 "ORF Member E2E"。
[api] 当前会话 的认证状态 应为 已登录。
```

如果属性本身是业务概念，优先使用中文业务名词。

推荐：

```text
[api] 当前会话 应为 已登录。
```

可接受：

```text
[api] 当前会话 的 authenticated 字段 应为 true。
```

第一种适合测试用例主文，第二种适合接口契约或实现映射说明。

---

#### 4.1.3 集合归属断言

句型：

```text
[手段] 对象 的 属性 应属于 值集合。
[手段] 对象 的 属性 应不属于 值集合。
```

示例：

```text
[prisma] 目标 的流转状态 应属于 open、applying、recruiting。
[api] 当前用户 的角色 应属于 member、admin。
```

---

#### 4.1.4 包含断言

句型：

```text
[手段] 容器 应包含 对象。
[手段] 容器 应不包含 对象。
```

示例：

```text
[api] 悬赏大厅数据 应包含 目标。
[playwright] 悬赏大厅列表 应显示 目标。
[prisma] 目标 的当前挑战者 应不包含 普通成员。
```

“显示”是 UI 层的包含。

“包含”是数据层或集合层的包含。

---

#### 4.1.5 UI 可交互断言

句型：

```text
[playwright] 对象 应可见。
[playwright] 对象 应不可见。
[playwright] 对象 应可点击。
[playwright] 对象 应不可点击。
[playwright] 对象 应可用。
[playwright] 对象 应不可用。
```

示例：

```text
[playwright] 主导航 应可见。
[playwright] 目标 的 "申请挑战" 操作 应可见。
[playwright] 目标 的 "申请挑战" 操作 应可点击。
[playwright] 目标 的 "已申请" 操作 应不可点击。
```

“可见”和“可点击”应该分开写。

推荐：

```text
[playwright] 目标 的 "申请挑战" 操作 应可见。
[playwright] 目标 的 "申请挑战" 操作 应可点击。
```

不推荐：

```text
[playwright] 目标 的申请按钮应能看到并可以点。
```

---

#### 4.1.6 变化断言

句型：

```text
[手段] 对象 的 状态 应变为 值。
[手段] 对象 的 状态 应保持 值。
```

示例：

```text
[prisma] 目标 的流转状态 应变为 applying。
[prisma] 目标 的流转状态 应保持 recruiting。
[api] 目标 对当前成员 应变为 已申请。
```

“变为”表示 Action 前后发生变化。

“保持”表示 Action 后仍然等于 Action 前或指定状态。

---

### 4.2 动作执行句

动作执行句用于描述测试实际做了什么。

主要用于：

```text
Setup
Action
Clean
```

#### 4.2.1 页面动作

句型：

```text
[playwright] 打开 页面。
[playwright] 点击 对象。
[playwright] 填写 字段 为 值。
[playwright] 选择 选项。
[playwright] 确认 弹窗。
[playwright] 提交 表单。
```

示例：

```text
[playwright] 打开 登录页。
[playwright] 使用 普通成员账号 登录。
[playwright] 打开 悬赏大厅。
[playwright] 点击 目标 的 "申请挑战" 操作。
[playwright] 在确认弹窗中点击 "申请挑战"。
```

---

#### 4.2.2 API 动作

句型：

```text
[api] 调用 接口。
[api] 读取 业务数据。
[api] 监听 请求。
[api] 等待 请求完成。
```

示例：

```text
[api] 读取 悬赏大厅数据。
[api] 监听 创建挑战申请请求。
[api] 等待 创建挑战申请请求完成。
[api] 注销 当前登录会话。
```

在主用例中优先写业务语义。

推荐：

```text
[api] 读取 悬赏大厅数据。
```

在实现映射中再写具体接口：

```text
GET /api/bounties
```

---

#### 4.2.3 数据动作

句型：

```text
[prisma] 创建 数据。
[prisma] 删除 数据。
[prisma] 更新 对象 的 属性 为 值。
[prisma] 恢复 对象 的 属性 为 原值。
```

示例：

```text
[prisma] 删除 本用例创建的挑战申请。
[prisma] 恢复 目标 的流转状态为 原流转状态。
[prisma] 清理 普通成员 的历史测试会话。
```

数据动作应谨慎使用。

如果某个数据是 B 的一部分，不应该在当前用例的 Action 中创建或删除。

---

#### 4.2.4 Mock 动作

句型：

```text
[mock] 配置 服务 对 请求 返回 响应。
[mock] 配置 接口 返回 成功。
[mock] 配置 接口 返回 失败。
```

示例：

```text
[mock] 配置 支付网关 对支付请求返回 支付成功。
[mock] 配置 邮件服务 记录发送请求。
```

Mock 应用于不可控、昂贵、外部依赖或非本用例关注点的系统。

Mock 不应该掩盖本用例真正要验证的业务动作。

---

### 4.3 运行时变量句

运行时变量句用于给测试过程中选出的对象命名。

句型：

```text
[手段] 选择 一个满足条件的对象 作为 名称。
[手段] 记录 对象 的 属性 作为 名称。
[手段] 记录 当前时间 作为 名称。
```

示例：

```text
[api] 选择 一个当前可申请的悬赏目标 作为 目标。
[api] 记录 目标 的 ID 作为 目标 ID。
[api] 记录 目标 的标题 作为 目标标题。
[prisma] 记录 目标 的申请前流转状态 作为 原流转状态。
[api] 记录 创建挑战申请响应中的申请 ID 作为 申请 ID。
```

运行时变量的命名应该使用业务名词。

推荐：

```text
目标
目标 ID
目标标题
原流转状态
申请 ID
动作开始时间
```

不推荐：

```text
runtime.bountyTarget
obj
data1
resp
```

---

### 4.4 条件句

条件句用于表达分支逻辑。

句型：

```text
若 条件，则 断言。
若 条件，则 执行动作。
若 条件 A，且 条件 B，则 执行动作。
```

示例：

```text
若 原流转状态 不是 recruiting，则 目标 的流转状态 应变为 applying。
若 原流转状态 是 recruiting，则 目标 的流转状态 应保持 recruiting。
若 目标 不存在其他 pending 挑战申请，且 原流转状态 不是 recruiting，则 恢复 目标 的流转状态为 原流转状态。
```

条件句不写成代码形式。

不推荐：

```text
if runtime.before.flowStatus !== "recruiting" then ...
```

---

### 4.5 任一结果句

任一结果句用于描述多个可接受结果。

句型：

```text
[手段] 应满足以下任一结果：
- 结果 A。
- 结果 B。
```

示例：

```text
[playwright] 应满足以下任一结果：
- 目标 的操作状态 显示为 "已申请"，且该操作不可点击。
- 目标 不再出现在 可申请目标列表 中。
```

任一结果句用于真实业务允许多种表现的情况。

不要用任一结果句掩盖不确定的预期。

如果系统应该只有一种正确行为，就只写一种断言。

---

### 4.6 清理恢复句

清理恢复句用于 Clean 阶段。

句型：

```text
[手段] 删除 本用例创建的对象。
[手段] 恢复 对象 的属性为 原值。
[手段] 清空 临时状态。
[手段] 注销 当前会话。
[手段] 应不存在 本用例残留。
```

示例：

```text
[prisma] 删除 本用例创建的挑战申请。
[prisma] 应不存在 本用例创建的挑战申请。
[api] 注销 当前登录会话。
[playwright] 清空 当前浏览器登录态。
[api] 当前会话 应为 未登录。
```

Clean 的句子必须表达两个目的：

```text
清理本用例新增或改变的内容
确认系统回到 B
```

---

## 5. 各阶段写法规范

### 5.1 B 阶段

B 阶段描述测试开始前和测试结束后都应该成立的基准状态。

B 阶段常用句型：

```text
[api] 服务 应可用。
[prisma] 数据库 应可连接。
[prisma] 数据库 schema 应为 当前测试版本。
[prisma] 应不存在 本用例不允许存在的残留数据。
[playwright] 当前浏览器 应为 未登录状态。
```

示例：

```text
[api] 前端服务 应可用。
[api] 后端服务 应可用。
[prisma] ORF 数据库 应可连接。
[api] Ory 服务 应可访问。

[playwright] 当前浏览器 应不存在 登录态。
[api] 当前会话 应为 未登录。
```

B 中不写 Action。

B 中不声明或依赖具体账号、身份、成员关系、目标或其他业务 fixture。

---

### 5.2 Setup 阶段

Setup 阶段描述如何把系统从 B 推进到 S0。

Setup 阶段常用句型：

```text
[api] 准备 本用例独占的登录身份，并设置固定测试密码。
[prisma] 准备 本用例独占的用户和成员关系。
[playwright] 创建新的浏览器上下文。
[playwright] 打开 页面。
[playwright] 使用 账号 登录。
[api] 读取 数据。
[api] 选择 一个满足条件的对象 作为 变量。
[prisma] 记录 对象 的当前状态 作为 原状态。
```

示例：

```text
[api] 准备 普通成员 的独占登录身份，并设置固定测试密码。
[prisma] 准备 普通成员用户和 member 成员关系。
[playwright] 创建新的浏览器上下文。
[playwright] 打开 登录页。
[playwright] 使用 普通成员账号 登录。
[playwright] 打开 悬赏大厅。

[api] 读取 悬赏大厅数据。
[api] 选择 一个当前可申请且当前成员尚未申请的悬赏目标 作为 目标。
[api] 记录 目标 的 ID 作为 目标 ID。
[api] 记录 目标 的标题 作为 目标标题。
[prisma] 记录 目标 的申请前流转状态 作为 原流转状态。
```

Setup 可以包含必要的过程动作，但不应该验证本用例的核心业务结果。

---

### 5.3 S0 阶段

S0 阶段描述 Action 发生前必须成立的状态。

S0 阶段常用句型：

```text
[api] 当前会话 应为 已登录。
[playwright] 当前页面 应为 指定页面。
[playwright] 指定业务对象 应可见。
[playwright] 指定业务操作 应可点击。
[prisma] 应不存在 会影响 Action 的残留数据。
```

示例：

```text
[api] 当前会话 应为 已登录。
[api] 当前登录用户 应为 普通成员。
[api] 当前登录用户 的角色 应为 member。
[api] 当前登录用户 的状态 应为 active。

[playwright] 当前页面 应为 悬赏大厅。
[playwright] 主导航 应可见。
[playwright] 当前用户显示 应为 "ORF Member E2E"。

[api] 悬赏大厅数据 应包含 目标。
[api] 目标 对当前成员 应为 尚未申请。
[api] 目标 对当前成员 应允许申请挑战。

[playwright] 悬赏大厅列表 应显示 目标。
[playwright] 目标 的 "申请挑战" 操作 应可见。
[playwright] 目标 的 "申请挑战" 操作 应可点击。

[prisma] 应不存在 普通成员 对 目标 的 pending 挑战申请。
```

S0 的作用是确认 Action 的起点正确。

---

### 5.4 Action 阶段

Action 阶段描述本用例唯一要验证的业务动作。

Action 阶段常用句型：

```text
[playwright] 点击 业务操作。
[playwright] 填写 表单字段 为 值。
[playwright] 提交 表单。
[playwright] 确认 弹窗。
[api] 监听 关键业务请求。
[api] 关键业务请求 应成功。
```

示例：

```text
[playwright] 点击 目标 的 "申请挑战" 操作。
[playwright] 提交挑战申请确认弹窗 应可见。
[playwright] 确认弹窗 应显示 "提交后等待指挥官确认"。

[api] 监听 创建挑战申请请求。
[playwright] 在确认弹窗中点击 "申请挑战"。
[api] 创建挑战申请请求 应成功。
```

Action 中可以有少量过程性断言，例如弹窗出现、关键请求成功。

但 Action 不应该包含：

```text
创建基础用户
修改权限
删除残留数据
恢复业务状态
注销登录
```

这些属于 B、Setup 或 Clean。

---

### 5.5 S1 阶段

S1 阶段描述 Action 后系统应该达到的目标状态。

S1 阶段常用句型：

```text
[prisma] 应存在 Action 创建的数据。
[prisma] 数据 的属性 应为 预期值。
[api] 业务对象 对当前用户 应变为 新状态。
[playwright] 页面 应显示 新状态。
[playwright] 页面 不应显示 错误提示。
```

示例：

```text
[prisma] 应存在 普通成员 对 目标 的 pending 挑战申请。
[prisma] 该挑战申请 的目标 应为 目标。
[prisma] 该挑战申请 的申请人 应为 普通成员。
[prisma] 该挑战申请 的状态 应为 pending。
[prisma] 该挑战申请 的创建时间 应不为空。
[prisma] 该挑战申请 应由本用例创建。

若 原流转状态 不是 recruiting，则 目标 的流转状态 应变为 applying。
若 原流转状态 是 recruiting，则 目标 的流转状态 应保持 recruiting。

[api] 再次读取 悬赏大厅数据。
[api] 目标 对当前成员 应为 已申请。

[playwright] 应满足以下任一结果：
- 目标 的操作状态 显示为 "已申请"，且该操作不可点击。
- 目标 不再出现在 可申请目标列表 中。

[playwright] 页面 不应显示 错误提示。
```

S1 不描述如何修复失败。

S1 只描述 Action 之后应该观察到什么。

---

### 5.6 Clean 阶段

Clean 阶段描述如何清理本用例产生的影响，使系统回到 B。

Clean 阶段常用句型：

```text
[prisma] 删除 本用例创建的数据。
[prisma] 恢复 被本用例改变的业务状态。
[api] 注销 当前会话。
[playwright] 清空 当前浏览器登录态。
[api] 当前会话 应为 未登录。
[prisma] 应不存在 本用例残留。
[prisma] 删除或恢复 本用例在 Setup 中准备的业务数据。
```

示例：

```text
[prisma] 删除 本用例创建的挑战申请。
[prisma] 应不存在 本用例创建的挑战申请。

若 目标 不存在其他 pending 挑战申请，且 原流转状态 不是 recruiting，则 恢复 目标 的流转状态为 原流转状态。

[api] 注销 当前登录会话。
[playwright] 清空 当前浏览器登录态。

[api] 当前会话 应为 未登录。
[playwright] 当前浏览器 应不存在 登录态。

[api] 删除 普通成员 的独占登录身份。
[prisma] 删除 普通成员 的独占用户和团队成员关系。
[prisma] 删除 本用例准备的目标。
[prisma] 应不存在 本用例创建的挑战申请残留。
```

Clean 不是可选项。

Clean 应删除或恢复 Setup 与 Action 准备或改变的独占业务数据，不应改变 B 中的环境与服务条件。

## 6. 业务语言和实现映射

### 6.1 主用例写业务语言

主用例应该写业务语义。

推荐：

```text
[api] 目标 对当前成员 应为 尚未申请。
[prisma] 应不存在 普通成员 对 目标 的 pending 挑战申请。
[playwright] 目标 的 "申请挑战" 操作 应可点击。
```

不推荐：

```text
[api] hasCurrentApplication === false。
[prisma] challengeApplications.findFirst(...) === null。
[playwright] page.locator(...).click()。
```

---

### 6.2 实现映射层写技术细节

如果需要把步骤翻译成代码，可以在测试实现、helper 或映射说明中定义技术细节。

例如，主用例写：

```text
[api] 目标 对当前成员 应为 尚未申请。
```

实现映射可以定义为：

```text
GET /api/bounties
在 availableItems 中找到目标
读取 hasCurrentApplication
期望 hasCurrentApplication = false
```

主用例写：

```text
[prisma] 应存在 普通成员 对 目标 的 pending 挑战申请。
```

实现映射可以定义为：

```text
challengeApplication.findFirst({
  where: {
    applicantId: member.id,
    objectiveId: target.id,
    status: "pending"
  }
}) 不为空
```

主用例写：

```text
[playwright] 点击 目标 的 "申请挑战" 操作。
```

实现映射可以定义为：

```text
在悬赏大厅列表中定位目标行
在目标行内定位名称为 "申请挑战" 的按钮
执行 click
```

---

### 6.3 字段名使用原则

字段名不是禁用项，但不应该优先出现在主用例中。

当字段名本身就是接口契约或业务规则的一部分时，可以出现。

推荐主用例写法：

```text
[api] 目标 对当前成员 应为 已申请。
```

接口契约写法：

```text
[api] 目标 的 hasCurrentApplication 字段 应为 true。
```

两者用途不同。

主用例关注业务状态。

接口契约关注字段准确性。

## 8. 推荐写法和不推荐写法

### 8.1 存在性表达

推荐：

```text
[prisma] 应存在 普通成员用户。
[prisma] 应不存在 普通成员 对 目标 的 pending 挑战申请。
```

不推荐：

```text
[prisma] 普通成员用户已存在。
[prisma] 申请不存在。
[prisma] user / exists = 1。
```

说明：

```text
“应存在 / 应不存在”更像测试断言。
“已存在”容易变成陈述，不够明确是不是预期。
“exists = 1”过于实现化。
```

---

### 8.2 属性表达

推荐：

```text
[prisma] 普通成员 的角色 应为 member。
[prisma] 普通成员 的状态 应为 active。
```

不推荐：

```text
[prisma] 普通成员是 member active。
[prisma] role = member, status = active。
```

说明：

```text
“对象 的 属性 应为 值”是稳定句型。
```

---

### 8.3 UI 表达

推荐：

```text
[playwright] 目标 的 "申请挑战" 操作 应可见。
[playwright] 目标 的 "申请挑战" 操作 应可点击。
```

不推荐：

```text
[playwright] 申请挑战按钮能点。
[playwright] 点申请挑战。
```

说明：

```text
断言可点击是一种状态。
点击是一种动作。
二者要分开写。
```

---

### 8.4 运行时选择表达

推荐：

```text
[api] 选择 一个当前可申请且当前成员尚未申请的悬赏目标 作为 目标。
```

不推荐：

```text
[api] 找一个目标。
[api] target = availableItems[0]。
```

说明：

```text
运行时选择必须写清楚选择条件和变量名称。
```

---

### 8.5 条件表达

推荐：

```text
若 原流转状态 不是 recruiting，则 目标 的流转状态 应变为 applying。
```

不推荐：

```text
if flowStatus != recruiting then applying。
```

说明：

```text
主用例使用自然语言条件句。
代码条件留给实现层。
```

```text
[prisma] 该挑战申请 的创建时间 应不为空。
[prisma] 该挑战申请 应由本用例创建。

若 原流转状态 不是 recruiting，则 目标 的流转状态 应变为 applying。
若 原流转状态 是 recruiting，则 目标 的流转状态 应保持 recruiting。

[api] 再次读取 悬赏大厅数据。
[api] 目标 对当前成员 应为 已申请。

[playwright] 应满足以下任一结果：
- 目标 的操作状态 显示为 "已申请"，且该操作不可点击。
- 目标 不再出现在 可申请目标列表 中。

[playwright] 页面 不应显示 错误提示。
```

### Clean：恢复到 B

```text
[prisma] 删除 本用例创建的挑战申请。
[prisma] 应不存在 本用例创建的挑战申请。

若 目标 不存在其他 pending 挑战申请，且 原流转状态 不是 recruiting，则 恢复 目标 的流转状态为 原流转状态。

[api] 注销 当前登录会话。
[playwright] 清空 当前浏览器登录态。

[api] 当前会话 应为 未登录。
[playwright] 当前浏览器 应不存在 登录态。

[api] 删除 普通成员 的独占登录身份。
[prisma] 删除 普通成员 的独占用户和团队成员关系。
[prisma] 删除 本用例准备的目标。
[prisma] 应不存在 本用例创建的挑战申请残留。
```

## 10. 给 Codex 或测试生成器的理解规则

Codex 或测试生成器在读取步骤语言时，应先识别句子的业务语义，再选择具体实现方式。

### 10.1 先识别阶段

先确定当前句子位于哪个阶段：

```text
B
Setup
S0
Action
S1
Clean
```

阶段决定句子的职责。

同一句话在不同阶段可能有不同意义。

例如：

```text
[prisma] 应不存在 普通成员 对 目标 的 pending 挑战申请。
```

在 S0 中表示 Action 前置条件。

在 Clean 中表示清理后无残留。

---

### 10.2 再识别手段

根据标签选择适配器：

```text
[playwright] -> 页面操作或 UI 观测
[api] -> HTTP 请求、会话、接口返回、服务可用性
[prisma] -> 数据库查询或数据修改
[mock] -> 外部依赖替身或响应配置
```

---

### 10.3 再识别句型

根据谓语识别意图：

```text
应存在 / 应不存在 -> 存在性断言
应为 / 应属于 -> 属性断言
应可见 / 应可点击 -> UI 状态断言
打开 / 点击 / 登录 / 提交 -> 动作执行
选择 / 记录 -> 运行时变量绑定
删除 / 恢复 / 清空 -> 清理恢复
若 / 则 -> 条件分支
任一结果 -> 多分支可接受结果
```

---

### 10.4 最后翻译实现

翻译时应尽量保持业务语义稳定。

例如：

```text
[playwright] 目标 的 "申请挑战" 操作 应可点击。
```

优先翻译为：

```text
通过目标标题或业务标识定位目标行
在目标行内通过角色和可访问名称定位 "申请挑战" 按钮
断言按钮可见且 enabled
```

不优先翻译为：

```text
使用 CSS nth-child 定位按钮
```

## 11. 文档模板

新的测试用例可以按以下模板书写。

```markdown
# 用例：xxx

## 1. 测试目标

验证：xxx。

边界：

- 不验证 xxx。
- 不验证 xxx。

## 2. 状态模型

### B：基准状态

[api] xxx 应可用。
[prisma] 数据库 schema 应为 当前测试版本。
[playwright] 当前浏览器 应不存在 xxx。

### Setup：构造 S0

[api] 准备 本用例独占的登录身份。
[prisma] 准备 本用例独占的业务数据。
[playwright] 打开 xxx。
[api] 选择 一个满足 xxx 的对象 作为 xxx。
[api] 记录 xxx 作为 xxx。

### S0：Action 前状态

[api] xxx 应为 xxx。
[playwright] xxx 应可见。
[playwright] xxx 应可点击。
[prisma] 应不存在 xxx。

### Action：本次测试唯一业务动作

[playwright] 点击 xxx。
[api] 监听 xxx 请求。
[playwright] 提交 xxx。
[api] xxx 请求 应成功。

### S1：Action 后状态

[prisma] 应存在 xxx。
[api] xxx 应变为 xxx。
[playwright] xxx 应显示 xxx。
[playwright] 页面 不应显示 错误提示。

### Clean：恢复到 B

[prisma] 删除 本用例创建的 xxx。
[prisma] 恢复 xxx 为 原状态。
[api] 注销 当前会话。
[playwright] 清空 当前浏览器登录态。
[prisma] 应不存在 本用例残留。
```

## 12. 总结

数据化测试步骤语言的目标不是把测试写成代码，而是把测试步骤写成规范、稳定、可执行映射的中文。

它的核心是：

```text
用业务对象描述主体
用稳定谓语描述动作和状态
用执行手段标签标注观测或执行方式
用 B、Setup、S0、Action、S1、Clean 保持测试结构
用受控句型保证测试文档可以被人读懂，也可以被工具翻译
```

最终效果应该是：

```text
测试文档读起来像业务测试说明
测试生成器读起来像可执行规格
测试代码落地时可以映射到 Playwright、API、Prisma、Mock
```

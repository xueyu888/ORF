# ORF 自适应材质系统

本文定义 ORF 如何消费用户自定义背景、如何生成窗口级材质，以及页面可以使用哪些视觉角色。它是背景与材质的唯一规范；通用组件几何、色彩语义和页面验收继续以 [ORF 前端视觉系统.md](./ORF%20前端视觉系统.md) 为准。

## 1. 目标与边界

ORF 的背景不是被遮住的装饰图，而是界面的环境光。材质系统必须同时获得两类品质：

- 稳定、克制、可预测：高信息密度、长时间工作和 Windows 桌面窗口中始终清楚。
- 有生命力、能感知环境：不同背景真实影响材质的色温、通透度和边缘光，而不是被固定灰白或深黑蒙层抹平。

材质系统只负责视觉派生，不改变背景选择、上传、裁剪、切换、权限、接口业务语义或数据保留规则。前端分析结果不写回业务数据，也不成为后端事实源。

## 2. 状态模型与唯一事实源

完整状态链如下：

```text
背景图片 / 裁剪 / 槽位 / 材质偏好 / 外观模式
→ 计算当前槽位真正可见的图片区域
→ 低分辨率分析亮度、色相、饱和度、动态范围和复杂度
→ 材质策略生成该槽位的光学参数
→ sidebar / topbar / workspace 三个常驻层发布 CSS 变量
→ 页面只消费 content / floating / modal 等语义角色
```

必须严格区分四类状态：

| 类型 | 内容 | 生命周期 |
| --- | --- | --- |
| 业务事实 | 图片、裁剪、槽位、切换规则、用户材质偏好、外观模式 | 由既有设置接口保存 |
| 派生数据 | 可见区域、亮度分位数、平均色、动态范围、复杂度、材质参数 | 本地计算并缓存，可随时重建 |
| 展示状态 | 当前槽位的 CSS 变量、外观派生的稳定前景语气、透明度回退 | 只存在于当前渲染树 |
| 临时状态 | hover、press、窗口失焦、背景过渡 | 不写入设置，不触发重新分析 |

必须保持以下不变量：

1. 同一时刻最多只有 `sidebar`、`topbar`、`workspace` 三个常驻模糊材质层。
2. 列表、表格、卡片、表单分组和页面内容面不得再次使用 `backdrop-filter`。
3. 背景图片保留原始颜色，不因亮色或暗色主题被整体降亮度、降饱和或染成固定色。
4. 图片分析只在图片、裁剪或槽位可见比例发生实质变化时运行；hover、路由内展开和普通重渲染不得重复运行。
5. 分析失败、浏览器不支持模糊、用户减少透明度或高对比模式开启时，界面必须切换到稳定实色或近实色回退。
6. 文字、图标、语义色和焦点环由主题与可访问性 token 保证；不得依赖背景图片本身提供对比度。
7. 页面不能拥有自己的材质算法、固定玻璃滤镜或背景专用遮罩。

## 3. 模块职责

```text
src/features/appearance/material/
├─ backgroundViewport.ts       计算 cover-crop 后真正可见的源图区域
├─ backgroundAnalyzer.ts       调度 Worker、缓存和失败回退
├─ backgroundAnalyzer.worker.ts 低分辨率像素分析
├─ materialPolicy.ts           纯函数：分析结果 + 偏好 + 角色 + 外观 → 参数
├─ materialTokens.ts           角色、参数、CSS 变量和稳定回退契约
├─ materialCache.ts            有界内存缓存和并发请求去重
├─ useAdaptiveMaterial.ts      React 生命周期与视口变化协调
└─ VisualMaterialLayer.tsx     唯一常驻材质层组件
```

模块边界：

- `backgroundViewport` 不读取 DOM、不请求网络，只做几何计算。
- `backgroundAnalyzer.worker` 不知道页面、主题或 CSS，只输出客观图像特征。
- `materialPolicy` 不读取图片或 DOM，只把稳定输入映射为稳定输出。
- `useAdaptiveMaterial` 负责编排，不自行发明视觉参数。
- `VisualMaterialLayer` 只渲染材质，不拥有背景选择或业务状态。
- AppShell 只组合三个常驻角色；页面不能直接实例化常驻材质层。

## 4. 背景分析契约

分析尺寸固定在最长边 96 像素附近；这是材质决策，不是图像识别，不需要保留细节。Worker 只采样 `cover-crop` 后当前槽位可见的源图区域。

输出至少包含：

- 线性 sRGB 相对亮度的 `p10 / p50 / p90`。
- 平均 RGB 与经 OKLab 收敛后的环境 tint。
- 平均饱和度。
- 动态范围 `p90 - p10`。
- 极暗与极亮像素占比。
- 相邻像素亮度差形成的边缘密度。
- 由动态范围、边缘密度和饱和度合成的复杂度。

颜色计算先将 sRGB 转为线性光，再进入 OKLab；不能直接在 gamma 编码后的 RGB 上平均明暗。缓存键由图片 URL、裁剪和槽位宽高比桶组成。缓存必须有容量上限，背景切换并发请求必须去重。

## 5. 材质策略

### 5.1 用户偏好

每个背景槽位拥有以下偏好：

- `tone`: `auto | soft-light | soft-dark`。它只控制材质 tint 的光学基底；`auto` 根据可见背景选择柔亮或柔暗材质，不能反转文字、图标、控件和语义色。最终前景始终由用户选择的亮色或暗色外观决定。
- `exposure`: `0..1`。从“安静”到“鲜活”，只影响算法偏置，不直接等于蒙层透明度。
- `overlayStrength`: `0..1`。控制自适应 tint 遮罩相对角色基线的强度；`0` 必须得到零 tint 遮罩，`1` 保留策略完整强度。
- `blurStrength`: `0..1`。控制角色派生模糊的相对强度；`0` 必须得到零模糊并关闭无意义的背景滤镜，`1` 保留策略完整强度。
- `reduceTransparency`: 布尔值。开启后使用近实色材质，不运行常驻模糊。

### 5.2 派生参数

`materialPolicy` 为每个角色生成：

```ts
type AdaptiveMaterial = {
  backdropTone: "soft-light" | "soft-dark";
  tintColor: string;
  tintOpacity: number;
  blurRadius: number;
  saturation: number;
  noiseOpacity: number;
  borderLightOpacity: number;
  borderDarkOpacity: number;
  shadowOpacity: number;
  transparency: "adaptive" | "reduced" | "fallback";
};
```

策略约束：

- 用户外观是页面前景明暗的唯一事实源；背景分析只派生 tint、透明度、模糊、饱和度、边界光和阴影。切换背景、裁剪或材质 tone 不得改变文字与控件明暗。
- 背景越复杂或动态范围越大，材质可适度增加模糊与 tint，但不能通过压暗原图解决。
- `exposure` 越高，材质越薄、背景色温参与越多；越低则更稳定，但仍保留环境 tint。
- `overlayStrength` 与 `blurStrength` 只缩放统一策略的派生结果，不保存页面或角色的固定 CSS 数值；二者必须正交，调整一个不得暗中改写另一个。
- `sidebar` 必须比 `topbar` 更薄且默认不模糊，让背景主体清晰可辨；导航可读性由浅色文字、图标阴影和局部交互态保证，不得再使用固定的重黑遮罩。
- `workspace` 只建立窗口级阅读底座，内容面使用低对比半透明填充，不再次模糊。
- `workspace` tint 与 `content` 主表面必须按最终叠加结果共同校准，不能分别看都透明、叠加后却接近实色。默认 exposure 与中等复杂背景下，中性色遮罩的合成覆盖目标约为 76%–78%，至少让约五分之一、目标让约四分之一的背景色彩与光影继续参与内容面观感。
- 主内容面、次级内容面和控件面必须形成逐级变薄的透光关系；可读性优先通过文字语义色、局部控件底、细描边和阴影保证，不得靠提高整张卡片的不透明度解决。
- 降低透明度、高对比或能力不支持时，`blurRadius` 必须为 0，并使用足够稳定的近实色填充。
- 窗口失焦只提高少量材质稳定度，不重新分析图片，不改变布局。

## 6. 角色系统

页面和组件只能消费以下角色：

| 角色 | 所有者 | 是否允许常驻模糊 | 用途 |
| --- | --- | ---: | --- |
| `sidebar` | AppShell | 是 | 全局导航材质 |
| `topbar` | AppShell | 是 | 窗口标题、搜索和全局操作 |
| `workspace` | AppShell / AuthPage | 是 | 当前页面或登录入口的环境底座 |
| `content` | 页面/组件 | 否 | 表格、列表、编辑器、统计面板、设置分组 |
| `floating` | 通用浮层 | 临时允许 | Popover、菜单、搜索结果、预览、Toast |
| `modal` | 通用弹窗 | 临时允许 | Dialog 与需要隔离注意力的确认流程 |

`content` 通过统一的 `--orf-material-content-*` 变量表达层级。其中 `container` 只负责把一组内容框成整体，必须比内部 `primary / secondary / tertiary` 表面更薄，避免工作台外框与内部列面板重复叠加成实色。页面只决定布局、信息密度和少量语义强调，不得定义 `--*-glass-filter`、背景专用 tint 或固定 blur。

## 7. 配置迁移

背景配置从 v2/v3 无损迁移到 v4：

1. 保留图片、裁剪、模式、切换规则和间隔。
2. 旧 `overlayOpacity` 写入 `migration.overlayOpacityV2`，用于审计和回溯，不再成为运行时材质输入。
3. 首次迁移时根据旧值生成一次 `material.exposure` 初始值；此后只保存和读取新的材质偏好。
4. v3 配置补入 `material.overlayStrength = 1` 与 `material.blurStrength = 1`，升级前后的默认视觉保持不变；用户随后可分别调至 `0`。
5. v4 保存后不再输出运行时 `overlayOpacity`，前端也不得读取它。
6. 系统设置和个人设置使用同一规范化函数；不存在只迁移一侧的兼容路径。

迁移不得删除背景文件、裁剪或用户偏好。旧字段退出运行时后，应删除前端控件、CSS 变量和代码引用，避免新旧系统同时影响结果。

## 8. 字体与数字

界面字体栈统一为：

```css
"Segoe UI Variable Text",
"Segoe UI Variable",
"Noto Sans CJK SC Variable",
"Microsoft YaHei UI",
sans-serif
```

正文、标签和标题主要使用 400、500、600 三档。数据表、积分、日期、时间、百分比和统计值使用 `font-variant-numeric: tabular-nums`，避免刷新时列宽抖动。若项目分发字体，只能使用许可证允许再分发并随构建明确归档的字体资产。

## 9. Windows 桌面连续性

- Electron 窗口创建时的 `backgroundColor` 必须与缓存的亮/暗外观同步，避免暗色启动闪白。
- 自定义背景存在时，Web 材质系统始终是事实实现；系统原生 Mica 只能在没有自定义背景时作为能力回退，不能改变页面角色契约。
- 1360、1920、2560 三档桌面宽度都要检查材质连续性、表格密度和背景暴露量。
- 窗口失焦、恢复、缩放和侧边栏宽度变化不得出现整层闪烁或重新解码背景。

### 9.1 聊天工作台

- 聊天保留已经验证的“频道栏 / 消息流 / 按需右面板”结构与消息阅读密度；背景改造不得重新发明信息架构。
- 聊天与其他页面遵循同一个稳定前景契约：前景亮暗由用户外观设置决定；页面背景只通过半透明的频道栏、消息画布、标题栏和输入区传递色相与光影，不能让背景分析在会话中途反转文字明暗。
- 常驻聊天表面只消费 AppShell 的页面材质，不增加页面级模糊层。消息画布最稳定，频道栏与右面板提供次级纵深，标题栏、输入框和浮层使用更高不透明度保障边界与操作识别。
- 胶囊和圆形优先用于搜索、筛选、频道入口和图标按钮；多行文本框、数据行与资源卡片使用适度圆角，不能因为统一圆角而把非按钮内容做成胶囊。顶部菜单必须支持 `Escape` 关闭及方向键、`Home`、`End` 导航。

## 10. 验收矩阵

样板页先使用悬赏大厅。至少覆盖以下六种背景与主题组合：

1. 亮色主题 + 极亮背景。
2. 亮色主题 + 极暗背景。
3. 亮色主题 + 高饱和复杂背景。
4. 暗色主题 + 极亮背景。
5. 暗色主题 + 极暗背景。
6. 暗色主题 + 高饱和复杂背景。

每组继续检查独立的侧边栏、顶栏和页面背景，以及默认、hover、focus-visible、展开指标、表格溢出、浮层、窗口失焦和移动视口。验收门槛：

- 原图没有主题级 `brightness`、`saturate` 或固定颜色滤镜。
- 常驻 `backdrop-filter` 层不超过三个，页面内容不存在嵌套模糊。
- 背景切换和主题切换没有闪白、闪黑或先显示旧蒙层。
- 极亮和极暗背景上没有生硬纯白/纯黑大块，也没有文字丢失。
- 背景仍能辨认色彩与光影，内容在长时间阅读下保持稳定。
- 透过主内容卡片仍能感知背景的主色倾向；不能只在卡片外侧空白区看见背景。
- 无透明能力、减少透明度和高对比模式均有可读回退。
- 页面样式只消费统一角色，不再携带页面私有玻璃算法。

## 11. 实施与清理顺序

1. 固化本文、前端视觉总规范和代码 token 契约。
2. 实现可见区域、分析 Worker、缓存、策略和材质层。
3. 完成 v2/v3 → v4 无损迁移，将遮罩与模糊改为统一策略上的两个正交强度设置。
4. AppShell 接入三个常驻层，移除主题对原图的整体滤镜。
5. 在悬赏大厅完成六场景和三档桌面分辨率闭环。
6. 统一其他非聊天页面，删除页面私有 glass/tint/blur 规则。
7. 完成字体、Electron 启动底色、能力回退、高对比、减少透明度、失焦和移动端收尾。
8. 用引用搜索、构建、自动检查和真实截图证明旧运行时路径已经退出。

任何阶段都不得保留“旧蒙层仍生效、新材质也生效”的双重控制。迁移可以兼容数据，渲染路径必须唯一。

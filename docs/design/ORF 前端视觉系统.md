# ORF 前端视觉系统

本文是 ORF 前端视觉语言、组件几何和视觉验收的唯一规范。业务状态、权限、接口和数据保留规则仍以对应的 `docs/rules`、`docs/frontend`、`docs/backend` 文档为事实源；本文不得重新定义业务语义。

## 1. 目标与边界

ORF 是高信息密度的工作台，不是展示型官网，也不是主题皮肤陈列页。视觉系统的目标是让用户更快确认当前上下文、识别下一步动作、阅读证据并完成协作。

- 前端可以重组布局、组件组合、信息顺序和交互呈现，但不得借视觉改造改变接口语义、权限、业务状态流或数据写入行为。
- 亮色和暗色是两套独立校准的主题，不通过简单反色生成。
- Windows 桌面端、Web 桌面端和移动端共享同一业务事实源；响应式布局只改变编排和导航，不复制业务状态。
- Apple、Linear 和 Fluent 只作为质量参照，不复制某一产品的外观。ORF 必须形成自己的清晰、克制、精密的工具感。

## 2. 唯一事实源与模块边界

```text
视觉语义文档
  └─ designTokens / appearance tokens       颜色、间距、字阶、线条、圆角、阴影、动效
      ├─ ui primitives                       按钮、输入、标签、浮层等通用组件
      ├─ app shell                           侧边栏、顶栏、页面出口、移动导航
      └─ feature styles                      页面结构与该页面独有状态
```

必须保持以下不变量：

1. `designTokens` 和外观模块是颜色、层级、几何、密度和动效的代码事实源。
2. 通用组件拥有自己的结构、状态和可访问性；页面不能重新发明按钮、输入框或浮层。
3. AppShell 只拥有全局导航、窗口级层次和背景槽位，不拥有页面业务布局。
4. 页面样式只表达页面布局、信息优先级和页面独有状态，不能重定义全局 token 或通用控件。
5. 用户背景配置仍是事实；前景材质、遮罩和文字对比度由外观系统派生，不能把图片颜色当作可依赖的设计 token。
6. hover、focus、展开、临时选择和浮层开关是 UI 状态，不进入业务数据或背景配置。
7. 禁止通过文件末尾的高优先级选择器、`!important` 堆叠或跨页面大选择器修复局部视觉问题。冲突必须回到所属模块解决。

## 3. 视觉层级

界面只保留四个稳定层级：

| 层级 | 用途 | 表达方式 |
| --- | --- | --- |
| Atmosphere | 用户自定义背景、品牌氛围 | 降低对比和饱和度，仅在结构之外可见 |
| Canvas | 页面工作区 | 稳定实色或近实色背景，不依赖模糊维持可读性 |
| Surface | 列表、编辑器、设置区、聊天阅读区 | 1px 发丝线、极轻层差；同层内容优先连续排布 |
| Floating | 菜单、Popover、Dialog、Toast | 明确边界和阴影；关闭后不改变底层结构 |

毛玻璃不是默认材质。只有窗口级导航或临时浮层确实需要表现空间关系时才允许少量使用；内容层不使用大面积模糊。参考 Apple 对材质层级和控件层的使用边界，以及 Fluent 对描边和 elevation 的层次定义。

同一层级不能靠连续套卡片表达。列表行、聊天消息和表单分组优先使用留白、对齐、分隔线和字阶；只有可独立移动、选择或操作的内容单元才成为卡片。

## 4. 色彩与主题

### 4.1 亮色

- 页面背景是冷静的近白灰，不使用脏灰或大面积半透明白雾。
- 主内容面使用稳定白色，边界以低对比发丝线建立。
- 主文字接近深墨蓝，次文字保持足够对比度，不以过浅灰色制造“高级感”。
- 强调色只用于主操作、当前选择、链接和必要的信息标记。

### 4.2 暗色

- 页面背景和内容面必须有可辨认的层差，避免所有区域混成同一块黑色。
- 不使用纯黑背景和纯白正文；通过深蓝灰层级、描边和有限阴影表达结构。
- 强调色降低面积和发光，不能产生霓虹边缘或泛蓝雾。
- 图片背景上方的前景内容仍使用稳定暗色材质，不把透明度当作主题层次。

### 4.3 语义色

成功、警告、危险、信息和中性色只表示状态，不承担装饰。每个语义色必须同时定义文字、背景、边框和暗色主题值；不得只以颜色传递状态。

## 5. 几何与组件语法

- 带文字的按钮、筛选器、标签页、切换器和短输入控件使用真正的胶囊形：高度固定，圆角为高度的一半。
- 仅图标按钮使用正圆；图标在视觉中心，不允许椭圆或近方形圆角按钮。
- 多行内容、列表行、卡片、表单区、弹窗、编辑器和预览面板不是按钮，不做胶囊。
- 卡片圆角必须克制且统一；禁止在同一页面混用多组相近但不相等的圆角。
- 图标采用一致的视觉笔画，常用尺寸为 16、18、20；图标不能依赖不同线宽制造层级。
- 桌面点击目标和移动触控目标分别满足其平台可用性；视觉尺寸较小的圆形按钮仍要有足够命中区。

通用控件的几何由组件变体决定，不通过类名包含 `button`、`tab`、`action` 等字符串的全局选择器猜测语义。

## 6. 字体、密度与注意力

- 页面标题只负责定位，不与主操作竞争。
- 主操作在一个视口内原则上只有一个最高强调级；次操作、筛选和工具按钮逐级降噪。
- 数字、状态、截止时间和负责人按任务优先级排版，不让装饰图标占据首要视觉位置。
- 高密度页面通过对齐、列宽、字阶和行高获得效率，不通过压缩可读性获得“紧凑”。
- 空状态、错误态、加载态、只读态和禁用态必须保持原布局上下文，避免页面跳变。

## 7. 背景系统

登录页、顶部栏、侧边栏和页面内容区继续使用既有独立背景槽位。视觉系统只规定如何消费这些背景，不改变背景数据契约。

- 背景是 atmosphere，不是内容面。
- 任意用户图片都必须经过主题相关的遮罩、明度和对比度保护。
- 侧边栏和顶栏必须在极亮、极暗、高饱和、复杂纹理图片上保持导航可读。
- 页面背景不能穿透正文列表、表格、编辑器或聊天阅读面。
- 背景的裁剪、缩放、选择和回退规则以《设置边界规则》为事实源。

## 8. 页面结构原则

### 8.1 桌面与 Web

- AppShell 提供稳定导航和页面坐标；页面内容围绕一个主要工作面组织。
- 侧栏、主区、检查器三栏只在任务确实需要同时比较时出现；不能为了填满宽度长期保留空栏。
- 工具栏将搜索、筛选、排序和主操作按任务顺序组织，而不是平均分布。

### 8.2 移动端

- 移动端是重新编排，不是桌面页面等比缩小。
- 首屏先出现当前上下文、核心状态和下一步动作；辅助统计和解释后置。
- 浮动操作不得遮挡消息、表单、底部导航或系统安全区。
- 列表、详情和编辑器的移动切换只改变展示状态，不复制业务数据。

## 9. 样板页与验收门槛

视觉系统先在悬赏大厅、聊天、个人设置三类样板页闭环，再扩展到全站：

- 悬赏大厅验证高密度列表、筛选、状态和主操作。
- 聊天验证长文本、连续阅读、附件、回复、消息操作、空态和异常态。
- 个人设置验证表单分组、外观主题、背景配置和平台能力。

每个样板页必须检查亮色、暗色、桌面、Windows 窗口和移动视口，并覆盖默认、hover、focus-visible、加载、空、错误、禁用、溢出和浮层状态。构建通过和无控制台错误只是工程门槛，不能代替截图级视觉验收。

## 10. 遗留清理规则

- 已停用的主题文档、预览路由、配置项、参考资产和只服务于旧主题的组件必须同时删除，不能保留隐式入口。
- 生产样式不得导入旧主题 token 或组件样式。
- 重命名或迁移样式模块时，必须清理旧路径和旧选择器；不保留没有调用方的兼容别名。
- 业务兼容接口、旧数据读取和背景迁移不属于视觉遗留，必须遵守对应业务文档，不能随前端清理删除。
- 每次改造都要用引用搜索、构建、自动检查和真实截图证明旧路径已退出、新模块已闭环。

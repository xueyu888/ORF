# 用户管理 - 后端

## 接口访问约定

前端数据统一通过同源 `/api` 请求后端接口，例如 `/api/tasks`。
前端不直接写死后端域名或端口，开发和生产环境由代理或网关转发到实际后端服务。

前端页面和交互见 [用户管理 - 前端.md](../frontend/用户管理%20-%20前端.md)。

## 认证边界

- Ory Kratos 负责注册、登录、密码和 session。
- ORF 后端提交账号密码到 Ory，并通过 Ory `/sessions/whoami` 校验登录态。
- Ory 和 ORF 都使用 PostgreSQL 数据库实现。
- ORF 数据库保存业务用户、默认作用域成员关系、成员角色、最近在线时间和 Ory identity 绑定。
- 删除已绑定登录身份的用户需要配置 `ORY_ADMIN_URL`，后端会通过 Ory Kratos admin API 删除对应 identity；未配置时拒绝删除，避免本地账号已删但 Ory 账号仍可登录。
- `users.id` 是 ORF 内部不可变 UUID 主键，不能由邮箱、姓名或 Ory traits 推导；邮箱是可变登录/联系属性，姓名是可变显示属性。
- ORF 目标挑战者、征召、申请人、指标提出人、任务执行人、反馈处理人、战利品、试验收、对齐申请和匿名互评等业务参与关系以 `users.id` 派生的 UUID 字段为唯一身份事实源；旧姓名字段只作为展示快照或兼容读模型，不参与权限和归属判断。
- 用户头像事实源是 `users.avatar_object_key`、`users.avatar_mime_type` 和 `users.avatar_updated_at`；接口只暴露派生 `avatarUrl`，不暴露对象存储 key。
- 已绑定账号用 `users.ory_identity_id` 映射 Ory identity；未绑定的预批准成员和历史数据才按 `traits.email` 回退匹配。
- 未通过 Ory session，不能访问 ORF `/api` 业务接口。
- 数据库不可用时，Ory 登录成功也不能进入 ORF。
- 业务 API 在全局 `preHandler` 完成一次 session 校验，并在同一请求内复用已校验用户，避免路由处理阶段重复请求 Ory。
- Ory 或数据库不可用时返回 503，不把基础设施故障伪装成账号未授权。
- 开发环境的 Ory Kratos 必须使用有界 PostgreSQL 连接池。`npm run ory:dev` 会通过 `scripts/prepare-ory-env.ts` 在运行时 DSN 上写入 `max_conns`、`max_idle_conns`、`max_conn_idle_time` 和 `max_conn_lifetime`，默认值见 `.env.example`；不要让 Ory 长期保留几十个 idle 连接挤占 ORF API 和真实 E2E 测试。成员接入共享 Ory 时，只需要把 `.env` 的 `ORY_PUBLIC_URL` 指向公共入口，不要本地启动 `ory:dev`。

## 业务规则

- 新 Ory identity 首次进入 ORF 时，按邮箱创建或更新 ORF 用户。
- 如果邮箱命中未绑定的预批准成员，后端写入 `users.ory_identity_id`，后续登录按 identity ID 识别该成员。
- 如果 identity ID 已绑定，后端优先使用 identity ID 识别成员；Ory 邮箱变化不能让同一 identity 生成重复 ORF 用户。
- 新用户默认加入默认运行时作用域，角色为 `member`。
- 首次通过密码登录进入 ORF 的 Ory identity 也必须创建为 `pending`，不能绕过注册审核直接成为 `active`。
- 已存在的 ORF 用户再次登录时，后端只刷新最近在线时间，不用 Ory traits 覆盖 ORF 显示名；显示名只能通过用户管理接口修改。改名不迁移业务参与记录，业务归属继续由 UUID 字段保持不变，读取时再按当前 `users.name` 生成展示名。
- Ory 已存在相同邮箱 identity 时，注册失败，前端显示 `邮箱已存在`。
- 登录、注册、创建成员和编辑成员的后端接口都在请求边界裁剪邮箱首尾空白并统一转成小写；注册姓名和成员姓名也会裁剪首尾空白，裁剪后为空时拒绝写入。
- 管理员新增成员是预批准成员：ORF 先保存 `active` 成员关系；该邮箱首次完成 Ory 注册或登录后才绑定 `ory_identity_id`。
- 预批准成员和已绑定成员都可以通过用户管理接口编辑邮箱；已绑定成员修改邮箱时，后端必须先通过 Ory admin API 同步对应 identity 的 `traits.email`，再更新 ORF `users.email`。
- 管理员不能删除自己，也不能将自己的角色降级为成员。
- `PATCH /api/users/:userId/disable` 是停用账号：保留 ORF 用户、默认作用域成员关系和 Ory identity，只把 `users.status` 改为 `disabled`，用于保留历史责任主体但禁止继续使用。
- `PATCH /api/registration-requests/:userId/reject` 是拒绝注册：保留申请痕迹和账号绑定，状态为 `rejected`。
- `DELETE /api/users/:userId` 是账号级硬删，不是从团队移除。只允许删除未被 ORF 业务记录引用的用户；成功后删除 ORF 用户、默认作用域成员关系、收件通知、未挂接评论的个人临时附件、已绑定 Ory identity，并清理头像和个人设置等个人派生数据。
- 如果成员已经创建、更新或参与过目标、指标、行动项、反馈、评论、附件、战利品、互评、对齐申请、试验收或积分流水等 ORF 业务记录，后端返回 `409 User is referenced by ORF records`，管理员应使用停用。
- 当前默认作用域内成员显示名大小写不敏感唯一，避免列表、筛选、点名输入和展示快照出现歧义；历史业务记录中的旧展示名不会阻止新显示名写入。
- 编辑已有成员显示名时，后端只更新 `users.name` 和成员投影，不迁移 ORF 业务表里的旧展示快照；如果新显示名已经属于当前默认作用域内其他成员，后端返回 409。
- 所有用户管理接口都需要管理员权限；用户只能通过最近在线上报接口更新自己的在线时间。
- 头像写入不是管理员用户管理能力；`POST /api/users/me/avatar` 和 `DELETE /api/users/me/avatar` 只能修改当前 session 用户自己的头像。
- `GET /api/users/:userId/avatar` 需要已认证 active 用户，并只允许读取当前用户默认作用域内的用户头像文件。

## 头像接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| `POST` | `/api/users/me/avatar` | 已激活登录用户本人 | 上传或替换当前用户头像，支持 PNG、JPEG、GIF、WebP。 |
| `DELETE` | `/api/users/me/avatar` | 已激活登录用户本人 | 删除当前用户头像并回退首字母占位。 |
| `GET` | `/api/users/:userId/avatar` | 同默认作用域已激活用户 | 受控读取头像图片内容。 |

头像上传复用统一图片校验：后端必须同时校验声明 MIME、真实文件头和 `OBJECT_STORAGE_UPLOAD_MAX_BYTES`。上传成功后返回当前用户 `OrfUser` 投影，客户端用它同步侧边栏、成员列表和评论输入区身份展示。

## 身份绑定用例

| 用例 | 输入 | 结果 |
| --- | --- | --- |
| 预批准成员首次注册 | ORF 已有 `active` 用户，`ory_identity_id = null`，Ory 返回同邮箱 identity | ORF 绑定 `ory_identity_id`，用户保持原显示名、角色和状态 |
| 已绑定成员再次登录 | Ory 返回已绑定 identity ID | 后端按 identity ID 找到同一 ORF 用户，不按邮箱创建新用户 |
| 已绑定成员邮箱漂移 | Ory identity ID 匹配，Ory traits email 与 ORF email 不同 | 仍返回同一 ORF 用户，不创建重复 pending 用户 |
| 绑定后编辑邮箱 | `PATCH /api/users/:userId` 修改已绑定用户邮箱，且 Ory admin API 可用 | 同步 Ory identity 邮箱并更新 ORF `users.email`，`users.id` 不变 |
| 绑定后编辑邮箱但 Ory 不可写 | `PATCH /api/users/:userId` 修改已绑定用户邮箱，且 Ory admin API 未配置或拒绝 | 返回 503 或 409，ORF 用户邮箱不写入 |
| 绑定前编辑邮箱 | `PATCH /api/users/:userId` 修改未绑定预批准用户邮箱 | 按邮箱唯一性规则更新邮箱，`users.id` 不变 |

## 最近在线口径

- 用户模型暴露 `lastOnlineAt` 作为成员管理的最近在线时间。
- 最近在线不是审计登录时间；登录审计如果后续需要，应单独设计审计表或 auth 日志。
- 没有在线记录的用户返回 `lastOnlineAt = null`。
- 登录和注册成功后写入 `lastOnlineAt = now`；前端真实交互上报 `POST /api/users/me/activity` 时也写入 `lastOnlineAt = now`。
- 最近在线时间必须由服务端生成，客户端不能提交时间戳。
- 后端必须对在线上报做持久化节流；同一用户距离上次 `lastOnlineAt` 不足 60 秒时不写库。
- 在线上报只允许已认证 ORF 用户更新自己，不能替其他用户写入在线时间；业务接口的 active 审批边界保持不变。

# 用户管理 - 后端

## 接口访问约定

前端数据统一通过同源 `/api` 请求后端接口，例如 `/api/tasks`。
前端不直接写死后端域名或端口，开发和生产环境由代理或网关转发到实际后端服务。

前端页面和交互见 [用户管理 - 前端.md](../frontend/用户管理%20-%20前端.md)。

## 认证边界

- Ory Kratos 负责注册、登录、密码和 session。
- ORF 后端提交账号密码到 Ory，并通过 Ory `/sessions/whoami` 校验登录态。
- Ory 和 ORF 都使用 PostgreSQL 数据库实现。
- ORF 数据库只保存业务用户、团队和成员角色。
- Ory 用户按 `traits.email` 映射到 ORF `users.email`。
- 未通过 Ory session，不能访问 ORF `/api` 业务接口。
- 数据库不可用时，Ory 登录成功也不能进入 ORF。
- 业务 API 在全局 `preHandler` 完成一次 session 校验，并在同一请求内复用已校验用户，避免路由处理阶段重复请求 Ory。
- Ory 或数据库不可用时返回 503，不把基础设施故障伪装成账号未授权。
- 开发环境的 Ory Kratos 必须使用有界 PostgreSQL 连接池。`npm run ory:dev` 会通过 `scripts/prepare-ory-env.ts` 在运行时 DSN 上写入 `max_conns`、`max_idle_conns`、`max_conn_idle_time` 和 `max_conn_lifetime`，默认值见 `.env.example`；不要让 Ory 长期保留几十个 idle 连接挤占 ORF API 和真实 E2E 测试。

## 业务规则

- 新 Ory identity 首次进入 ORF 时，按邮箱创建或更新 ORF 用户。
- 新用户默认加入第一个团队，角色为 `member`。
- Ory 已存在相同邮箱 identity 时，注册失败，前端显示 `邮箱已存在`。
- 管理员不能删除自己，也不能将自己的角色降级为成员。
- 同一团队内成员显示名大小写不敏感唯一；创建或编辑成员时不能制造重名，因为挑战者、征召、互评和积分流水都依赖团队内唯一成员名。
- 所有用户管理接口都需要管理员权限。

# 对象存储 - 后端

本文档记录 ORF 用户上传二进制文件的统一存储契约。当前使用方包括聊天附件、评论附件、用户头像和设置背景图；评论附件迁移步骤见 [评论图片附件迁移方案.md](../project/评论图片附件迁移方案.md)。

## 1. 原则

1. ORF 代码只依赖 S3-compatible 对象存储接口，不绑定 MinIO 专用 API。
2. 本地和本地服务器部署先使用 MinIO；以后可以替换为 AIStor、Garage、RustFS 或云厂商 S3 兼容服务。
3. bucket 必须保持私有。浏览器不直接访问对象存储，文件读取统一经过 ORF 后端权限校验。
4. PostgreSQL 保存业务元数据和权限关系；对象存储只保存文件内容。
5. 文件 URL、bucket endpoint 和 object key 不写入评论正文或用户读模型；业务 DTO 只暴露稳定 ID 或后端受控读取 URL。

## 2. 环境变量

| 变量 | 用途 |
| --- | --- |
| `OBJECT_STORAGE_DRIVER` | 当前固定为 `s3`。 |
| `OBJECT_STORAGE_ENDPOINT` | S3 API 地址；本地 MinIO 为 `http://127.0.0.1:9000`，共享环境为 `https://125.70.13.137:19443`。 |
| `OBJECT_STORAGE_REGION` | S3 region；MinIO 本地可用 `us-east-1`。 |
| `OBJECT_STORAGE_BUCKET` | ORF 上传文件 bucket，默认 `orf-comment-attachments`。 |
| `OBJECT_STORAGE_ACCESS_KEY` | ORF 后端访问对象存储的 access key。 |
| `OBJECT_STORAGE_SECRET_KEY` | ORF 后端访问对象存储的 secret key。 |
| `OBJECT_STORAGE_FORCE_PATH_STYLE` | MinIO 需要 `true`。 |
| `ORF_INFRA_UPLOAD_MAX_BYTES` | Web / MinIO public-gateway / 后端 multipart 的基础设施承载上限，默认 `10737418240`。它不定义具体业务能上传多大，只保证合法业务上传不会被承载层提前拦截。 |
| `OBJECT_STORAGE_UPLOAD_MAX_BYTES` | 通用对象存储小文件上传大小上限。评论附件、头像和背景仍是小文件链路，默认 `10485760`。 |

MinIO 本地服务使用：

| 变量 | 用途 |
| --- | --- |
| `MINIO_ROOT_USER` | MinIO root 用户名，仅用于本地初始化和管理。 |
| `MINIO_ROOT_PASSWORD` | MinIO root 密码；本地和服务器都必须改成强密码。 |
| `MINIO_IMAGE` | 可选，覆盖 compose 使用的 MinIO 镜像；服务器部署建议固定版本。 |
| `MINIO_MC_IMAGE` | 可选，覆盖 bucket 初始化使用的 MinIO Client 镜像；服务器部署建议固定版本。 |

## 3. 本地 MinIO

启动：

```bash
npm run storage:dev
```

访问：

```text
S3 API: http://127.0.0.1:9000
Console: http://127.0.0.1:9001
Bucket: orf-comment-attachments
```

停止：

```bash
npm run storage:down
```

`docker-compose.minio.yml` 会创建私有 bucket。不要把 bucket 设为 public。成员接入共享基础设施时，`OBJECT_STORAGE_ENDPOINT` 指向公共 `19443` 入口，不直接连本地 `9000`。

## 4. 适配层契约

后端实现时新增统一适配层，例如 `server/storage/objectStorage.ts`。聊天、评论、证据或报告附件不能直接 import MinIO SDK。

```ts
type StoredObject = {
  body: NodeJS.ReadableStream;
  contentLength?: number;
  contentType?: string;
};

interface ObjectStorage {
  putObject(input: { key: string; body: Buffer; contentLength: number; contentType: string }): Promise<void>;
  putObjectStream(input: { key: string; body: NodeJS.ReadableStream; contentType: string; maxBytes: number; peekBytes?: number }): Promise<{ contentLength: number; peeked: Buffer }>;
  getObject(key: string): Promise<StoredObject | null>;
  deleteObject(key: string): Promise<void>;
}
```

聊天附件是独立业务模块设置：`chat.attachmentMaxBytes` 默认 2GiB，由系统设置管理。聊天附件使用流式对象存储上传，不能复用评论附件、头像或背景图的 `Buffer` 小文件链路。

## 5. Object Key

评论附件 key：

```text
comments/{teamId}/{targetType}/{targetId}/{yyyy}/{mm}/{attachmentId}.{ext}
```

`teamId` 来自 ORF 当前存储作用域，`targetId` 需要做安全字符归一化。即使当前产品不暴露多团队，key 仍保留该层级，避免以后迁移时混淆。

用户头像 key：

```text
users/{userId}/avatar/{timestamp}.{ext}
```

`userId` 需要做安全字符归一化。头像对象 key 只保存在 `users.avatar_object_key`，接口通过 `/api/users/{userId}/avatar` 代理读取。

聊天附件 key：

```text
chat/{teamId}/{channelId}/{attachmentId}/{fileName}
```

`teamId`、`channelId` 和 `fileName` 都需要做安全字符归一化。聊天附件上传接口使用频道路径 `/api/chat/channels/{channelId}/attachments` 作为所属频道事实源，multipart 只承载文件本身；内容读取继续通过附件 ID 的后端受控 URL。

## 6. 迁移

从 WSL 迁到本地服务器时，需要迁移两类状态：

1. PostgreSQL：包含评论、附件元数据和权限关系。
2. MinIO bucket：包含附件文件内容。

应用迁移后只需要更新 `.env` 中的 `OBJECT_STORAGE_ENDPOINT`、账号和 bucket。历史评论正文仍引用附件 ID，不需要批量改 URL。成员接入共享对象存储时，优先使用共享接入包里的安装脚本，不要手工猜测 `OBJECT_STORAGE_SECRET_KEY`。

## 7. 风险

| 风险 | 约束 |
| --- | --- |
| 私有评论附件外泄 | 后端代理读取，不开放 public bucket。 |
| 文件伪装 | 图片、Markdown 和 PDF 的预览能力由后端根据 MIME 和安全文件头派生；其他文件按下载处理。 |
| 孤儿文件 | 未绑定评论的 pending 附件设置过期时间，定期清理。 |
| 对象存储替换 | 业务代码只依赖 `ObjectStorage` 适配层。 |

# 评论组件 - 后端

本文档只记录评论后端的必要约束，前端交互见 [评论组件 - 前端.md](../frontend/评论组件%20-%20前端.md)。评论附件的底层文件存储见 [对象存储 - 后端.md](./对象存储%20-%20后端.md)。

## 后端要求

1. 评论必须写入 ORF 当前 PostgreSQL 数据库，使用现有 `DATABASE_URL`、当前 schema 和 Drizzle migration，不单独建立评论数据库或评论服务。
2. 评论线程和消息继续绑定 `objective`、`result`、`task`、`subtask` 或 `feedback`；其中 `result` 在产品层展示为指标，`feedback` 在产品层展示为团队内部 issue。
3. 评论随 ORF 主数据返回；优先并入 `/api/tasks-page` 的返回集合，避免前端用 `localStorage` 保存评论。
4. 评论新增、编辑、删除和解决状态变更必须通过后端写入数据库，前端操作成功后刷新或合并评论数据。
5. 评论权限按对象边界处理：能看到对象即可看评论；发评论必须登录并满足评论写入规则；编辑和删除限作者本人或管理员。

## @ 提及方案

`@` 提及使用评论正文内的稳定 token，不新增评论提及表：

```text
@[显示名](orf-user:{userId})
```

后端职责：

1. 创建评论或回复成功写入后，解析正文里的 `orf-user:{userId}` token。
2. 只使用 `userId` 作为事实来源；`显示名` 只是当时插入时的可读文本，不能用于匹配用户。
3. token 解析使用共享 `src/features/rich-text/orfRichTextTokens.ts`，评论、反馈和 Chat 不各自复制 `orf-user` 正则。
4. 按评论目标解析出的 `team_id` 校验被提及用户必须在当前作用域内且 `status = active`。
5. 同一条评论里重复提及同一用户只保留一次；触发人自己不接收通知。
6. 普通 `@文本`、非法 token、跨 scope 用户、非 active 用户只作为普通正文保存，不产生通知。
7. 创建评论和回复都会触发 `comment.mention.created`；编辑历史评论第一版不补发新增提及通知。
8. 工作项评论通知 `targetHref` 指向 `/tasks?comment={commentMessageId}#{objective|bounty|action|subAction}:{targetId}`；反馈 issue 评论通知指向 `/feedback/:feedbackId?comment={commentMessageId}`。线程状态通知没有单条新消息时使用 `comment={commentThreadId}`。`metadata` 保存 `commentThreadId`、`commentMessageId`、`targetType`、`targetId`、`targetTitle`、`mentionedUserIds`。

## 评论系统通知

评论相关提醒统一创建系统通知事件，并投影到聊天里的 `我的系统通知`：

1. `comment.mention.created` 优先通知正文里被稳定 token 提及的 active 成员。
2. `comment.reply.created` 通知被回复评论的作者；触发人自己不接收，同一条评论里已经被 `@` 提及的人不重复接收。
3. `comment.thread.status.changed` 通知评论线程创建人；触发人自己不接收。
4. 这三类通知都带 `replyTargetType` / `replyTargetId`，用户可在聊天系统消息里直接回复，回复会写回原评论目标。
5. 通知事实只保存事件和收据；聊天投影状态写入 `notification_deliveries`，回复内容仍属于评论消息事实源。

## 反馈 issue 参与者通知

反馈 issue 的普通评论或回复除了 `@` 提及通知，还会派生 `feedback.commented`：

1. 收件人只来自当前反馈的相关人员：active 指挥官、反馈创建人、反馈处理人、已参与该反馈评论的人和显式关注该反馈的人。
2. 触发人不接收自通知。
3. 同一条评论里已经通过 `@` 收到 `comment.mention.created` 或通过直接回复收到 `comment.reply.created` 的成员，不再重复收到 `feedback.commented`。
4. 当前用户对该反馈设置 `muted` 时，不接收 `feedback.commented` 等普通反馈通知；`comment.mention.created`、`comment.reply.created` 和被设为反馈处理人的强通知不受静音抑制。
5. 通知 `targetType` 为 `feedback`，`targetId` 为反馈 ID，`targetHref` 指向 `/feedback/:feedbackId?comment={commentMessageId}`。

提及候选人通过评论目标边界查询：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/comments/mentionable-users?targetType=...&targetId=...` | 返回当前用户可在该评论目标内提及的 active 成员。 |

候选接口必须复用评论写入权限：没有权限在该对象发评论的人不能读取该对象的提及候选人。返回字段只包含 `id`、`name`、`email`、`role`、`status`、`avatarUrl`，不暴露认证系统内部身份或头像对象存储 key。

## 附件方案

评论附件采用 GitLab Markdown uploads 模式：

1. 前端粘贴、拖放或选择文件后先调用附件上传接口。
2. 后端校验目标对象和写入权限，限制大小，并按文件内容规范化 MIME 与预览能力。
3. 文件写入 S3-compatible 对象存储，当前部署使用 MinIO。
4. PostgreSQL 写入 `comment_attachments` 元数据。
5. 上传成功后返回 `![文件名](orf-attachment:{attachmentId})`，前端 Draft 记录附件引用，提交时再序列化进评论正文。
6. 创建或编辑评论时，后端通过共享 token 模型解析正文中的 `orf-attachment:{attachmentId}`，把 pending 附件绑定到消息。
7. 展示时后端随评论返回附件元数据和派生的预览能力；文件内容通过 ORF 后端受控接口读取。

评论正文仍是轻量文本，不存 base64、不存 MinIO URL、不存 public URL。

反馈 issue 创建页没有已存在的 `targetId`，因此不走普通 pending 附件上传接口。前端 Draft 在本地记录 `orf-pending-attachment:{clientId}` 引用和 object URL，提交时把序列化正文与附件文件随 `/api/feedback` 的 `multipart/form-data` 一起提交。后端创建反馈时同时创建该反馈的首条评论，把 pending token 替换成稳定的 `orf-attachment:{attachmentId}`，并在同一事务中绑定 `comment_attachments.message_id`。创建失败时，已经写入对象存储的文件必须被清理。

## 附件数据模型

新增 `comment_attachments`：

| 字段 | 说明 |
| --- | --- |
| `id` | 附件 ID，例如 `catt_...`。 |
| `team_id` | 当前 ORF 存储作用域。 |
| `target_type` | 评论绑定对象类型。 |
| `target_id` | 评论绑定对象 ID。 |
| `message_id` | 绑定后的评论消息；pending 附件为空。 |
| `object_key` | 对象存储 key。 |
| `file_name` | 原始文件名的安全版本。 |
| `mime_type` | 后端规范化后的 MIME。图片、PDF、Markdown 和安全文本会被标记为可预览类型；其他文件只允许下载。 |
| `file_size` | 字节数。 |
| `width` / `height` | 图片尺寸；非图片或无法读取时为空。 |
| `created_by` | 上传用户。 |
| `created_at` | 上传时间。 |
| `attached_at` | 绑定到评论消息的时间。 |
| `expires_at` | pending 附件过期时间。 |

`CommentMessage` 返回时增加：

```ts
attachments: CommentAttachment[]
authorUserId?: string | null
authorAvatarUrl?: string | null
```

`authorAvatarUrl` 是按 `authorUserId` 从用户头像事实源派生的展示字段。评论读模型必须自包含作者头像投影，不能要求普通成员额外读取管理员用户列表。`CommentAttachment` 只暴露 `id`、`fileName`、`mimeType`、`fileSize`、`width`、`height`、`previewKind`、`contentUrl`、`previewUrl` 和 `downloadUrl`，不暴露 `object_key`。

`previewKind` 是后端从附件 MIME 和安全文件头派生的展示能力：

| `previewKind` | 行为 |
| --- | --- |
| `image` | 内联图片预览。 |
| `markdown` | 允许打开预览，也允许下载。 |
| `pdf` | 允许打开预览，也允许下载。 |
| `text` | `.txt`、`.log`、`.csv`、`.json` 或可信 `text/plain` / `text/csv` / `application/json` 按纯文本打开预览，也允许下载。 |
| `download` | 不允许打开预览，只能下载。 |

## 接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/comments/attachments` | 上传 pending 评论附件。 |
| `GET` | `/api/comments/attachments/:attachmentId/content` | 读取附件内容。图片、Markdown、PDF 和安全文本默认 inline；其他文件默认 `attachment` 下载。 |

`POST /api/feedback` 作为反馈 issue 创建入口，接收 `multipart/form-data` 时支持：

| 字段 | 说明 |
| --- | --- |
| `phenomenon` | 反馈标题。 |
| `initialBody` | 反馈首条正文，允许包含由 Draft 序列化出的 `orf-pending-attachment:{clientId}` 附件占位 token。 |
| `causeCategories` | JSON 字符串数组，至少一个分类。 |
| `impact` | 影响级别，允许为空字符串。 |
| `ownerUserId` | 当前默认作用域内 active 成员的 `users.id`。 |
| `attachment:{clientId}` | 与正文占位 token 对应的附件文件。 |

上传接口使用 `multipart/form-data`：

| 字段 | 说明 |
| --- | --- |
| `targetType` | `objective`、`result`、`task`、`subtask`、`feedback`。 |
| `targetId` | 目标对象 ID。 |
| `file` | 附件文件。 |

创建和编辑评论继续使用现有评论接口。后端根据正文里的 `orf-attachment:{attachmentId}` 完成绑定和解绑。只有附件的评论正文仍然是非空文本，因为附件 token 本身就是序列化后的正文事实。

## 权限和生命周期

1. 上传附件使用与发评论相同的写入权限。
2. 读取附件使用评论读取权限；工作项目标参与者、管理员和 `comment.manage` 用户可读，反馈 issue 由同一团队作用域内 active 用户读取；目标结算或反馈关闭后仍可读取历史附件。
3. pending 附件只能由上传者继续引用；上传路径会顺带清理过期 pending 附件的 DB 元数据和对象存储文件。
4. 编辑评论移除附件 token 后，附件从消息解绑并删除对象。
5. 删除评论消息时，同步删除该消息下的附件元数据和对象。

## 验证

1. API 测试覆盖：无权限上传、超限文件、pending 绑定、评论 DTO 返回附件、授权读取附件内容、无权限读取失败、关闭目标后历史附件仍可读、删除评论后附件内容不可再读取；图片、Markdown、PDF、安全文本和 download-only 文件的 `Content-Disposition` 行为应分别覆盖。
2. 构建覆盖：`CommentMessage.attachments` DTO、前端渲染和上传入口必须通过 TypeScript 校验。
3. 浏览器截图验收覆盖：评论列表内图片缩略图可见，点击后打开大图预览；Markdown/PDF/文本附件显示预览和下载动作，其他文件只显示下载动作。
4. 提及测试覆盖：候选接口按目标权限收敛；创建评论后只通知 active、同 scope、非本人、去重后的被提及用户；普通 `@文本` 不产生通知。

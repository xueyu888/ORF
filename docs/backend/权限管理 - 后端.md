# 权限管理 - 后端

## 接口访问约定

前端数据统一通过同源 `/api` 请求后端接口，例如 `/api/tasks`。
前端不直接写死后端域名或端口，开发和生产环境由代理或网关转发到实际后端服务。

本文档只记录权限管理的 RBAC 模型、校验规则和接口口径。

前端页面和草稿交互见 [权限管理 - 前端.md](../frontend/权限管理%20-%20前端.md)。

## 技术选型
1. 使用postgresql数据库来实现权限表的持久化
2. 不需要缓存

## 模型

权限采用 Stage-aware RBAC：

```text
User -> TeamMember.role -> PermissionRule[]
can(user, stage, action, resource)
```

| 字段 | 值 |
| --- | --- |
| `role` | `admin`、`member` |
| `stage` | `goalSetting`、`resultClaiming`、`orfReestimate`、`goalFrozen` |
| `resource` | `objective`、`result`、`task`、`subtask` |
| `action` | `view`、`create`、`edit`、`delete` |

`result` 在产品层展示为悬赏指标；权限枚举保持后端资源名不变。

## 规则

- 用户不直接拥有权限，只通过团队角色获得权限。
- 管理员默认拥有全部权限，不需要保存单独规则。
- 成员权限由 `PermissionRule` 决定。
- 拖拽移动、调整排序、修改父对象时，校验的资源对象是被操作对象本身，按 `can(user, stage, "edit", resource)` 校验。
- 例如移动任务到另一个悬赏指标，校验 `task.edit`；移动子任务到另一个任务，校验 `subtask.edit`；调整悬赏指标顺序，校验 `result.edit`。

## 默认成员权限

| 阶段 | 权限 |
| --- | --- |
| `goalSetting` | `objective.view`、`result.view` |
| `resultClaiming` | `objective.view`、`result.view` |
| `orfReestimate` | `objective.view/edit`、`result.view/edit`、`task.view/create/edit`、`subtask.view/create/edit` |
| `goalFrozen` | `objective.view`、`result.view`、`task.view/create/edit`、`subtask.view/create/edit` |

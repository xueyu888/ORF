# 权限管理 - 后端

## 接口访问约定

前端数据统一通过同源 `/api` 请求后端接口，例如 `/api/permissions`。

## 文档定位

本文档只记录权限管理的后端模型、校验规则和接口口径。

权限 key 唯一配置来源是 `src/config/permissions.ts`。

## 权限设计原则

权限只描述全局业务动作，不描述前端显隐。

权限只配置管理员和成员存在差异的动作。管理员默认拥有全部权限；成员默认权限显式配置。

前端显隐由 [前端显隐配置.md](../frontend/前端显隐配置.md) 管理，不进入权限表。

权限不表达对象状态判断。是否为提出人、是否在优先期、悬赏目标是否可申请等对象状态，由业务守卫处理。

权限 key 使用扁平结构，例如 `result.create`、`challenge.assign`、`comment.manage`。

前端可以基于权限控制按钮可见性、可用性和只读态；后端接口必须重新校验权限。

## 技术选型

1. 使用 PostgreSQL 持久化权限配置。
2. 不需要缓存。

## 模型

权限采用角色权限 key 列表：

```text
User -> default-scope membership.role -> PermissionRule
can(user, permissionKey)
```

| 字段 | 说明 |
| --- | --- |
| `role` | `admin`、`member` |
| `permissions` | 当前角色开启的权限 key 数组 |

管理员默认拥有全部权限，不需要保存单独规则。

成员权限由 `PermissionRule.permissions` 决定。

## 持久化

当前继续使用 `role_permissions` 表保存角色权限。

权限读取是纯查询：`GET /api/me/access`、`GET /api/permissions` 和所有业务鉴权都只能读取现有权限行，不能在查询过程中插入默认数据。每个团队在创建时由数据库触发器同步建立一条成员权限记录；迁移 `0079_explicit_team_permission_initialization` 会为既有缺失团队补齐空权限行，但不覆盖任何已有权限配置。读取时如果记录仍缺失，按配置损坏返回 `503`，不能回退到演示数据或临时默认值。

成员权限保存为一条角色记录：

| 字段 | 值 |
| --- | --- |
| `role` | `member` |
| `stage` | `global` |
| `resource` | `permissionKeys` |
| `actions` | 权限 key 数组 |

`stage`、`resource`、`actions` 是历史字段名，业务含义以 `actions` 中的权限 key 为准。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/me/access` | 返回当前用户、当前作用域权限规则和当前用户可执行权限；普通成员和管理员都可读取 |
| `GET` | `/api/permissions` | 管理员读取当前默认作用域权限配置 |
| `PUT` | `/api/permissions/:role` | 保存指定角色权限配置 |

`/api/permissions` 是权限配置管理接口，不作为普通成员的全局权限读取入口。Provider 启动和权限失效刷新使用 `/api/me/access`。

`PUT /api/permissions/admin` 不允许修改。

## 默认成员权限

成员默认不开启权限清单中的任何权限。

# ORF 反馈收件箱 - 前端

`/feedback` 展示当前团队作用域内的内部反馈列表，采用 GitHub Issues 风格的搜索、状态切换、元数据筛选、单列表结构和详情时间线，并复用悬赏大厅同色系浅色工作台皮肤。

## 入口显隐

- `新建反馈` 在当前用户为 active 成员时展示。
- 反馈是团队级内部 issue，不要求也不展示关联指标。
- 反馈可以选择归属一个项目，也可以保持未归属；项目只作为反馈元数据和筛选上下文，不改变权限、处理人或通知收件人边界。
- 反馈创建的最终权限仍以后端 `/api/feedback` 校验为准，前端只负责避免向非 active 用户展示不可完成入口。

## 新建反馈

- 反馈收件箱只处理内部反馈；新建反馈进入 `/feedback/new`，不再由全局弹窗承载正文编辑。
- 前端创建反馈时不提交来源字段；团队内部属性由反馈模型和路由边界表达。
- 新建页提交标题、首条正文、分类、影响、处理人和可空项目；目标或指标不参与必填校验。
- 新建页分类只提供压缩后的固定五类：技术问题、管理问题、流程问题、权限问题、体验问题。历史反馈里的细分原因只作为旧反馈原始标签展示，不继续扩展新建页下拉选项。
- 处理人来自当前活跃成员列表，避免把不可处理的文本处理人提交给后端。
- 新建页正文复用评论输入字段的图片粘贴和图片选择入口。创建前图片只作为本地 pending 附件，提交时随 `/api/feedback` multipart 请求一起绑定为反馈首条评论附件。

## 列表页

- 顶部展示当前 Open/Closed 数量、标签数量和里程碑数量；里程碑当前没有 ORF 事实源，因此计数固定为 0。
- 顶部标签数量进入 `/feedback/labels`，里程碑数量进入 `/feedback/milestones`；二者是 issue 索引入口，不承载反馈详情动作。
- 搜索输入支持 GitHub-like qualifier：`is:` / `status:`、`assignee:` / `owner:`、`author:`、`label:`、`impact:`、`project:`、`sort:`，未带 qualifier 的文本只作为展示查询。
- 筛选行提供处理人、作者、项目、标签、影响和排序；这些筛选只维护 URL 查询展示状态，不回写反馈事实源。
- 标签由反馈原因分类和影响等级统一派生；同一套派生规则同时用于列表行、标签筛选和详情侧栏。
- 从标签页点击标签会回到 `/feedback?label=...`，列表页只把该参数当作展示筛选。列表页还支持 `q`、`state`、`assignee`、`author`、`project`、`impact`、`sort` 查询参数，用于分享和恢复当前视图。
- 列表头展示 `Open`、`Closed`、`All` 三个列表状态及匹配数量。
- 每条反馈以 issue 行展示：状态图标、标题、标签、反馈 ID、作者、项目、创建时间、最近活动时间、Open/Closed 状态、处理人和评论数量。
- 默认按最近活动时间倒序展示；最近活动时间取反馈 `updatedAt` 和该反馈评论线程 `updatedAt` 的较大值。排序还支持最近创建、评论最多和最早更新。
- 点击任意反馈行进入 `/feedback/:feedbackId` 详情页；列表页不承载回复、关闭或重新打开动作。
- 反馈详情说明文本中的 `/path` 内部链接用前端路由跳转，`http://` / `https://` 外部链接在新窗口打开。

## 标签和里程碑索引

- `/feedback/labels` 是只读标签索引页，标签集合、颜色、Open/Closed 计数和反馈总数都由当前可见反馈通过 `feedbackIssueLabels` 派生。
- 标签页支持搜索和排序；搜索只匹配标签名和派生说明，排序只影响展示顺序。
- 标签页不创建、编辑、删除标签，也不维护独立标签表，避免和反馈原因分类、影响等级形成多事实源。
- `/feedback/milestones` 是只读里程碑索引页；当前 ORF 反馈模型没有里程碑字段或里程碑集合，所以展示 Open 0 / Closed 0 的空状态。
- 里程碑创建、分配、权限、旧反馈迁移和关闭规则需要先有明确业务模型后再接入；前端不会先制造可写入口。

## 详情页

- 详情页采用 issue 结构：顶部展示标题、Open/Closed、短 ID、处理人、更新时间和评论数。
- 主体左侧展示原始 issue 正文、反馈活动和评论时间线，右侧展示 GitHub-like 元数据：State、Title、Assignees、Labels、Impact、Projects、Notifications、Milestone、Relationships、Participants 和 Timeline。
- Assignees 来自反馈 `ownerUserId` / `owner`；Labels 来自反馈原因分类和影响等级；Projects 来自 `Feedback.projectId` 关联的 `Project.name`；Participants 来自创建人、处理人和评论线程作者。
- Relationships 从标题、说明和评论正文中的 `/feedback/:feedbackId` 链接派生；只链接当前前端已加载的反馈，不新增关系表。
- Projects 已有可空反馈项目事实源，允许在详情侧栏编辑；Milestone 当前没有 ORF 事实源，只展示空状态，不在前端制造业务事实。
- 元数据编辑通过详情侧栏统一保存标题、处理人、标签、影响和项目。Open 反馈允许管理员、创建人、处理人编辑；Closed 反馈只有管理员可直接编辑，创建人和处理人需要先重新打开。
- 原始 issue 正文是反馈创建时生成的首条评论，正文和附件以评论系统为唯一事实源；旧数据没有首条评论时才回退展示旧说明字段。
- 反馈活动来自 `feedback.activity`，只作为详情时间线事件展示，不替代评论正文或反馈状态事实。
- 评论数只统计原始 issue 正文之后的讨论消息。
- 评论时间线复用共享评论输入器，支持发送评论、回复、原评论行内编辑、`@` 成员、粘贴、拖放或选择附件。
- `@` 候选人来自当前反馈目标的 `/api/comments/mentionable-users?targetType=feedback&targetId=...`。
- 关闭和重新打开只在当前用户有反馈状态管理权限时展示；打开态关闭后写入 `Closed`，关闭态重新打开后写回 `Open`。
- 详情页不展示、编辑或要求关联指标；不接入 GitHub repository、commit、PR development 链路。

## 消息通知

- 反馈创建、反馈评论、反馈状态变化和反馈处理人变化由后端写入路径派生通知，前端不在页面层自行判断收件人。
- 反馈普通通知只通知相关人员：active 指挥官、反馈处理人、反馈创建人、已参与该反馈评论的人和显式关注该反馈的人；触发人不接收自通知。
- 详情页 Notifications 控件只写入当前用户对该反馈的显式关注或静音偏好。静音会抑制普通反馈通知，但不会抑制评论 `@` 提及、直接回复或被设为处理人的强通知。
- 评论正文中的 `@` 成员继续使用评论提及通知；已被 `@` 提及的人不再重复接收同一条评论的反馈参与者通知。
- 项目变化只记录反馈活动，不因为项目成员或项目上下文扩大通知范围。
- 通知点击后进入 `/feedback/:feedbackId` 详情页。

# 状态探索与可重复组件

当前随机测试分成两类。

## 第一类：状态探索测试

目标：

```text
尽量完整地探索页面状态和路径入口
避免被可无限增长的列表拖入状态爆炸
记录哪些区域需要后续局部专项测试
```

默认配置：

```text
UI_EXPLORER_TEST_KIND=stateExploration
UI_EXPLORER_STATE_ABSTRACTOR=stateExploration
UI_EXPLORER_STEPS=1000
UI_EXPLORER_MAX_DURATION_MS=0
```

状态探索主流程有两个结束预算：

```text
最大步数
最大运行时长
```

任一预算先到，主流程就结束。`UI_EXPLORER_MAX_DURATION_MS=0` 表示不按时间结束。

状态探索测试不追求“每一条数据数量都不同”。它关心页面是否进入了一个新的可操作形态。

评论示例：

```text
没有评论
有评论
```

这两个是不同状态。

下面这些不是状态探索阶段要拆开的状态：

```text
1 条评论
2 条评论
3 条评论
```

它们属于同一个“有评论”状态。具体评论数量增长会被记录为可重复增长区域，交给第二类测试。

## 状态合并原则

状态探索抽象遵循三条规则。

### 数量增长可以合并

如果两个 DOM 的差异只来自某个区域下重复子项数量变化，状态探索阶段把它们合并。

示例：

```text
评论列表多了一条评论
任务列表多了一条结构相同的任务卡片
表格多了一行同结构数据
```

这类变化不直接制造新状态。

### 业务标签变化不能合并

如果重复区域里出现不同业务标签，必须区分状态。

示例：

```text
待征召
挑战中
已完成
已关闭
评审中
已解决
```

这些标签说明业务状态不同，即使 DOM 结构相似，也不能合并。

### 层级存在性不能合并

ORF 里存在：

```text
目标
指标 / 结果
任务
子任务
```

状态探索阶段关心每一层的子层级是否存在。

示例：

```text
目标下没有指标
目标下有指标
指标下没有任务
指标下有任务
任务下没有子任务
任务下有子任务
```

这些属于不同状态。

但同一层里具体有几个相同结构的子项，不应该无限拆分状态。

## 代码实现

状态探索使用这条链路：

```text
stateNormalizer.ts
  -> 采集 StateDomSnapshot
  -> 采集 DOM tree

repeatableRegionDetector.ts
  -> 识别可重复增长区域
  -> 折叠重复子项文本
  -> 输出 RepeatableRegionRecord

stateAbstractorRegistry.ts
  -> stateExploration 抽象器
  -> 生成 StateAbstraction
  -> 生成状态 ID
```

`RepeatableRegionRecord` 记录：

```text
所在 routePattern
区域类型
区域标签
组件名
父组件名
无 / 有
业务标签集合
层级存在性集合
重复子项结构
```

它不记录精确条目数量作为状态 ID 的依据。

状态探索的状态 ID 不直接使用每一条 `RepeatableRegionRecord`。第一类测试会把这些区域先汇总成更粗的状态语义：

```text
评论是否存在
业务标签集合
目标 / 指标 / 任务 / 子任务层级集合
```

普通列表、布局容器、没有业务标签也没有层级含义的重复区域，不参与全局状态 ID。它们仍然保留在 `repeatableRegions` 中，供第二类局部组件测试使用。

## 第二类：可重复组件局部测试

目标：

```text
只测试第一类测试中发现的可重复增长组件
只在组件内部探索
避免重新探索整站路径
```

评论示例：

```text
只进入评论面板内部
测试新增
测试回复
测试编辑
测试删除
测试展开回复
测试关闭边界
测试空输入和错误提示
```

第二类测试需要使用第一类测试的输出：

```text
repeatableRegions
routePattern
代表状态 ID
组件 DOM selector
当前组件内部候选事件
```

当前代码已经实现第二类测试的自动派生阶段：

```text
repeatableRegionRunner.ts
  -> 从第一类结果里收集 RepeatableRegionRecord
  -> 按组件作用域、存在性、业务标签、层级标签去重
  -> 从 eventSequence / transitionTable / candidates 中恢复代表状态路径
  -> 只采集组件 selector 内部的 UiTarget
  -> 只执行 target 绑定事件
  -> 事件导致路径逃逸或组件不可见时恢复代表状态
```

第二类测试默认随第一类测试自动执行。可通过下面配置控制预算：

```text
UI_EXPLORER_REPEATABLE_REGION_TESTS=1
UI_EXPLORER_REPEATABLE_REGION_MAX_OBJECTS=12
UI_EXPLORER_REPEATABLE_REGION_STEPS=8
```

设置 `UI_EXPLORER_REPEATABLE_REGION_TESTS=0` 可以关闭第二类测试。

## 可重复组件测试对象去重

测试对象不是“每一条数据”，而是“一个可重复区域在一个业务上下文中的测试作用域”。

对象 key 由下面字段组成：

```text
routePattern
repeatable region signature
区域类型
无 / 有
业务标签集合
层级集合
```

这带来三个效果：

```text
同一个评论面板里 1 条评论和 2 条评论不会变成两个测试对象
同一个评论面板在“待征召”和“挑战中”下会变成两个测试对象
DOM 中真正形成不同重复区域的目标、指标、任务、子任务会分别成为测试对象
```

目标-指标-任务-子任务的处理原则是：

```text
如果每个层级在 DOM 中有独立的可重复容器，就分开测
如果多个层级只是同一个容器里的嵌套内容，就只测这个容器一次，并保留层级标签
```

这样可以避免“每个目标下的每个任务都单独跑一遍”的重复测试，同时保留层级结构本身带来的差异。

## 报告含义

`report.html` 的首页先展示结果判断需要的信息：

```text
状态图
执行事件数
成功事件数
异常事件数
严重失败数
探索分数
覆盖率
异常情况
```

报告顶部还有一条轻量的被测对象信息，展示被测工程、被测应用、入口 URL、测试类型和 SEED。安全边界、状态抽象、允许路径、Node.js、浏览器等是测试环境，不参与结果判断，放在报告后部。

状态图带有探索路径回放。回放数据来自同一份 `eventSequence`，按实际执行步骤依次高亮状态和状态转移，不额外制造另一套路径模型。回放可以退出，退出后状态图回到普通浏览状态。

异常情况复用状态图。每个异常按“步骤、操作、所在状态、结果”展示，按钮会把状态图定位到对应步骤；报告不直接展示 Playwright 原始长错误文本。

`report.html` 还展示：

```text
可重复区域
可重复组件局部测试
```

这个指标表示状态探索中发现了多少个可重复增长组件。

可重复区域只记录业务上可能无限增长的区域，例如评论、目标/指标/任务/子任务列表。topbar、sidebar、surface、space-y、通用 card/container 等布局容器不作为可重复区域展示，也不进入第二阶段局部测试对象。

报告中的可重复区域表格展示：

```text
类型
路径
组件名
父组件名
标签
存在性
业务标签
层级
```

它的作用不是证明组件内部已经测全，而是告诉下一轮局部测试应该测哪里。

第二类测试会额外输出：

```text
repeatable-regions.json
repeatable-regions.html
```

`repeatable-regions.html` 不展示状态图。它展示：

```text
测试对象
已测对象
组件名
父组件名
组件内执行事件数
候选覆盖
离开组件次数
运行异常
严重失败
事件样本
```

第二类测试关心组件局部稳定性和边界逃逸，不负责证明全局状态空间覆盖。

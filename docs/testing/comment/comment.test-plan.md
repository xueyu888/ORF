# 评论功能黑盒测试计划

## 1. 测试目标

根据评论功能黑盒规格，验证当前实现是否满足用户可观察的评论能力。

本轮只生成测试设计，不生成测试代码，不引入随机测试。

## 2. 测试依据

测试依据按优先级排序：

1. 评论功能目标。
2. 使用对象和权限预期。
3. 输入条件和外部条件。
4. 成功行为、失败行为、安全约束。
5. 黑盒不确定性地图。

当前源码、内部函数名、内部接口形态、内部存储方式不作为黑盒预期来源。

## 3. 当前文档结构

| 文件 | 黑盒职责 |
|---|---|
| `comment.module-profile.md` | 评论功能黑盒规格 |
| `comment.uncertainty-map.md` | 评论功能黑盒不确定性地图 |
| `comment.test-plan.md` | 评论功能黑盒测试计划 |
| `comment.test-cases.md` | Given / When / Then 黑盒用例 |
| `comment.dev-gate.md` | 开发门禁 |

## 4. 测试层级

| 层级 | 是否使用 | 黑盒目标 |
|---|---|---|
| 功能冒烟 | 是 | 评论区能打开、关闭、展示空状态 |
| 交互测试 | 是 | 新增、回复、编辑、删除路径成立 |
| 输入校验测试 | 是 | 空、空白、危险内容、长文本按规格处理 |
| 权限测试 | 是 | 登录、未登录、无权限场景按规格处理 |
| 恢复测试 | 是 | 保存失败、删除失败、刷新后继续可用 |
| 布局测试 | 轻量 | 小屏幕、长标题、长正文不破坏核心操作 |
| 随机测试 | 否 | 本轮不做 |
| 源码映射测试 | 后续 | 规格确认后再读代码生成自动化实现 |

## 5. 自动化实现阶段边界

后续生成测试代码时才允许读取源码，用于确定：

- 从哪里打开评论功能。
- 如何准备用户、对象和已有评论数据。
- 如何模拟外部成功、失败、超时。
- 如何观察评论是否出现、消失或保持。
- 如何判断当前实现缺口。

自动化阶段不得做：

- 根据源码删减黑盒预期。
- 因为当前没有某个接口就取消功能验收。
- 把内部函数调用当成主要断言。

如果当前实现没有后端评论接口、没有跨设备持久化或没有权限拦截，应记录为实现缺口或待确认规格，而不是把黑盒规则改成“不需要”。

## 6. 测试数据规划

| 数据 | 目的 |
|---|---|
| 无评论对象 | 验证空状态和首条评论 |
| 有多条评论对象 | 验证列表展示和数量 |
| 有回复的评论 | 验证回复入口和回复列表 |
| 两个相似对象 | 验证评论隔离 |
| 普通登录用户 | 验证核心操作 |
| 未登录用户 | 验证限制或只读规则 |
| 无权限用户 | 验证权限限制 |
| 管理员用户 | 验证管理权限，待确认 |
| 空输入 | 验证输入校验 |
| 纯空白输入 | 验证输入校验 |
| 多行和 emoji 输入 | 验证文本处理 |
| script / HTML 输入 | 验证安全处理 |
| 超长输入 | 验证边界和布局 |
| 外部保存失败 | 验证失败提示和恢复 |

## 7. 测试代码位置

未来测试代码统一放到：

```text
tests/testing/comment/
```

不使用：

```text
tests/comment/
```

该路径应保持不被 Git 跟踪。

## 8. 报告位置

测试报告放到：

```text
reports/testing/comment.test-report.md
```

报告需要区分：

- 通过。
- 失败。
- 跳过。
- 规格待确认。
- 实现缺口。
- 测试代码问题。
- 环境问题。

## 9. 执行流程

第一轮：

```text
1. 人确认黑盒规格
2. 人确认 P0 / P1 用例
3. 根据已确认规格读取源码
4. 生成自动化实现计划
5. 生成测试代码
6. 执行测试
7. 输出门禁结论
```

第二轮：

```text
1. 对失败用例分类
2. 实现缺口进入修复
3. 规格不清进入待确认
4. 修复后新增回归用例
```

## 10. 本轮明确不做

- 不写测试代码。
- 不引入随机测试。
- 不根据源码重写规格。
- 不把当前实现当成目标功能。

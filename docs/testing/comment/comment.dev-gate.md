# 评论功能开发门禁

## 1. 门禁目标

判断当前评论功能是否达到单模块开发阶段的最低可推进标准。

门禁依据是黑盒规格和 Given / When / Then 用例，不依据当前内部实现。

## 2. 必须通过项

| 门禁项 | 状态 | 说明 |
|---|---|---|
| 核心打开路径通过 | 待执行 | 用户能打开评论区并看到正确上下文 |
| 空状态展示通过 | 待执行 | 无评论时不是空白或误导状态 |
| 已有评论展示通过 | 待执行 | 作者、正文、时间、操作可见 |
| 对象隔离通过 | 待执行 | 不同对象评论不串数据 |
| 合法评论提交通过 | 待执行 | 提交后评论可见 |
| 输入校验通过 | 待执行 | 空、空白、空编辑不能成功保存 |
| 回复路径通过 | 待执行 | 回复出现在正确评论关系下 |
| 编辑路径通过 | 待执行 | 编辑只影响目标评论 |
| 删除确认通过 | 待执行 | 删除前确认，取消不删除 |
| 删除路径通过 | 待执行 | 确认后评论按规格删除 |
| 持久化可观察结果通过 | 待执行 | 刷新或重新打开后已保存评论仍可见 |
| 跨用户 / 跨设备可见通过 | 待执行 | 已保存评论对有权限用户和同一用户其他设备可见 |
| 登录 / 权限场景通过 | 待执行 | 未授权操作不能成功 |
| 重复操作防护通过 | 待执行 | 重复提交不产生重复评论 |
| 基础安全场景通过 | 待执行 | script / HTML 不执行 |
| 失败恢复场景通过 | 待执行 | 保存或删除失败后有反馈且可恢复 |
| P0 用例全部通过 | 待执行 | CMT-BB-001 到 CMT-BB-020 |
| P1 用例通过或风险已记录 | 待执行 | CMT-BB-021 到 CMT-BB-036 |

## 3. 不允许推送的情况

出现以下任一情况，不允许推送：

- 评论区无法打开。
- 无评论对象没有可理解空状态。
- 已有评论无法展示。
- 评论串到错误对象。
- 合法评论无法提交。
- 空评论或纯空白评论可以提交。
- 回复关联错误。
- 编辑评论影响错误对象或错误评论。
- 删除没有确认。
- 取消删除仍然删除评论。
- 刷新或重新打开后已保存评论丢失。
- 有权限用户或同一用户其他设备无法看到已保存评论。
- 未登录或无权限用户可以成功执行受限操作。
- 未登录用户可以进入评论页面。
- 重复提交产生重复评论。
- script 或危险 HTML 被执行。
- 超过 500 字符的评论可以成功提交。
- 保存失败时没有失败反馈或重试入口。
- 保存或删除失败导致功能卡死、输入丢失且无反馈。
- P0 用例失败。
- 测试无法运行且原因未确认。

## 4. 已确认规格项

以下规则已经在黑盒规格中确认，门禁执行时按明确规则判定，不再作为待确认项跳过：

- 未登录用户无法进入评论页面。
- 管理员允许编辑和删除他人评论。
- 评论权限跟随目标对象权限。
- 评论最大长度为 500 字符。
- 只包含 emoji 的评论允许提交。
- URL 不需要自动链接。
- 编辑历史不可见。
- 删除外层评论时，它下面的回复一起删除。
- 保存失败时需要重试入口。
- 评论需要跨浏览器、跨设备、多人共享。

如果自动化阶段发现当前实现不满足上述规则，应记录为实现缺口，而不是降级黑盒预期。

## 5. 仍需澄清的规格项

如果后续发现黑盒规格没有覆盖的新问题，并且影响 P0/P1 判定，门禁结论应为：

```text
需要澄清规格
```

## 6. 门禁结论

执行后只能给出以下结论之一：

```text
允许推送
不允许推送
需要补充测试
需要澄清规格
```

## 7. 实现缺口记录规则

自动化阶段如果发现当前实现没有满足黑盒规格，应记录为：

```text
实现缺口
```

不应把黑盒预期改成当前实现。

示例：

- 如果当前实现没有后端评论接口，但规格要求多人共享评论，应记录为“多人共享评论实现缺口”。
- 如果当前实现只在本地保存，但规格要求跨设备保留，应记录为“跨设备持久化实现缺口”。
- 如果当前实现没有权限拦截，但规格要求未授权不能评论，应记录为“评论权限实现缺口”。


测试过程文档模板参考：
~/prj/test/test_framework/module-test-framework
~/prj/test/test_framework/random-test-framework

你可以把整个工作理解成一句话：

> **先把模块测试空间定义清楚，再生成确定性测试；再补充随机测试；最后用门禁判断能否推送、合并或发布。**

不要一开始就让 AI 直接写测试代码。正确顺序应该是：

```text
模块画像 → 不确定性地图 → 测试计划 → 确定性用例 → 随机测试设计 → 测试代码 → 运行门禁 → 报告与回流
```

---

# 1. 第一步：选定测试目标

先明确你现在测的是哪个模块，以及测到什么程度。

例如：

```text
模块：评论组件
目标：开发门禁
结论：判断当前版本是否可以推送
```

或者：

```text
模块：评论服务
目标：合并门禁
结论：判断是否可以合并到主分支
```

不同目标对应不同测试强度。

| 目标     | 适合阶段          | 测试强度        |
| ------ | ------------- | ----------- |
| 开发门禁   | 本地开发 / push 前 | 轻量，覆盖 P0/P1 |
| 合并门禁   | PR / MR 前     | 中等，覆盖主要风险   |
| 发布门禁   | 发布前           | 较重，覆盖系统风险   |
| 夜间随机测试 | 定时任务          | 大样本探索       |

你现在如果要起步，建议先做：

> **单模块开发门禁。**

---

# 2. 第二步：建立模块测试画像

这是最重要的入口文件。

建议每个模块都有一个文件：

```text
docs/testing/{module-name}/{module-name}.module-profile.md
```

例如：

```text
docs/testing/comment/comment.module-profile.md
```

里面要回答：

```text
1. 这个模块是什么？
2. 它负责什么？
3. 它不负责什么？
4. 它接收什么输入？
5. 它有哪些状态？
6. 它依赖什么？
7. 它产生什么可观察结果？
8. 它有哪些高风险点？
```

如果是前端模块，重点写：

```text
渲染
槽位
布局
交互
状态流转
接口结果
错误提示
可访问性
```

如果是后端模块，重点写：

```text
响应
数据处理
业务规则
状态变更
持久化
事务
幂等
依赖失败
```

这一步的产物是：

```text
模块测试画像
```

它决定后面所有测试怎么生成。

---

# 3. 第三步：生成不确定性地图

基于模块画像，让 AI 生成：

```text
docs/testing/{module-name}/{module-name}.uncertainty-map.md
```

它要列出这个模块有哪些不确定性。

例如前端评论组件：

```text
渲染不确定性：默认状态、空状态、错误状态是否正确显示
输入不确定性：空评论、超长评论、特殊字符是否正确处理
状态不确定性：idle、loading、success、error 是否正确流转
依赖不确定性：接口成功、失败、超时、401 时是否正确处理
交互不确定性：输入、提交、重复点击、失败后重试是否正确
安全不确定性：XSS 内容是否会执行
布局不确定性：长文本、移动端、slot 内容是否导致错位
```

后端评论服务则可能是：

```text
参数不确定性：content、targetId、parentId 是否正确校验
业务规则不确定性：未登录、无权限、目标不存在时是否拒绝
数据处理不确定性：评论内容是否正确清洗、保存、返回
状态变更不确定性：是否正确创建评论记录
依赖不确定性：数据库失败、缓存失败时是否正确处理
幂等不确定性：重复请求是否导致重复评论
安全不确定性：是否允许伪造 userId
```

这一步的目标是：

> **把“我要测什么”系统性列出来。**

---

# 4. 第四步：生成确定性测试用例

接下来生成：

```text
docs/testing/{module-name}/{module-name}.test-cases.md
```

这里先不要搞随机测试，先做确定性用例。

确定性用例要覆盖：

```text
核心正常路径
明确异常路径
输入边界
状态流转
依赖成功 / 失败
权限 / 安全
回归风险
```

例如评论组件的 P0/P1 用例：

```text
1. 登录用户可以成功提交评论
2. 空评论不能提交
3. 纯空格评论不能提交
4. 超长评论不能提交
5. 未登录用户不能提交
6. 接口失败时显示错误并保留输入
7. 接口超时时 loading 能恢复
8. 重复点击不会重复创建评论
9. script 内容不得执行
10. 成功后评论列表刷新
```

这些是模块测试的主干。

随机测试不能替代这些用例。

---

# 5. 第五步：定义开发门禁

然后生成：

```text
docs/testing/{module-name}/{module-name}.dev-gate.md
```

开发门禁要回答：

> 哪些测试通过后，当前模块可以推送？

例如：

```text
评论模块开发门禁：

必须通过：
1. 模块可正常加载 / 渲染 / 初始化
2. 核心正常路径通过
3. P0 用例全部通过
4. P1 用例全部通过，或风险已记录
5. 接口成功 / 失败基础场景通过
6. 重复提交防护通过
7. 基础安全用例通过
8. 测试可以稳定运行

不允许推送：
1. 模块无法运行
2. 核心路径失败
3. 非法输入导致崩溃
4. 接口失败导致页面卡死
5. P0 用例失败
6. XSS 内容可执行
```

这一步非常关键。

测试不是为了“跑一下”，而是为了得到一个工程结论：

```text
允许推送 / 不允许推送 / 需要补充测试
```

---

# 6. 第六步：设计随机测试增强层

确定性测试用例清楚之后，再补随机测试。

生成：

```text
docs/testing/{module-name}/{module-name}.random-test-plan.md
```

随机测试不要一上来就大样本。

先定义：

```text
随机什么？
检查什么不变量？
跑多少样本？
失败如何复现？
失败如何回流？
```

例如评论组件可以随机：

```text
评论内容
用户状态
接口结果
点击序列
viewport
初始评论列表
slot / children
```

对应不变量：

```text
组件不得崩溃
空评论不得提交
超长评论不得提交
接口失败后输入应保留
接口失败后 loading 必须结束
提交中不得重复创建评论
script 内容不得执行
错误状态必须有提示
```

门禁配置可以是：

```text
开发门禁：随机 30 组
合并门禁：随机 300 组
夜间任务：随机 10000 组
```

---

# 7. 第七步：生成测试数据与 Mock

生成：

```text
docs/testing/{module-name}/{module-name}.test-data.md
tests/{module-name}/{module-name}.fixtures.*
tests/{module-name}/{module-name}.mocks.*
```

测试数据要覆盖：

```text
正常数据
边界数据
非法数据
安全数据
依赖成功响应
依赖失败响应
字段缺失响应
超时响应
```

例如评论模块：

```text
normalComment
emptyComment
spacesOnlyComment
maxLengthComment
overMaxLengthComment
scriptInjection
htmlInjection
apiSuccessResponse
api500Response
api401Response
apiTimeout
missingFieldResponse
```

Mock 的原则是：

> **Mock 外部依赖，不要 Mock 被测模块自己的核心逻辑。**

---

# 8. 第八步：生成自动化测试代码

这时候才让 AI / Codex 写测试代码。

前端模块通常生成：

```text
tests/comment/comment.component.test.*
tests/comment/comment.random.test.*
tests/comment/comment.fixtures.*
tests/comment/comment.mocks.*
```

后端模块通常生成：

```text
tests/comment/comment.service.test.*
tests/comment/comment.controller.test.*
tests/comment/comment.property.test.*
tests/comment/comment.fixtures.*
tests/comment/comment.mocks.*
```

前端重点断言：

```text
是否正确渲染
slot / children 是否正确
按钮状态是否正确
输入是否正确响应
接口是否被正确调用
成功后 UI 是否更新
失败后 UI 是否恢复
是否出现错误提示
是否产生重复提交
是否存在安全问题
```

后端重点断言：

```text
响应码是否正确
响应体是否正确
数据是否正确处理
数据库状态是否正确变化
非法输入是否拒绝
权限是否正确校验
依赖失败是否正确处理
事务是否回滚
重复请求是否幂等
```

---

# 9. 第九步：运行门禁

运行测试时不要只看 pass / fail，要根据门禁解释结果。

建议生成：

```text
reports/testing/{module-name}.test-report.md
```

报告包含：

```text
执行命令
通过用例
失败用例
失败原因
失败类型
覆盖的不确定性
剩余风险
门禁结论
```

失败类型最好分清：

```text
业务实现问题
测试代码问题
环境问题
规格不清楚
Mock 设计问题
随机测试不可复现
```

最终结论应该是：

```text
允许推送
不允许推送
需要补充测试
需要澄清规格
```

而不是简单说：

```text
测试过了。
```

---

# 10. 第十步：随机测试失败回流

如果随机测试发现问题，不要只修 bug。

流程应该是：

```text
1. 记录 seed
2. 保存失败样本
3. 最小化复现条件
4. 确认是否真实缺陷
5. 修复缺陷
6. 新增确定性回归用例
7. 更新测试用例清单
```

也就是说：

> 随机测试发现的问题，最终要沉淀回模块测试体系。

否则随机测试只是一次性发现问题，没有形成长期资产。

# 12. 给 Codex 的实际执行顺序

你可以这样分三轮操作。

## 第一轮：只生成测试设计，不写代码

```text
请读取评论模块源码，并根据 docs/testing 中的测试方法论，为该模块生成：

1. comment.module-profile.md
2. comment.uncertainty-map.md
3. comment.test-plan.md
4. comment.test-cases.md
5. comment.dev-gate.md

暂时不要生成测试代码。
如果规格不清楚，请标记为“待确认假设”，不要自行编造业务规则。
```

## 第二轮：生成测试代码

```text
请根据已确认的模块测试画像、测试计划和测试用例，生成评论模块的自动化测试代码。

优先覆盖 P0 / P1 用例。
生成 fixtures、mocks 和组件测试。
不要只断言组件存在，必须断言业务行为、状态变化、接口调用和错误提示。
```

## 第三轮：增加随机测试

```text
请基于评论模块的测试用例和不变量，生成随机测试计划和小样本随机测试代码。

要求：
1. 定义生成器
2. 定义不变量
3. 记录 seed
4. 失败时输出失败样本和复现命令
5. 开发门禁默认随机 30 组
```

## 第四轮：运行并生成结论

```text
请运行评论模块相关测试。
根据测试结果生成 test-report 和 gate-checklist。
结论必须是：
- 允许推送
- 不允许推送
- 需要补充测试
- 需要澄清规格

不要只输出测试日志。
```

# 13. 最终流程图

```text
选择模块
  ↓
确定测试目标：开发门禁 / 合并门禁 / 发布门禁
  ↓
建立模块测试画像
  ↓
生成不确定性地图
  ↓
生成确定性测试用例
  ↓
定义门禁标准
  ↓
准备测试数据与 Mock
  ↓
生成自动化测试代码
  ↓
运行确定性测试
  ↓
设计并运行随机测试
  ↓
失败样本回流为回归用例
  ↓
生成测试报告和门禁结论
```

# 14. 一句话落地版

你开始测某个模块时，不要从“写测试代码”开始，而是从这三个问题开始：

```text
1. 这个模块的可观察行为是什么？
2. 哪些不确定性必须被降低？
3. 哪些用例通过后，当前阶段可以接受？
```

然后再让 AI 做：

```text
模块画像 → 用例 → Mock → 自动化代码 → 随机增强 → 报告 → 门禁结论
```

这样你就可以用同一套流程处理不同模块，同时允许前端、后端、组件、服务各自有不同的测试重点。

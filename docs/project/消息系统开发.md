# 消息系统开发

## 定位

ORF 的持久沟通界面是聊天：普通频道、私信、系统公告、我的系统通知都在聊天页阅读。聊天消息由 `chat_channels`、`chat_messages`、`chat_channel_members` 和 `chat_thread_follows` 表达。

系统通知不是聊天消息的别名。业务模块调用 `publishNotificationEvent` 后，先创建 `notification_events` 和 `notification_receipts`，明确记录触发人、业务对象、接收人和已读状态；再通过 `notification_deliveries` 投影到聊天。聊天投递失败只影响下游 delivery 状态，不能反向让已经成功的业务 mutation 返回失败。

GitLab、GitHub 等工程动态进入对应 ORF 普通项目频道，不创建系统通知。只有被建模为 ORF 内部目标、反馈、评论、申请、工作日志提醒等业务事件时，才创建系统通知事件，并按策略投影到系统公告或我的系统通知。

在线横幅广播和工作日志强提醒弹窗是实时展示能力，不等同于持久消息；页面数据同步仍通过 `orf.read-model.invalidated` 完成。工作日志欠账是否继续弹窗由 `work_log_reminder_states` 决定，不由通知事件或聊天投影决定。工作日志提醒基础设施默认关闭，正式启用前必须补齐团队日期覆盖和工作日志应填成员设置。

## 状态链和事实源

1. 业务 mutation 成功写入原业务表。
2. 业务模块调用 `publishNotificationEvent`。
3. 通知策略注册表决定事件进入 `teamAnnouncement` 或 `personalNotification`。
4. 通知仓库写入 `notification_events`，事件记录触发人、通知 kind、业务目标、跳转地址和回复目标。
5. 通知仓库应用集中隔离策略后写入 `notification_receipts`，每个实际接收人一条收据；团队公告中的触发人保留收据但默认已读，个人通知默认排除触发人。
6. 通知仓库写入 `notification_deliveries`，记录聊天投影的 `pending` / `delivered` / `failed` 状态、下游频道、消息 ID、重试次数和错误。
7. 投递层确保系统机器人、系统公告频道或用户个人系统会话存在，并调用 `sendChatMessage` 写入 `chat_messages`，`source = 'system'`，`system_metadata.notificationEventId` 回链通知事件。
8. `/api/notifications` 和 `/api/chat/system-conversations` 读取通知事件和收据；聊天页读取聊天投影。

唯一事实源：

| 事实 | 权威来源 |
| --- | --- |
| 业务状态 | 目标、指标、任务、反馈、评论、工作日志等原业务表 |
| 聊天会话 | `chat_channels` |
| 通知事件、kind、目标、回复目标 | `notification_events` |
| 通知接收人和已读状态 | `notification_receipts` |
| 通知到聊天的投递状态 | `notification_deliveries` |
| 聊天消息和系统通知投影 | `chat_messages` |
| 系统消息投影回链 | `chat_messages.system_metadata.notificationEventId` |
| 工作日志欠账提醒状态 | `work_log_reminder_states` |
| E2E 触发通知隔离规则 | `server/notifications/notificationIsolationPolicy.ts` |
| 当前用户频道已读/未读 | `chat_channel_members.last_read_at`、`last_read_message_id`、`manually_unread` |
| 话题已读/未读 | `chat_thread_follows.last_viewed_at` |
| 历史迁移来源 | 旧 `notifications` |

系统通知没有删除或清空语义。用户可以管理已读/未读注意力状态；聊天里的系统投影可以像普通聊天消息一样查看、复制、保存、固定、标记未读，但不能被普通用户编辑或删除，系统频道不能被用户改名、归档或改成员。

## 系统频道

当前固定两个系统频道：

| 频道 | `system_kind` | 频道类型 | 可见范围 | 典型事件 |
| --- | --- | --- | --- | --- |
| 系统公告 | `teamAnnouncement` | `public` | 当前作用域 active 用户 | `objective.published` |
| 我的系统通知 | `personalNotification` | `direct` 兼容投影 | `system_recipient_user_id` 指向的当前用户 | 申请、征召、战利品、反馈、评论、工作日志提醒 |

系统频道显示在聊天侧栏的“系统”分组，但打开后就是普通 `/chat/:channelId`。旧 `/chat/system/teamAnnouncements` 和 `/chat/system/personalNotifications` 只作为兼容路由，前端会替换到对应系统频道 URL。

个人系统通知历史上复用了 `direct` 类型以降低前端改造成本，但它不是人类私聊。普通 direct 的“两人成员”不变量只适用于 `system_kind IS NULL` 的私聊；系统投影的可见性由 `system_kind` 和 `system_recipient_user_id` 决定，系统机器人只是投递 actor，不是通知事实源。

系统消息正文使用普通聊天富文本，包含标题、正文和“打开目标”链接。可回复目标来自 `notification_events.replyTargetType` / `replyTargetId`，聊天 `system_metadata` 只保留事件回链和展示投影；普通聊天 composer 对系统频道禁用，避免系统频道变成用户随意发言的业务流。

## 通知判定原则

1. 只有成功写入业务状态的 mutation 才能创建通知事件。
2. 校验失败、权限失败、重复点击、并发失败和只读查询都不创建通知事件。
3. 触发人默认不接收自己的个人通知；系统公告可以看到历史，但触发人不会被标成未读。
4. 接收人必须是当前默认作用域内 `active` 用户。
5. 所有通知事件必须带 `targetType`、`targetId` 和 `targetHref`。
6. 可回复通知必须带 `replyTargetType` 和 `replyTargetId`，或能由通知策略从目标/metadata 推导。
7. 聊天投影失败必须记录在 `notification_deliveries`，不能让业务 mutation 500；补偿任务只重试投影，不重复创建通知事件。
8. 聊天 `system_metadata` 只保存展示、导航和事件回链辅助信息，不承载业务真相。
9. 没有明确下一步动作的高频更新不发系统通知，应进入页面时间线、活动流或审计日志。
10. 同一业务动作按主语义只生成一种通知事件；提及、直接回复和参与者通知需要去重。
11. `actorUserId` 对应的 `users.name` 包含 `E2E` 时，该用户触发的业务通知只投递给 `tangyl@sdrising.com`、`zrx831@gmail.com` 或用户名包含 `E2E` 的 active 用户；其他用户不产生收据、不生成聊天投影、不计未读、不推送。没有 `actorUserId` 的系统/历史事件才回退检查 `actorName`。`tangyl@sdrising.com` 和 `zrx831@gmail.com` 只是 E2E 通知接收白名单，不是 E2E 发送源。

## E2E 通知隔离

E2E 隔离是通知层治理规则，不属于目标、挑战、反馈或评论等业务模块。业务模块仍按原有业务语义提交 `actorName`、`actorUserId`、`NotificationKind` 和候选 `recipientUserIds`，不得在各业务动作中散落 `E2E` 字符串判断。

集中规则定义在 `server/notifications/notificationIsolationPolicy.ts`：

| 规则 | 含义 |
| --- | --- |
| E2E 触发人 | 优先使用 `actorUserId -> users.name` 包含 `E2E`；没有用户 ID 时才回退 `actorName` |
| 允许接收邮箱 | `tangyl@sdrising.com`、`zrx831@gmail.com` |
| 允许接收用户名 | `users.name` 包含 `E2E` |
| 接收白名单语义 | 只允许接收 E2E 触发的通知，不会让这些邮箱发出的普通通知被隔离 |

通知仓库是主收口：在 `notification_events` 保留事件事实后，只为允许接收人写入 `notification_receipts` 和 `notification_deliveries`。E2E 触发的 `teamAnnouncement` 不投递到公共系统公告频道，而是按允许接收人生成个人聊天投影，避免测试发布悬赏污染全员公告。

历史已生成的系统消息不做物理删除；`/api/notifications`、旧系统会话兼容 API 和聊天读取/未读/搜索入口通过同一策略过滤历史投影，避免普通用户继续看到或计入旧 E2E 消息。

## 数据模型

`notification_events` 表达事件事实：

| 字段 | 说明 |
| --- | --- |
| `stream` | `teamAnnouncement` 或 `personalNotification` |
| `actor_user_id` / `actor_name` | 触发业务事件的人；系统自动任务可为空 |
| `kind` | `NotificationKind` |
| `target_type` / `target_id` / `target_href` | 被通知的业务对象和跳转 |
| `reply_target_type` / `reply_target_id` | 可回复通知的评论目标 |
| `metadata` | 展示和回复锚点辅助数据 |

`notification_receipts` 表达接收人事实：

| 字段 | 说明 |
| --- | --- |
| `event_id` / `recipient_user_id` | 事件和接收人 |
| `delivered_at` | 通知事实交付给接收人的时间，不等于聊天投影成功 |
| `read_at` | 通知已读事实源 |

`notification_deliveries` 表达下游投递：

| 字段 | 说明 |
| --- | --- |
| `channel` | 当前实现为 `chat`，后续可扩展到 push/email |
| `status` | `pending`、`delivered`、`failed` |
| `destination_id` / `message_id` | 下游聊天频道和消息 |
| `attempts` / `last_error` / `next_attempt_at` | 补偿投递状态 |

`chat_channels` 的系统字段：

| 字段 | 说明 |
| --- | --- |
| `system_kind` | 空值表示普通频道；`teamAnnouncement` 表示系统公告；`personalNotification` 表示我的系统通知 |
| `system_recipient_user_id` | 个人系统通知频道所属用户；系统公告为空 |

`chat_messages` 的系统字段：

| 字段 | 说明 |
| --- | --- |
| `source` | `user` 或 `system` |
| `system_metadata.notificationEventId` | 对应 `notification_events.id` |
| `system_metadata.kind` / `stream` | 事件 kind 和 stream 的投影副本 |
| `system_metadata.targetType` / `targetId` / `targetHref` | 关联对象和跳转位置的投影副本 |
| `system_metadata.replyTargetType` / `replyTargetId` | 可回复消息评论目标的投影副本 |
| `system_metadata.metadata` | 展示和回复锚点辅助数据 |

## 测试口径

- 后端流程测试必须验证关键业务动作会生成正确 `notification_events`、`notification_receipts`、`notification_deliveries`，并在聊天成功时生成 `chat_messages.source/system_metadata`。
- 评论测试必须覆盖 `@`、直接回复、反馈参与者三类系统消息的去重。
- API 测试必须验证系统公告可被当前作用域用户读取，个人系统通知不能读取别人的频道。
- API 测试必须验证系统消息和系统频道不能被普通用户编辑、删除、归档或改成员。
- 前端测试必须验证系统入口在聊天侧栏，打开后渲染普通聊天消息列表。
- 聊天消息发送、聊天 `@` 提及和聊天线程回复不得创建系统消息。
- 新增通知事件时，必须同步更新 `NotificationKind`、通知策略注册表、后端投递测试和本文件。

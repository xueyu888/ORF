# 消息系统开发

## 定位

ORF 只有一个持久消息系统：聊天。普通频道、私信、系统公告、我的系统通知都由 `chat_channels`、`chat_messages`、`chat_channel_members` 和 `chat_thread_follows` 表达。

业务模块仍调用 `publishNotificationEvent`，但它只是系统聊天投递入口，不再创建独立的系统会话事实源。投递层按策略选择系统频道，并用 ORF 系统机器人写入普通聊天消息。

GitLab、GitHub 等工程动态进入对应 ORF 普通项目频道。只有被建模为 ORF 内部目标、反馈、评论、申请、工作日志提醒等业务事件时，才通过系统聊天投递到系统公告或我的系统通知。

在线横幅广播是实时展示能力，不等同于持久消息；页面数据同步仍通过 `orf.read-model.invalidated` 完成。

## 状态链和事实源

1. 业务 mutation 成功写入原业务表。
2. 业务模块调用 `publishNotificationEvent`。
3. 通知策略注册表决定事件进入 `teamAnnouncement` 或 `personalNotification`。
4. 投递层确保系统机器人、系统公告频道或用户个人系统私信存在。
5. 投递层调用 `sendChatMessage` 写入 `chat_messages`，`source = 'system'`，业务目标、回复目标和通知 kind 写入 `system_metadata`。
6. 未读、已读、实时、推送、本地通知、移动端角标全部复用聊天链路。
7. 旧 `/api/notifications` 和 `/api/chat/system-conversations` 只做兼容投影，不再定义新事实。

唯一事实源：

| 事实 | 权威来源 |
| --- | --- |
| 业务状态 | 目标、指标、任务、反馈、评论、工作日志等原业务表 |
| 聊天会话 | `chat_channels` |
| 聊天消息和系统消息 | `chat_messages` |
| 系统消息 kind、目标、回复目标 | `chat_messages.system_metadata` |
| 当前用户频道已读/未读 | `chat_channel_members.last_read_at`、`last_read_message_id`、`manually_unread` |
| 话题已读/未读 | `chat_thread_follows.last_viewed_at` |
| 历史迁移来源 | `notification_events`、`notification_receipts`、旧 `notifications` |

系统消息没有删除或清空语义。用户可以像普通聊天一样查看、复制、保存、固定、标记未读；系统消息不能被普通用户编辑或删除，系统频道不能被用户改名、归档或改成员。

## 系统频道

当前固定两个系统频道：

| 频道 | `system_kind` | 频道类型 | 可见范围 | 典型事件 |
| --- | --- | --- | --- | --- |
| 系统公告 | `teamAnnouncement` | `public` | 当前作用域 active 用户 | `objective.published` |
| 我的系统通知 | `personalNotification` | `direct` | 当前用户和 ORF 系统机器人 | 申请、征召、战利品、反馈、评论、工作日志提醒 |

系统频道显示在聊天侧栏的“系统”分组，但打开后就是普通 `/chat/:channelId`。旧 `/chat/system/teamAnnouncements` 和 `/chat/system/personalNotifications` 只作为兼容路由，前端会替换到对应系统频道 URL。

系统消息正文使用普通聊天富文本，包含标题、正文和“打开目标”链接。可回复目标保留在 `system_metadata.replyTargetType` / `replyTargetId`，兼容 API 可以把回复写入对应业务评论；普通聊天 composer 对系统频道禁用，避免系统频道变成用户随意发言的业务流。

## 通知判定原则

1. 只有成功写入业务状态的 mutation 才能创建系统聊天消息。
2. 校验失败、权限失败、重复点击、并发失败和只读查询都不创建系统消息。
3. 触发人默认不接收自己的个人通知；系统公告可以看到历史，但触发人不会被标成未读。
4. 接收人必须是当前默认作用域内 `active` 用户。
5. 所有系统消息必须带 `targetType`、`targetId` 和 `targetHref`。
6. 可回复系统消息必须带 `replyTargetType` 和 `replyTargetId`，或能由通知策略从目标/metadata 推导。
7. 系统消息 metadata 只保存展示和导航辅助信息，不承载业务真相。
8. 没有明确下一步动作的高频更新不发系统消息，应进入页面时间线、活动流或审计日志。
9. 同一业务动作按主语义只生成一种系统消息；提及、直接回复和参与者通知需要去重。

## 数据模型

`chat_channels` 的系统字段：

| 字段 | 说明 |
| --- | --- |
| `system_kind` | 空值表示普通频道；`teamAnnouncement` 表示系统公告；`personalNotification` 表示我的系统通知 |
| `system_recipient_user_id` | 个人系统通知频道所属用户；系统公告为空 |

`chat_messages` 的系统字段：

| 字段 | 说明 |
| --- | --- |
| `source` | `user` 或 `system` |
| `system_metadata.kind` | `NotificationKind` |
| `system_metadata.stream` | `teamAnnouncement` 或 `personalNotification` |
| `system_metadata.targetType` / `targetId` / `targetHref` | 关联对象和跳转位置 |
| `system_metadata.replyTargetType` / `replyTargetId` | 可回复消息的评论目标 |
| `system_metadata.metadata` | 展示和回复锚点辅助数据 |

`notification_events` 和 `notification_receipts` 是历史迁移来源。迁移 `0057_system_notifications_as_chat.sql` 会把旧事件和收据迁入系统聊天频道；新代码不再写入这两张表。旧逐条 receipt 已读模型会折叠为聊天频道的单调已读边界，迁移策略优先保证历史未读不被吞掉。

## 后端边界

| 模块 | 职责 |
| --- | --- |
| `server/notifications/policies/registry.ts` | 注册每种 `NotificationKind` 的 stream 和回复目标推导规则 |
| `server/notifications/publisher.ts` | 统一补齐 stream 和回复目标，保持业务调用入口稳定 |
| `server/repositories/notificationRepository.ts` | 确保系统机器人和系统频道，向 `chat_messages` 投递系统消息，提供旧通知 API 的聊天投影 |
| `server/repositories/systemConversationRepository.ts` | 兼容旧系统会话 API，读取聊天投影并把兼容回复写入业务评论 |
| `server/repositories/chatRepository.ts` | 聊天消息事实源、系统消息写入、系统频道只读约束、聊天未读和实时推送 |
| `server/routes/notificationRoutes.ts` | 旧通知兼容 API；删除和清空返回 `410` |
| `server/routes/systemConversationRoutes.ts` | 旧系统会话兼容 API |
| `server/db/schema.ts` / `drizzle/*` | 聊天系统字段、历史迁移和 runtime schema guard |

## 前端边界

| 模块 | 职责 |
| --- | --- |
| `src/pages/ChatPage.tsx` | 只渲染普通聊天页面；兼容旧系统路由到系统频道 |
| `src/features/chat/ChatSidebar.tsx` | 从 `channels.systemKind` 派生“系统”分组 |
| `src/features/chat/ChatMessageFeed.tsx` / `ChatMessageItem.tsx` | 复用普通聊天消息渲染；系统消息禁用编辑和删除 |
| `src/features/chat/chatChannelPresentation.ts` | 系统频道的标题、搜索和图标展示 |
| `src/components/MobileBottomNav.tsx` | 聊天角标只读 `chatUnreadSummary.totalUnreadCount` |
| `src/state/OrfProvider.tsx` | 聊天实时事件刷新聊天未读和本地通知；旧 notification 状态仅兼容旧接口 |

`/notifications` 前端路由只重定向到 `/chat/system/personalNotifications`，再由聊天页替换到普通系统频道 URL。

## 测试口径

- 后端流程测试必须验证关键业务动作会生成正确 `chat_messages.source/system_metadata`、系统频道和接收人。
- 评论测试必须覆盖 `@`、直接回复、反馈参与者三类系统消息的去重。
- API 测试必须验证系统公告可被当前作用域用户读取，个人系统通知不能读取别人的频道。
- API 测试必须验证系统消息和系统频道不能被普通用户编辑、删除、归档或改成员。
- 前端测试必须验证系统入口在聊天侧栏，打开后渲染普通聊天消息列表。
- 聊天消息发送、聊天 `@` 提及和聊天线程回复不得创建系统消息。
- 新增通知事件时，必须同步更新 `NotificationKind`、通知策略注册表、后端投递测试和本文件。

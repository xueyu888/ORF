# 消息系统开发

## 定位

ORF 的持久沟通界面是聊天：普通频道、私信、系统公告、我的系统通知都在聊天页阅读。聊天消息由 `chat_channels`、`chat_messages`、`chat_channel_members` 和 `chat_thread_follows` 表达；逐收件人的移动推送任务由 `chat_push_deliveries` 表达。realtime 只向当前在线 SSE 连接发送内存唤醒事件，不建立持久投递记录。普通/私有群聊可以通过 `chat_channels.project_id` 绑定一个 ORF 项目作为频道上下文；群聊轻量资源流通过 `chat_channel_drive_links` 绑定团队云盘里的文件或文件夹。

系统通知不是聊天消息的别名。普通业务模块可以通过通知发布入口创建 `notification_events` 和 `notification_receipts`，明确记录触发人、业务对象、接收人和已读状态；再通过 `notification_deliveries` 投影到聊天。反馈模块是例外边界：反馈业务事务先写入自己的 outbox，由 feedback notification worker 以稳定幂等键调用通知端口，通知模块只物化通用事件、收据和聊天投影，不计算反馈收件人或解析反馈 payload。聊天投递失败只影响下游 delivery 状态，不能反向让已经成功的业务 mutation 返回失败。

GitLab、GitHub 等工程动态进入对应 ORF 普通项目频道，不创建系统通知。只有被建模为 ORF 内部目标、反馈、评论、申请、工作日志提交/提醒等业务事件时，才创建系统通知事件，并按策略投影到系统公告或我的系统通知。

在线横幅广播和工作日志强提醒弹窗是实时展示能力，不等同于持久消息；页面数据同步仍通过 `orf.read-model.invalidated` 完成。工作日志欠账是否继续弹窗由 `work_log_reminder_states` 决定，不由通知事件或聊天投影决定。工作日志提醒基础设施默认关闭，正式启用前必须补齐团队日期覆盖和工作日志应填成员设置。

普通聊天发送在同一个数据库事务中写入 `chat_messages` 和逐收件人的 `chat_push_deliveries`。事务提交后，realtime 立即按一次收件人查询向在线连接广播轻量唤醒；`ChatRealtimeEvent` 不允许携带完整频道或消息投影，只允许附带当前收件人的强提醒原因、统一目标路径和发送者展示身份，供客户端即时 Toast/flash 使用。页面不能把 SSE 载荷写回消息事实，只能回到事实接口对账。系统频道中的消息是 `notification_events` 的阅读投影，不再生成第二次聊天 Toast 或聊天强提醒；一次性 Toast 由原通知事件负责，避免同一业务事件从通知和聊天投影各弹一次。普通项目频道里的系统投影仍按频道消息处理。realtime 不重试、不进入 dead letter，也不参与消息完整性判断。独立 push worker 统一领取推送任务并按固定全局并发分发，不为每次发消息各自启动一轮数据库读取。push 失败使用租约、硬超时、有限次数指数退避和 `dead_letter` 收口；进程中断后过期租约可由后续领取恢复。客户端首次连接、每次重连、网络恢复、窗口重新聚焦或页面重新可见时，均从持久消息接口对账，因此错过实时事件不会再要求用户手动刷新。

传输状态只陈述服务端实际观察到的边界：持久队列最多确认推送服务接受了多少个设备请求。ORF 不持久化客户端 ACK，也不把“写入连接”“推送服务接受”解释为用户已经看到或已读；已读事实仍只来自聊天成员和话题的读游标。旧 realtime 记录迁入只读诊断归档 `chat_legacy_realtime_deliveries`，统一标记 `completed / legacy_realtime_retired`，30 天后清理且不能被 worker 领取。历史 push 的 `delivered` 无法还原真实传输结果，迁移后仅在 push 队列记为 `completed / legacy_processed`。

实时恢复由一个显式连接代次驱动：

```text
disabled/disconnected
  -> connecting
  -> connected(connectionEpoch)
  -> reconciling(connectionEpoch)
  -> ready(connectionEpoch)
```

`connectionEpoch` 是当前客户端运行时的连接代次，不是消息事实或服务端投递回执。每次 `EventSource.open`，包括应用更新重启后的首次连接，都会产生新 epoch；全局未读/注意力投影与聊天页频道、当前消息窗口、已打开话题分别消费同一个 epoch。页面晚挂载时读取当前 epoch 并补做自己的对账，不依赖瞬时“连接恢复”事件。对账协调器同一时刻只运行一次；执行期间发生的新触发会在完成后尾随再运行一次，失败则保留错误并指数退避重试。

聊天消息窗口与滚动位置继续是会话内展示状态。普通聊天入口优先恢复当前用户本机从新版开始记录的停留频道；打开具体频道时由同一个 `ChatFeedOpenIntent` 决定入口目标，优先级固定为消息链接、第一条主消息未读、本机消息锚点、最新消息窗口。消息链接是一次目标消息打开意图，不是缓存命中判断：无论主消息或话题回复是否已经存在于会话窗口缓存，打开 `?message=` 或 `?thread=&message=` 时都必须回到 `getChatMessageContext` 或 `getChatThread` 重读目标消息事实，校准正文、附件、反应、固定、收藏和回执等消息投影后再完成定位。主消息未读目标和手动“跳到未读”都只使用 `/api/chat/channels/:channelId/unread-target?surface=main` 加载主消息上下文；话题提及目标只通过 `surface=threadMention` 打开话题并聚焦回复，不能和主消息滚动目标混用。聊天页按事件职责分别对账频道 bootstrap、当前主消息窗口和已打开话题：`read.changed` 只通过 bootstrap 刷新频道/话题已读投影，不能进入主消息窗口、重新读取已打开话题正文或触发滚动；话题正文读取只有在读游标真正前进时才广播一次 `read.changed`，重复读取不得重写读状态版本。消息创建、编辑、删除和反应变化只对账受影响频道的消息表面；连接 epoch 恢复才允许三个投影分别补做完整对账。对账拉取最新窗口后按 `messageId` 幂等合并：主消息视口以 `followingLatest` / `browsingHistory` 表达当前用户意图，用户位于最新位置时更新可见消息并继续跟随；用户阅读历史窗口时保留可见锚点，把最新窗口缓存在 `ChatFeedSnapshot.latestWindowMessages`，只用 `hasNewerMessages` 展示“回到最新”，用户进入最新位置时直接切换到已对账窗口。未读数字只来自服务端读光标和频道/话题未读投影，不能由历史窗口与最新分页的差集派生。异步对账提交时必须重新读取当前视口模式并放弃过期的程序滚动；滚动状态不得阻止数据同步，也不得反向改写消息、未读或频道事实。

连接恢复的完整性由团队级 `chat_sync_events` 变化序列证明。聊天频道、成员、消息、反应、固定、收藏、已读和话题关注发生逻辑变化时，数据库触发器在同一事务内追加一条事件；系统通知、GitHub/GitLab 机器人或其他直接写聊天表的链路同样被覆盖。事件只保存 `team_id`、单调 `seq`、协议版本、事件/对象类型、对象和频道引用、操作者引用、时间戳及白名单 metadata，不保存消息正文、附件正文或按收件人展开的副本。正文和权限始终在同步时回到聊天事实表读取，`chat_sync_events` 不能作为第二份消息库。

客户端把游标保存在本机，记录粒度为“用户 + 团队 + 客户端安装标识”；服务端不保存设备游标。每个连接 epoch 先读取变化窗口，再执行既有频道、未读、注意力和当前消息窗口对账，成功后才推进本地游标。游标缺失、早于保留窗口、超前/非法、团队不匹配、聊天权限指纹变化、协议版本不兼容或待补事件超过增量上限时，直接退化为完整对账。事件按 `messageId` 等对象引用幂等消费，不直接生成第二次消息、未读或托盘提醒。

事件保留策略固定为 30 天且每团队最多 100 万条，任一边界达到即由独立清理调度器删除旧事件。游标只是恢复加速路径；清理后老客户端仍通过完整频道、未读和最新消息窗口对账恢复，不能因为事件已清理而丢消息。

注意力系统是消息系统之上的展示派生层，不是新的通知事实源。Win11 任务栏角标、系统 Toast、任务栏闪烁、右下角托盘图标闪烁、托盘入口、AppShell 侧边栏“待我处理”和移动端底部 `待办` 入口都从可处理聊天提醒、普通聊天未读、系统通知、工作日志提醒、窗口状态和当前路由派生，具体方案见 [ORF 注意力系统方案.md](./ORF%20注意力系统方案.md)。普通聊天总未读只进入聊天入口和桌面 `badgeCount`，不进入“待我处理”；私聊、具名 @ 当前用户、`@所有人` 和话题内显式提及在 realtime 到达时先产生短生命周期强提醒意图，再由 `/api/chat/unread-summary` 的同一批 `unread_message_facts` 派生计数和 `nextTarget` 接管，二者按消息和提醒类型合并，不能重复计数。待办项、原生通知和 push 均复用 `nextTarget`/`chatMessageTargetPath` 定位具体消息；普通聊天入口和移动端聊天底栏只展示未读数量，打开含主消息未读的频道时由聊天消息流加载第一条主未读，不消费待办 `nextTarget`。注意力系统不得改变通知收件人、业务状态或聊天投影；用户在“待我处理”里打开通知项或点击“通知全部已读”时，只能调用既有通知已读接口更新 `notification_receipts.read_at`。发送者头像只从用户头像字段派生为 Toast 展示数据，不写入通知事件、消息或新的持久事实源。

## 状态链和事实源

1. 业务 mutation 成功写入原业务表。
2. 业务模块提交通知请求；反馈模块提交到 `feedback_event_dispatches` outbox 后由 worker 调用通知端口。
3. 通知展示 provider 或通用通知策略决定事件进入 `teamAnnouncement` 或 `personalNotification`。
4. 通知仓库写入 `notification_events`，事件记录触发人、通知 kind、业务目标、跳转地址和回复目标。
5. 通知仓库应用集中隔离策略后写入 `notification_receipts`，每个实际接收人一条收据；团队公告中的触发人保留收据但默认已读，个人通知默认排除触发人。
6. 通知仓库写入 `notification_deliveries`，记录聊天投影的 `pending` / `delivered` / `failed` 状态、下游频道、消息 ID、重试次数和错误。
7. 投递层确保系统机器人、系统公告频道或用户个人系统会话存在，并调用 `sendChatMessage` 写入 `chat_messages`，`source = 'system'`，`system_metadata.notificationEventId` 回链通知事件。
8. `/api/notifications` 和 `/api/chat/system-conversations` 读取通知事件和收据；聊天页读取聊天投影。

唯一事实源：

| 事实 | 权威来源 |
| --- | --- |
| 业务状态 | 目标、指标、任务、反馈、评论、工作日志等原业务表 |
| 聊天会话 | `chat_channels` |
| 群聊绑定项目 | `chat_channels.project_id` |
| 团队云盘树和文件元数据 | `drive_nodes`、`drive_files` |
| 群聊云盘快捷绑定 | `chat_channel_drive_links` |
| 云盘工作上下文链接 | `drive_node_context_links` |
| 通知事件、kind、目标、回复目标 | `notification_events` |
| 通知接收人和已读状态 | `notification_receipts` |
| 通知到聊天的投递状态 | `notification_deliveries` |
| 聊天消息和系统通知投影 | `chat_messages` |
| 聊天附件和预览类型 | `chat_attachments`，由聊天附件投影派生 `previewKind` |
| 聊天消息反应 | `chat_message_reactions`，由消息读取接口聚合为 `ChatMessage.reactions` |
| 普通聊天逐收件人移动推送状态 | `chat_push_deliveries` |
| 旧 realtime 投递诊断归档 | `chat_legacy_realtime_deliveries`；只读、不可领取、30 天清理 |
| 聊天断线恢复的非正文变化序列 | `chat_sync_events`；仅作为同步游标，不是消息事实源 |
| 系统消息投影回链 | `chat_messages.system_metadata.notificationEventId` |
| 工作日志欠账提醒状态 | `work_log_reminder_states` |
| 反馈处理人每日汇总运行状态 | `feedback_daily_digest_runs` |
| E2E 触发通知隔离规则 | `server/notifications/notificationIsolationPolicy.ts` |
| 当前用户频道已读/未读 | `chat_channel_members.last_read_at`、`last_read_message_id`、`manually_unread` |
| 话题已读/未读 | `chat_thread_follows.last_viewed_at` |
| 历史迁移来源 | 旧 `notifications` |

系统通知没有删除或清空语义。用户可以管理已读/未读注意力状态；聊天里的系统投影可以像普通聊天消息一样查看、复制、保存、固定、标记未读，但不能被普通用户编辑或删除，系统频道不能被用户改名、归档或改成员。

系统通知投影必须区分“投递作者”和“展示作者”。`chat_messages.author_user_id` 继续指向负责写入聊天投影的系统机器人，不能改写成触发业务事件的成员，也不能因此获得普通用户消息的编辑、删除或权限语义；`system_metadata.actorUserId`、`actorName` 是系统事件展示作者的事实。聊天消息流、话题、搜索和收藏等展示入口在存在有效成员触发人时统一展示该成员的姓名与当前头像，并标记为“系统事件”；定时任务、后台同步等没有成员触发人的事件继续展示系统机器人。展示作者只影响界面身份，不改变通知事件、收件人、已读、审计或聊天投递链路。

聊天附件和云盘是不同事实源：`chat_attachments` 只属于具体聊天消息；团队云盘由 `drive_nodes` 和 `drive_files` 维护，群聊只通过 `chat_channel_drive_links` 绑定云盘文件或文件夹。聊天头部提供资源入口，侧栏负责绑定已有云盘文件/文件夹、上传到默认文件夹、搜索频道资源和轻量预览；完整筛选、版本、回收站、上下文管理和详情管理统一进入 `/resources` 的资源工作台：左侧是资源集合，中间是搜索和高密度列表，右侧是文件预览、详情、版本、活动和上下文。上传云盘后可以在群聊里生成普通消息动态，但这条动态只是文件入口的展示投影，不是文件内容或文件归属事实源。

### 聊天界面呈现契约

聊天页的频道列表、消息流、头部、输入区、右侧面板和浮层只消费 AppShell 的共享前景材质与全局浅色/深色语义，不在聊天 CSS 内再维护第二套背景明暗判断或页面私有主题。`page_chat_background` 只决定聊天内容区背景；用户对背景、蒙层、模糊和材质强度的设置应继续由 AppShell 唯一事实源生效，聊天页不得重写或反向推导这些设置。

消息、未读、发送权限和业务引用的事实来源不变。反馈与工作日志卡片只是服务端引用数据的可折叠展示投影，加载、缺失和失败必须显式呈现，不得伪造业务状态。卡片以稳定引用键维护一次加载生命周期；卡片加载、图片解码和内容折叠造成的高度变化统一进入滚动容器的单一布局观察器。跟随最新、未读定位、消息定位、阅读位置恢复和话题定位都是互斥的视口意图：布局稳定前持续恢复当前意图，用户主动滚动后立即失效，不能各自维护短帧重试或独立观察器。加载更早消息属于当前阅读锚点恢复，必须复用同一布局意图和失效规则；锚点仍在窗口内时按消息锚点恢复，锚点临时不可用时才按分页前后高度差恢复。浏览历史时最新窗口对账只能更新会话缓存和“回到最新”提示，不替换当前可见窗口；`hasNewerMessages` 只表示当前视口之后还有最新窗口，不携带数字。未读数量只来自服务端读光标、频道成员读状态和话题关注读状态，历史窗口与最新分页是否重叠不得派生或展示额外数字。通过通知、搜索、复制链接或原生 Toast 打开的消息深链只能把会话缓存作为首帧展示状态；最终显示和高亮必须以服务端目标消息读取结果为准，不能靠刷新整页、清空缓存或让通知入口接管聊天数据来修正反应数量。系统频道等无发送权限的会话不渲染一套虚假可编辑的禁用输入器，只展示紧凑的只读状态提示。移动端使用同一业务事实源，只在列表、频道和右侧面板之间维护临时展示导航：返回顺序固定为面板到频道、频道到列表，不产生另一套聊天状态。

目标、指标、任务、反馈和工作日志等业务对象只通过 `drive_node_context_links` 表达资源关联。业务页可以按 `contextType` 和 `contextId` 读取资源投影并跳转到 `/resources/:nodeId/preview`，也可以把“上传并关联”“关联已有资源”“取消关联”编排到同一云盘事实源；但业务页不维护云盘删除、恢复、版本或详情状态机。当前挑战列表主视图不直接铺开目标、指标或任务资源块，避免空资源面板打断目标/任务主流程；这些关联关系仍由资源工作台和后续更合适的详情侧栏承载。工作日志页面的当天资源汇总只从当天各条 `work_log_entries.id` 的资源链接派生，不写入日期级云盘归属。

## 系统频道

当前固定两个系统频道：

| 频道 | `system_kind` | 频道类型 | 可见范围 | 典型事件 |
| --- | --- | --- | --- | --- |
| 系统公告 | `teamAnnouncement` | `public` | 当前作用域 active 用户 | `objective.published`、`worklog.submitted` |
| 我的系统通知 | `personalNotification` | `direct` 兼容投影 | `system_recipient_user_id` 指向的当前用户 | 申请、征召、战利品、反馈、评论、工作日志提醒 |

系统频道显示在聊天侧栏的“系统”分组，但打开后就是普通 `/chat/:channelId`。旧 `/chat/system/teamAnnouncements` 和 `/chat/system/personalNotifications` 只作为兼容路由，前端会替换到对应系统频道 URL。

个人系统通知历史上复用了 `direct` 类型以降低前端改造成本，但它不是人类私聊。普通 direct 的“两人成员”不变量只适用于 `system_kind IS NULL` 的私聊；系统投影的可见性由 `system_kind` 和 `system_recipient_user_id` 决定，系统机器人只是投递 actor，不是通知事实源。

系统消息正文使用普通聊天富文本，包含标题、正文和由通知展示 provider 按 namespace/payload 派生的动作链接；不得在业务正文里再手写重复动作链接。反馈评论、评论回复和评论提及通知的正文是评论内容快照：文本来自 `comment_messages.body` 并在聊天通知中展示为引用摘要，图片只保留同一条评论 `comment_attachments` 中可预览图片的展示引用，且作为引用摘要下的独立预览块展示；普通文件附件不投影到聊天通知正文。可回复目标来自 `notification_events.replyTargetType` / `replyTargetId`，聊天 `system_metadata` 只保留事件回链和展示投影；普通聊天 composer 对系统频道禁用，避免系统频道变成用户随意发言的业务流。

反馈通知由反馈模块计算收件人、静音、强提醒和展示 payload，通知模块只接收带幂等键的通用发布请求并物化个人系统通知。反馈动态只投递到相关成员的个人系统通知；`Feedback.projectId` 只作为反馈上下文展示，不决定聊天目的地。

聊天页对 `/tasks#objective:*`、`/tasks#action:*` 和 `/tasks#subAction:*` 链接按普通站内链接处理：普通点击进入 `/tasks` 完整页并由挑战页负责定位；浏览器新开仍按标准链接行为处理。聊天页不再拦截这些链接展开目标/行动项右侧工作区，这不改变 `notification_events.targetHref`、`chat_messages.system_metadata.targetHref` 或目标/行动项事实源。

`GET /api/chat/bootstrap` 是聊天页重初始化包，返回频道、成员、权限、设置、最后消息预览和未读聚合等重读模型。登录后空闲阶段可以预热一次，进入聊天优先消费会话缓存；结构性成员变化、聊天设置变化、手动重试或受节流的连接恢复使缓存失效并后台刷新，不能清空已显示的频道和消息后再转圈。`GET /api/chat/users` 只返回当前聊天可见的 `ChatUser[]` 轻量投影，用于 `user.presence.changed` 这类在线状态变化；presence 心跳不得触发完整 bootstrap。聊天频道消息窗口在同一登录会话内保留，切出再返回先显示原窗口，同时后台拉取最新消息；当前用户本机从新版开始记录停留频道和消息锚点，用于普通聊天入口恢复，不做历史迁移、跨设备同步或服务端写入；切换身份必须清空。

## 通知判定原则

1. 只有成功写入业务状态的 mutation 才能创建通知事件。
2. 校验失败、权限失败、重复点击、并发失败和只读查询都不创建通知事件。
3. 触发人默认不接收自己的个人通知；系统公告可以看到历史，但触发人不会被标成未读。
4. 接收人必须是当前默认作用域内 `active` 用户。
5. 所有通知事件必须带 `targetType`、`targetId` 和 `targetHref`。
6. 可回复通知必须带 `replyTargetType` 和 `replyTargetId`，或能由通知策略从目标/metadata 推导。
7. 聊天投影失败必须记录在 `notification_deliveries`，不能让业务 mutation 500；补偿任务只重试投影，不重复创建通知事件。
8. 聊天 `system_metadata` 只保存展示、导航和事件回链辅助信息，不承载业务真相。
9. 没有明确下一步动作的高频更新不发系统通知，应进入页面时间线、活动流或审计日志。
10. 同一业务动作按主语义只生成一种通知事件；提及、直接回复和参与者通知需要去重。
11. `actorUserId` 对应的 `users.name` 包含 `E2E` 时，该用户触发的业务通知只投递给 `tangyl@sdrising.com`、`zrx831@gmail.com` 或用户名包含 `E2E` 的 active 用户；其他用户不产生收据、不生成聊天投影、不计未读、不推送。没有 `actorUserId` 的系统/历史事件才回退检查 `actorName`。`tangyl@sdrising.com` 和 `zrx831@gmail.com` 只是 E2E 通知接收白名单，不是 E2E 发送源。
12. 普通消息或系统事件消息首次新增 Emoji 回应时，向界面展示作者创建 `chat.reaction.created` 个人通知并定位原消息；重复写入、撤销回应和回应自己的消息不创建通知。回应事实仍只来自 `chat_message_reactions`，通知不改变聊天已读游标。

## E2E 通知隔离

E2E 隔离是通知层治理规则，不属于目标、挑战、反馈或评论等业务模块。业务模块仍按自己的业务语义提交 actor、目标、payload、收件人候选和稳定幂等键；不得在各业务动作中散落 `E2E` 字符串判断。

集中规则定义在 `server/notifications/notificationIsolationPolicy.ts`：

| 规则 | 含义 |
| --- | --- |
| E2E 触发人 | 优先使用 `actorUserId -> users.name` 包含 `E2E`；没有用户 ID 时才回退 `actorName` |
| 允许接收邮箱 | `tangyl@sdrising.com`、`zrx831@gmail.com` |
| 允许接收用户名 | `users.name` 包含 `E2E` |
| 接收白名单语义 | 只允许接收 E2E 触发的通知，不会让这些邮箱发出的普通通知被隔离 |

通知仓库是主收口：在 `notification_events` 保留事件事实后，只为允许接收人写入 `notification_receipts` 和 `notification_deliveries`。E2E 触发的 `teamAnnouncement` 不投递到公共系统公告频道，而是按允许接收人生成个人聊天投影，避免测试发布悬赏污染全员公告。

历史已生成的系统消息不做物理删除；`/api/notifications`、旧系统会话兼容 API 和聊天读取/未读/搜索入口通过同一策略过滤历史投影，避免普通用户继续看到或计入旧 E2E 消息。

## 数据模型

`notification_events` 表达事件事实：

| 字段 | 说明 |
| --- | --- |
| `stream` | `teamAnnouncement` 或 `personalNotification` |
| `actor_user_id` / `actor_name` | 触发业务事件的人；系统自动任务可为空 |
| `kind` | `NotificationKind` |
| `target_type` / `target_id` / `target_href` | 被通知的业务对象和跳转 |
| `reply_target_type` / `reply_target_id` | 可回复通知的评论目标 |
| `metadata` | 展示和回复锚点辅助数据 |

`notification_receipts` 表达接收人事实：

| 字段 | 说明 |
| --- | --- |
| `event_id` / `recipient_user_id` | 事件和接收人 |
| `delivered_at` | 通知事实交付给接收人的时间，不等于聊天投影成功 |
| `read_at` | 通知已读事实源 |

`notification_deliveries` 表达下游投递：

| 字段 | 说明 |
| --- | --- |
| `channel` | 当前实现为 `chat`，后续可扩展到 push/email |
| `status` | `pending`、`delivered`、`failed` |
| `destination_id` / `message_id` | 下游聊天频道和消息 |
| `attempts` / `last_error` / `next_attempt_at` | 补偿投递状态 |

`chat_channels` 的系统字段：

| 字段 | 说明 |
| --- | --- |
| `system_kind` | 空值表示普通频道；`teamAnnouncement` 表示系统公告；`personalNotification` 表示我的系统通知 |
| `system_recipient_user_id` | 个人系统通知频道所属用户；系统公告为空 |

`chat_messages` 的系统字段：

| 字段 | 说明 |
| --- | --- |
| `source` | `user` 或 `system` |
| `system_metadata.notificationEventId` | 对应 `notification_events.id` |
| `system_metadata.kind` / `stream` | 事件 kind 和 stream 的投影副本 |
| `system_metadata.targetType` / `targetId` / `targetHref` | 关联对象和跳转位置的投影副本 |
| `system_metadata.replyTargetType` / `replyTargetId` | 可回复消息评论目标的投影副本 |
| `system_metadata.metadata` | 展示和回复锚点辅助数据 |

`chat_push_deliveries` 只表达普通聊天消息的移动推送任务，不表达 realtime、消息完整性或已读：

| 字段 | 说明 |
| --- | --- |
| `message_id` / `recipient_user_id` | 每个消息和收件人唯一一条 push 任务 |
| `status` | 处理生命周期：`pending`、`processing`、`retry_scheduled`、`completed`、`dead_letter`；不描述用户是否收到或已读 |
| `outcome` | 终态结果：历史 push 为 `legacy_processed`；新任务为 `push_accepted` / `push_partially_accepted` / `push_rejected` / `no_push_device` / `push_disabled`；接收对象不适用为 `not_applicable`，技术失败耗尽重试为 `failed` |
| `target_count` / `success_count` / `failure_count` | 当前尝试观察到的设备请求数；不代表人数、已展示数或已读数 |
| `attempts` / `last_error` / `next_attempt_at` | push 失败诊断和有限指数退避；最多 12 次，耗尽后进入 `dead_letter` |
| `lease_expires_at` | 进程中断后的任务回收边界 |
| `completed_at` | `completed` 或 `dead_letter` 进入终态的时间，不等于用户收到、展示或已读时间 |

`status` 与 `outcome` 正交：前者只负责 worker 生命周期，后者只负责可观察的传输结论。没有在线订阅者、没有 push 设备、接收人已失效或消息不再可见都是已判定的终态，不做无意义重试；网络、推送服务或构造链路的技术错误才进入 `retry_scheduled`。领取写回以任务 `attempts` 作为 fencing token，过期 worker 不能覆盖新租约结果；最后一次尝试的租约过期时直接进入 `dead_letter`，不能因进程崩溃突破最大尝试次数。一个 push 任务覆盖该用户的全部当前设备：只要有设备请求被接受就进入终态并记录成功/失败计数，避免为了失败设备重试时重复推送给已成功设备。

`AppShell` 在 `AttentionState.count > 0` 时才展示侧边栏“待我处理”入口和移动端底部 `待办` 入口；这些入口只消费可处理聊天提醒、系统通知和业务提醒的派生结果。普通 GitHub/GitLab 工程动态和普通频道消息只保留在聊天入口及桌面 `badgeCount`。侧边栏通知项打开后会标记该通知已读，并提供通知全部已读来清理历史积压；用户在聊天里读到带 `notificationEventId` 的系统消息时，后端同步更新对应 `notification_receipts.read_at`，让“待我处理”和聊天阅读状态一起收敛。完整历史仍在聊天系统会话，业务处理仍跳转到 `notification_events.targetHref` 或聊天消息目标。

`/notifications` 前端路由只重定向到 `/chat/system/personalNotifications`，再由聊天页替换到普通系统频道 URL。

聊天附件上传进度、已传大小和上传速度都是前端临时展示状态，来源于浏览器 XHR `upload.onprogress` 事件和 Composer 草稿模型内的时间差派生；它们不写入 `chat_messages`、`chat_attachments` 或草稿持久化。若浏览器无法提供可计算长度，Composer 只显示不确定进度条、已传大小和“上传中”，不伪造百分比。

工作日志提交公告只在新增日志成功后创建，不在编辑或删除历史日志时创建；公告正文只包含提交人和日期，不复制目标/分类标题或完整日志正文，目标/分类标题只作为 `metadata` 兜底展示信息。系统会话可以用 `targetId` 按需读取工作日志 API 渲染引用卡片，有卡片时消息正文只保留“提交人发布了新的工作日志”这类短提示；卡片只是展示投影，不改变通知事件的数据保留边界。它与 `worklog.reminder` 的欠账提醒语义分离，不能作为日志是否补齐的事实源。

工作日志欠账强提醒不按 10 分钟创建新的 `worklog.reminder` 事件。10 分钟节奏只更新 `work_log_reminder_states.next_remind_at` 并通过 `worklog.reminder.required` / `worklog.reminder.resolved` SSE 控制全局弹窗；通知中心的 `worklog.reminder` 只是入口和历史提醒事实。`ORF_WORK_LOG_REMINDER_ENABLED=false` 时，调度器、状态接口和日志写入后的提醒重算都不产生弹窗提醒。

聊天系统消息是通知投递时的物化投影。修改动作文案或 `targetHref` 生成规则只影响新通知；历史 `chat_messages.body` 和 `system_metadata.targetHref` 必须通过 `npm run notifications:repair-links -- --apply` 统一修复，禁止在业务代码或文档里保留旧链接作为兼容事实源。

## 测试口径

- 后端流程测试必须验证关键业务动作会生成正确 `notification_events`、`notification_receipts`、`notification_deliveries`，并在聊天成功时生成 `chat_messages.source/system_metadata`。
- 评论测试必须覆盖 `@`、直接回复与反馈适配器参与者通知之间的收件人去重。
- API 测试必须验证系统公告可被当前作用域用户读取，个人系统通知不能读取别人的频道。
- API 测试必须验证系统消息和系统频道不能被普通用户编辑、删除、归档或改成员。
- 前端测试必须验证系统入口在聊天侧栏，打开后渲染普通聊天消息列表。
- 聊天消息发送、聊天 `@` 提及和聊天线程回复不得创建系统消息。
- 新增通知事件时，必须同步更新 `NotificationKind`、通知策略注册表、后端投递测试和本文件。

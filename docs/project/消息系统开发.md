# 消息系统开发

## 定位

消息系统是 ORF 的系统级收件箱，用来承接会阻塞流程推进的业务事件。在线横幅广播是实时通道上的独立展示能力：它可以复用同一个领域事件，但不等同于持久化消息收件人。

它不属于悬赏大厅、我的挑战、反馈或成员管理中的任一页面；业务模块只产生领域事件，消息系统负责把事件投递给接收人并维护已读状态。

消息不是跨客户端界面同步机制。跨客户端同步使用独立的读模型失效事件：后端业务 mutation 成功写入数据库后，广播哪些读模型失效；前端按当前用户权限重新拉取自己的读模型。

## 实时读模型失效

`orf.read-model.invalidated` 是 ORF 的跨客户端同步契约，只表达“哪些读模型失效”，不携带目标、申请、战利品、用户等业务快照。

| 字段 | 说明 |
| --- | --- |
| `models` | 失效的读模型，如 `taskManagement`、`bountyHall`、`users`、`permissions`、`notifications`、`settings` |
| `reason` | 失效原因，如 `objective.challenge.application.changed`、`task.changed`、`user.changed` |
| `target` | 可选的失效对象定位，只包含 `type` 和 `id` |
| `actorUserId` | 可选的触发用户，用于调试和后续去重策略 |

读模型失效事件按当前作用域广播给在线 active 用户。事件本身不泄露业务数据；客户端收到后仍通过 `/tasks`、`/bounties`、`/api/me/access`、`/api/users`、`/api/notifications` 或设置接口按自身权限读取数据。`/api/permissions` 只用于管理员权限配置管理。

`notification.created` 只负责消息收件箱和铃铛即时更新；`system.broadcast` 只负责横幅展示；二者都不能作为页面读模型同步的事实源。

## 通知判定原则

1. 只有成功写入业务状态的 mutation 才能创建消息；校验失败、权限失败、重复点击、并发失败和只读查询都不创建消息。
2. 消息用于提醒接收人处理跨角色、跨页面或阻塞流程推进的事件，不用于替代普通操作成功 Toast。
3. 触发人默认不接收自己触发的消息；如果触发人后续也需要处理，应优先用当前页面待办、跳转或 Toast 承接。
4. 接收人必须是当前默认作用域内 `active` 用户；`pending`、`rejected`、`disabled` 用户不接收系统内消息。
5. 所有消息必须带 `targetType`、`targetId` 和 `targetHref`，点击后进入能处理该事件的页面和对象锚点；当持久化记录只携带页面级 `targetHref` 时，前端按 `kind`、`targetId` 和 `metadata` 派生当前锚点。
6. 消息只保存事件事实和少量展示 metadata；业务真相仍以目标、指标、战利品、反馈、任务等原业务表为准。
7. 不因为“有人可能感兴趣”而广播消息；没有明确下一步动作的更新应进入页面时间线或审计日志，而不是系统消息。
8. 频繁编辑类操作默认不通知；只在对象被指派、进入新处理阶段、需要审核、需要确认或流程完成时通知。
9. 同一业务动作只生成一种主消息；如果多个角色都要处理，使用同一个事件 kind 分发给不同接收人，或拆成明确的后续待办事件。
10. 定时提醒、邮件和外部 IM 是独立能力；本文只定义 ORF 系统内消息规则。

## 即时聊天边界

聊天消息不进入系统消息收件箱。`chat.direct.created`、`chat.mention.created`、`chat.thread.updated` 不作为系统内消息事件创建 `notifications` 行；聊天提醒只使用聊天模块自己的未读事实源、实时事件、推送和本地通知。

聊天主消息未读仍以 `chat_channel_members.last_read_at`、`last_read_message_id` 和 `manually_unread` 为事实源；话题回复未读仍以 `chat_thread_follows.last_viewed_at` 为事实源。右上角系统消息铃铛只展示 `notifications` 中的业务消息未读数，不能把聊天未读或聊天推送状态并入系统消息计数。

历史上已经写入 `notifications` 的聊天类记录属于旧数据兼容范围，不再作为当前系统消息收件箱读模型的一部分；当前接口读取、计数、标记已读和清空消息时应排除 `target_type = 'chat'` 的旧记录，不做隐式数据删除。

聊天归档属于 ORF 之外的本机私有服务能力。它不写入 `notifications`，不写入 `comment_messages`，也不反向驱动 ORF 业务流程；ORF 仓库不再维护归档表、同步任务、查看页或后端接口。

### 任务、子任务和评论

| 规则 | 触发动作 | 是否通知 | 接收人 | 建议事件 | 跳转 |
| --- | --- | --- | --- | --- | --- |
| WORK-01 | 创建任务并指定执行人 | 需要 | 任务执行人 | `task.assigned` | `/tasks#action:{taskId}` |
| WORK-02 | 修改任务标题、状态、完成状态、排序 | 不通知 | 无 | 无 | 无 |
| WORK-03 | 新增、修改、完成或移动子任务 | 不通知 | 无 | 无 | 无 |
| WORK-04 | 新建顶层评论 | 不通知 | 无 | 无 | 无 |
| WORK-05 | 回复某条评论 | 需要 | 被回复评论作者 | `comment.reply.created` | `/tasks#{objective|bounty|action|subAction}:{targetId}` |
| WORK-06 | 评论被解决或重新打开 | 需要 | 评论线程创建人 | `comment.thread.status.changed` | `/tasks#{objective|bounty|action|subAction}:{targetId}` |
| WORK-07 | 新建评论或回复时 `@` 提及成员 | 需要 | 被提及 active 用户 | `comment.mention.created` | `/tasks#{objective|bounty|action|subAction}:{targetId}` |

WORK-04 不通知是因为评论可能高频出现；没有 `@` 提及或直接回复时，评论只作为协作记录。

WORK-07 的事实来源不是普通 `@姓名` 文本，而是评论正文中的稳定 token：`@[显示名](orf-user:{userId})`。后端只认可 token 里的 `userId`，并按当前评论目标所在 team scope 重新校验用户是否存在、是否 `active`、是否在当前作用域内。普通 `@文本` 只按普通文字保存和展示，不产生消息。编辑历史评论第一版不补发新增提及通知，避免用户通过反复编辑刷通知；如后续需要，单独定义 `comment.mention.updated` 或编辑去重策略。

`comment.mention.created` 的去重规则：

1. 同一条评论里多次提及同一用户只生成一条消息。
2. 提及触发人自己不生成消息。
3. 被提及用户不存在、不在当前作用域、不是 `active` 时不生成消息。
4. 同一评论同时回复某人并 `@` 同一人时，第一版只发送 `comment.mention.created`，避免一个动作产生两条相似消息。

## 明确不通知的通用情况

1. 当前用户对自己动作的成功反馈，只用 Toast 或页面状态。
2. 纯读取、筛选、搜索、排序、展开、收起、标记消息已读。
3. 编辑标题、描述、排序、信心、任务完成状态这类高频小改动。
4. 后端返回 `400`、`403`、`404`、`409` 或并发保护失败的请求。
5. 接收人不存在、不是 active、或不在当前默认作用域内。
6. 需要通知的对象已经因为状态变化不可访问时，不创建系统内消息，改用外部渠道或页面状态。

## 数据模型

消息持久化在 `notifications` 表：

| 字段 | 说明 |
| --- | --- |
| `team_id` | 默认作用域隔离 |
| `recipient_user_id` | 接收人 |
| `actor_user_id` / `actor_name` | 触发人 |
| `kind` | 事件类型 |
| `title` / `body` | 展示文案 |
| `target_type` / `target_id` / `target_href` | 关联对象和跳转位置 |
| `read_at` | 已读时间，空值表示未读 |
| `metadata` | 少量展示辅助数据，不承载业务真相 |

业务真相仍在原业务表里，例如 `Objective.challengeApplications`、`Objective.assignedChallengers`、`objectiveLoot`。消息不能反向驱动业务状态。

## 后端边界

| 文件 | 职责 |
| --- | --- |
| `server/repositories/notificationRepository.ts` | 消息创建、查询、已读状态 |
| `server/repositories/orfRepository.ts` | 在业务 mutation 成功后调用消息投递 |
| `server/realtime/realtimeEventBus.ts` | 传输无关的实时事件分发，支持按用户投递通知、按作用域广播横幅、按作用域广播读模型失效和客户端更新唤醒事件 |
| `server/routes/notificationRoutes.ts` | `/api/notifications` 读取、已读、删除接口和当前用户作用域校验 |
| `server/app.ts` | 注册消息路由和 `/api/events` 实时事件入口 |
| `server/db/schema.ts` / `drizzle/*` | `notifications` 表结构 |

接口：

| 接口 | 用途 |
| --- | --- |
| `GET /api/notifications` | 当前用户消息列表和未读数 |
| `GET /api/events` | 已登录 active 用户的 SSE 实时事件流；`notification.created` 按用户投递消息，`system.broadcast` 按作用域投递横幅广播，`orf.read-model.invalidated` 按作用域投递读模型失效，`client.update.available` 按作用域唤醒客户端更新检查 |
| `PATCH /api/notifications/:notificationId/read` | 标记单条消息已读 |
| `PATCH /api/notifications/read-all` | 标记当前用户全部消息已读 |
| `POST /api/notifications/bulk-delete` | 删除当前用户勾选的消息收件箱记录 |
| `DELETE /api/notifications` | 清空当前用户当前作用域下的全部消息收件箱记录 |

所有读取和写入都按当前登录用户和默认作用域收敛。用户不能读取、标记或删除别人的消息。消息删除是当前用户当前作用域收件箱记录的硬删，不删除目标、指标、挑战申请、战利品、评论等业务事实；被删除消息不可恢复，后续同一业务对象的真实状态仍从原业务表读取。清空全部必须作用于当前用户当前作用域下的全部消息记录，不只作用于当前前端已加载的最近列表。

`@` 提及不新增消息表结构。评论正文 token 提供可恢复的提及位置和 `userId`；`notifications.metadata` 保存 `commentThreadId`、`commentMessageId`、`targetTitle` 和 `mentionedUserIds`，只用于展示和跳转辅助，不反向驱动评论业务状态。

消息入口放在顶部栏，不作为侧边栏一级导航。侧边栏保留主要业务空间；消息是横切状态入口。

完整消息页采用收件箱工作台结构：顶部工具条负责筛选、全部已读、勾选删除和清空；消息列表负责展示、勾选和跳转；危险删除动作必须二次确认。页面筛选和勾选只属于临时 UI 状态，不进入消息事实源。

`/tasks` 和 `/bounties` 的对象锚点只负责定位展示，不承载业务状态。挑战工作台识别 `objective`、`bounty`、`action`、`subAction` 锚点；悬赏大厅识别 `objective` 锚点。筛选条件隐藏目标时，目标锚点优先清空当前页面筛选并滚动到对应行。

客户端更新不进入系统消息收件箱。`client.update.available` 只唤醒运行中客户端重新检查 GitHub Release，兼容旧客户端的 `system.broadcast` 只展示在线横幅；二者都不写入 `notifications`，也不作为业务读模型刷新事实源。

## 测试口径

- 后端流程测试必须验证关键业务动作会生成正确接收人的消息。
- 后端流程测试必须验证关键业务 mutation 会广播对应的 `orf.read-model.invalidated`，且事件不携带业务快照。
- API 测试必须验证消息按当前用户隔离，不能读取、标记或删除别人的消息。
- 前端静态测试必须验证消息入口在顶部栏，不回到侧边栏主导航。
- 聊天消息发送、聊天 `@` 提及和聊天线程回复不得创建系统内消息；聊天未读只通过聊天读模型和推送/本地提醒验证。
- 新增通知事件时，必须同步更新 `NotificationKind`、后端投递测试、实时事件处理和通知中心前端 fixture；新增公共横幅时还必须定义对应 `system.broadcast` payload 和队列展示规则。
- 新增会改变页面读模型的 mutation 时，必须同步声明失效的 `models`；不能复用 `notification.created` 或 `system.broadcast` 触发页面刷新。
- 真实流程测试扩展时，应验证申请、征召、接受征召、战利品提交和结算后对应角色能看到未读消息并跳转到关联页面。

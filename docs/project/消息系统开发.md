# 消息系统开发

## 定位

系统消息是聊天里的系统会话，不再是独立通知中心。最终用户入口统一叫“聊天”；普通频道、私信和系统会话共享聊天页面壳，但事实源互不混用。

业务模块只发布通知事件，通知模块负责按策略投递到系统会话并维护个人已读状态。聊天页面只呈现系统会话、打开关联对象和承接回复入口，不定义业务事件是否通知。

GitLab push、merge request、pipeline 等工程动态进入对应 ORF 普通项目频道，不进入 `notification_events`；只有被建模为 ORF 内部任务、反馈或待办后才发布系统会话事件。

在线横幅广播是实时展示能力，可以复用同一个领域动作，但不等同于持久化通知事件；页面数据同步仍通过 `orf.read-model.invalidated` 完成。

## 状态链和事实源

1. 业务 mutation 成功写入原业务表。
2. 业务模块调用 `publishNotificationEvent` 发布通知事件。
3. 通知策略注册表决定事件进入 `teamAnnouncement` 还是 `personalNotification`。
4. `notification_events` 保存唯一事件事实。
5. `notification_receipts` 保存每个接收人的投递和已读状态。
6. `/api/chat/system-conversations` 把事件和收据投影成聊天里的系统会话。
7. 用户回复系统消息时，后端写入目标业务评论；通知事件本身不保存回复。

唯一事实源：

| 事实 | 权威来源 |
| --- | --- |
| 业务状态 | 目标、指标、任务、反馈、评论、工作日志等原业务表 |
| 系统消息事件 | `notification_events` |
| 当前用户已读/未读 | `notification_receipts.read_at` |
| 系统会话列表和消息流 | `notification_events` + 当前用户 `notification_receipts` 的投影 |
| 普通聊天未读 | `chat_channel_members`、`chat_thread_follows` |

系统消息没有“删除”“清空”语义；注意力状态只通过已读/未读管理。旧 `/api/notifications/bulk-delete` 和 `DELETE /api/notifications` 只保留为兼容保护，返回 `410`。

## 系统会话

当前固定两个系统会话：

| 会话 | stream | 可见范围 | 典型事件 |
| --- | --- | --- | --- |
| 系统公告 | `teamAnnouncement` | 当前作用域 active 用户都可查看历史；只有被投递的人产生未读 | `objective.published` |
| 我的系统通知 | `personalNotification` | 当前用户自己的收据 | 申请、征召、战利品、反馈、评论、工作日志提醒 |

`系统公告` 是团队公共事件窗口；`我的系统通知` 是个人待处理窗口。二者都是聊天页面里的会话，不是单独页面。

系统消息可回复的条件由事件上的 `replyTargetType` / `replyTargetId` 决定。回复写入对应目标的评论：

- 反馈通知回复到反馈评论。
- 目标/指标/任务/子任务相关通知回复到对应工作对象评论。
- 评论提及、评论回复和评论状态变更优先携带原评论消息锚点；用户回复时会进入同一评论目标。
- 工作日志提醒没有业务评论目标，不支持回复。

## 实时读模型失效

`orf.read-model.invalidated` 只表达“哪些读模型失效”，不携带目标、申请、战利品、用户等业务快照。

| 字段 | 说明 |
| --- | --- |
| `models` | 失效的读模型，如 `taskManagement`、`bountyHall`、`users`、`permissions`、`notifications`、`settings` |
| `reason` | 失效原因，如 `objective.challenge.application.changed`、`task.changed`、`notification.changed` |
| `target` | 可选的失效对象定位，只包含 `type` 和 `id` |
| `actorUserId` | 可选的触发用户，用于调试和后续去重策略 |

客户端收到失效后按自身权限重新拉取读模型。系统会话刷新 `/api/chat/system-conversations`；旧角标兼容仍可读取 `/api/notifications`。

`notification.created` 只负责当前接收人的系统消息即时插入；`system.broadcast` 只负责横幅展示；二者都不能反向定义页面业务状态。

## 通知判定原则

1. 只有成功写入业务状态的 mutation 才能创建通知事件。
2. 校验失败、权限失败、重复点击、并发失败和只读查询都不创建通知事件。
3. 触发人默认不接收自己的个人通知；系统公告事件仍可被触发人在公告窗口看到历史，但不产生未读。
4. 接收人必须是当前默认作用域内 `active` 用户。
5. 所有通知必须带 `targetType`、`targetId` 和 `targetHref`。
6. 可回复通知必须带 `replyTargetType` 和 `replyTargetId`，或能由通知策略从目标/metadata 推导。
7. 通知只保存事件事实和展示辅助 metadata，不承载业务真相。
8. 不因为“有人可能感兴趣”广播通知；没有明确下一步动作的更新应进入页面时间线、活动流或审计日志。
9. 高频编辑默认不通知；对象被指派、进入新处理阶段、需要审核、需要确认或流程完成时才通知。
10. 同一业务动作按主语义只生成一种通知；提及、直接回复和参与者通知需要去重。

## 即时聊天边界

普通聊天消息不进入系统消息事件。`chat.message.created`、聊天 `@` 提及和聊天话题回复只使用聊天模块自己的未读事实源、实时事件、推送和本地通知。

聊天主消息未读事实源仍是 `chat_channel_members.last_read_at`、`last_read_message_id` 和 `manually_unread`；话题回复未读事实源仍是 `chat_thread_follows.last_viewed_at`。

系统会话显示在聊天页面，但不写入 `chat_channels`、`chat_messages` 或 `chat_channel_members`。系统会话未读来自 `notification_receipts`，不能并入普通频道已读状态机。

历史 `notifications` 表只作为迁移来源和旧接口兼容层；当前新通知写入 `notification_events` 和 `notification_receipts`。

| `comment.mention.created` | `personalNotification` | 评论正文提及成员 | 被提及 active 成员 | 原评论目标 | 目标评论位置 |

| `comment.thread.status.changed` | `personalNotification` | 评论被解决或重新打开 | 评论线程创建人，排除触发人 | 原评论目标 | 目标评论位置 |
| `worklog.reminder` | `personalNotification` | 定时工作日志提醒 | 未填写当日工作日志的相关 active 用户 | 无 | `/work-logs?date={date}` |

## 评论通知去重

同一条评论可能同时命中 `@`、直接回复和反馈参与者通知。去重顺序：

1. `comment.mention.created` 优先。
2. `comment.reply.created` 排除已被 `@` 的用户。
3. `feedback.commented` 排除触发人、已被 `@` 的用户和直接回复接收人。

`@` 的事实来源是正文中的稳定 token：`@[显示名](orf-user:{userId})`。后端只认可 token 里的 `userId`，并按评论目标所在作用域重新校验用户是否存在、是否 active。

## 明确不通知的通用情况

1. 当前用户对自己动作的成功反馈，只用 Toast 或页面状态。
2. 纯读取、筛选、搜索、排序、展开、收起、标记已读/未读。
3. 编辑标题、描述、排序、信心、任务完成状态这类高频小改动。
4. 后端返回 `400`、`403`、`404`、`409` 或并发保护失败的请求。
5. 接收人不存在、不是 active、或不在当前默认作用域内。
6. 需要通知的对象已经因为状态变化不可访问时，不创建系统内消息，改用外部渠道或页面状态。

## 数据模型

`notification_events` 保存事件事实：

| 字段 | 说明 |
| --- | --- |
| `team_id` | 默认作用域隔离 |
| `stream` | 数据库枚举 `notification_stream`，只能是 `teamAnnouncement` 或 `personalNotification` |
| `actor_user_id` / `actor_name` | 触发人 |
| `kind` | 事件类型 |
| `title` / `body` | 展示文案 |
| `target_type` / `target_id` / `target_href` | 关联对象和跳转位置 |
| `reply_target_type` / `reply_target_id` | 可回复消息的评论目标 |
| `created_at` | 事件发生时间 |
| `metadata` | 展示和回复锚点辅助数据，不承载业务真相 |

`notification_receipts` 保存个人投递和已读：

| 字段 | 说明 |
| --- | --- |
| `event_id` | 通知事件 |
| `recipient_user_id` | 接收人 |
| `delivered_at` | 投递时间 |
| `read_at` | 已读时间；空值表示未读 |

`notifications` 是旧表。迁移 `0054_notification_events_and_receipts.sql` 会把非聊天旧通知迁入新事件/收据表；新代码不再写入旧表。

## 后端边界

| 模块 | 职责 |
| --- | --- |
| `server/notifications/policies/registry.ts` | 注册每种 `NotificationKind` 的 stream 和回复目标推导规则 |
| `server/notifications/publisher.ts` | 统一构造通知事件，按策略补齐 stream 和回复目标 |
| `server/repositories/notificationRepository.ts` | 事件/收据写入、旧 `/api/notifications` 兼容读取、已读/未读 |
| `server/repositories/systemConversationRepository.ts` | 把事件/收据投影成聊天系统会话，并把系统消息回复转成业务评论 |
| `server/routes/systemConversationRoutes.ts` | `/api/chat/system-conversations` 系统会话 API |
| `server/routes/notificationRoutes.ts` | 旧通知兼容 API；删除和清空返回 `410` |
| `server/realtime/realtimeEventBus.ts` | 按用户投递 `notification.created`，按作用域广播横幅和读模型失效 |
| `server/db/schema.ts` / `drizzle/*` | `notification_events`、`notification_receipts`、旧表迁移 |

接口：

| 接口 | 用途 |
| --- | --- |
| `GET /api/chat/system-conversations` | 系统会话摘要 |
| `GET /api/chat/system-conversations/:conversationId/messages` | 当前系统会话消息流 |
| `PATCH /api/chat/system-conversations/:conversationId/messages/:messageId/read` | 单条系统消息已读 |
| `PATCH /api/chat/system-conversations/:conversationId/messages/:messageId/unread` | 单条系统消息未读 |
| `PATCH /api/chat/system-conversations/:conversationId/read-all` | 当前系统会话全部已读 |
| `POST /api/chat/system-conversations/:conversationId/messages/:messageId/replies` | 回复系统消息，写入目标评论 |
| `GET /api/notifications` | 旧兼容：当前用户个人收据列表和未读数 |
| `PATCH /api/notifications/:notificationId/read` | 旧兼容：单条已读 |
| `PATCH /api/notifications/:notificationId/unread` | 旧兼容：单条未读 |
| `PATCH /api/notifications/read-all` | 旧兼容：全部已读 |
| `POST /api/notifications/bulk-delete` | 旧兼容保护：返回 `410` |
| `DELETE /api/notifications` | 旧兼容保护：返回 `410` |

## 前端边界

| 模块 | 职责 |
| --- | --- |
| `src/pages/ChatPage.tsx` | 组合普通聊天频道和系统会话；识别 `/chat/system/:systemConversationId` |
| `src/features/chat/ChatSidebar.tsx` | 展示系统会话分组、普通频道、私有频道和私信 |
| `src/features/chat/SystemConversationPanel.tsx` | 展示系统消息、已读/未读、打开目标和回复评论 |
| `src/state/apiClient.ts` | 系统会话 API client；旧通知 API 只保留读取 unread 角标 |
| `src/state/OrfProvider.tsx` | 保留系统消息 unread 角标状态和实时通知合并；不暴露旧通知列表、删除、清空或已读操作 |
| `src/config/navigation.ts` | 只保留“聊天”入口；不再提供单独“消息”页面 |

系统会话面板不复用普通聊天消息组件，不展示删除、保存、固定、表情、聊天线程等聊天专属能力。

## 测试口径

- 后端流程测试必须验证关键业务动作会生成正确事件、stream、回复目标和接收人收据。
- 评论测试必须覆盖 `@`、直接回复、反馈参与者三类通知的去重。
- API 测试必须验证系统公告可被当前作用域用户读取，个人通知不能读取别人的收据。
- API 测试必须验证系统消息删除和清空返回 `410`。
- 前端静态测试必须验证独立通知页和顶部铃铛不再出现，系统消息入口在聊天侧栏。
- 聊天消息发送、聊天 `@` 提及和聊天线程回复不得创建系统通知事件。
- 新增通知事件时，必须同步更新 `NotificationKind`、通知策略注册表、后端投递测试和系统会话前端展示口径。
- 新增会改变页面读模型的 mutation 时，必须同步声明失效的 `models`；不能复用 `notification.created` 或 `system.broadcast` 触发页面刷新。

# ORF 生产发布执行手册

用户说“发布新版本”时，按以下顺序执行：

```text
提交代码 → 构建生产不可变包和客户端私有 Draft
→ 切换并重启生产 Web/后端/网关 → 验收
→ 公开客户端并写入 ORF 主更新源 → 广播更新
```

不变量：生产入口验收通过之前，客户端版本只能存在于私有 GitHub Draft，不能公开 Release、不能写入 ORF 主更新源、不能广播。否则仍在运行的客户端可能先发现新版本，安装重启后却继续加载旧生产 Web。

## 1. 连接与输入

生产机：

```bash
ssh -p 6322 xue@199.199.199.8
```

每次先确定：

```text
VERSION=根 package.json 的版本，例如 0.0.121
TAG=v${VERSION}
NOTES=本次中文更新说明
FEATURE_MARKER=本次网页改动的稳定 JS 标识；没有网页改动时留空
```

源码可以在 `.13`、`.8` 或其他机器。源码所在机器负责提交和构建生产运行包；GitHub Actions 固定负责构建 Win11 安装器和 Android APK。

## 2. 提交与全部产物预构建

1. 在源码机更新根 `package.json` 版本，运行：

   ```bash
   npm run client:sync-versions
   ```

   Android `versionCode` 由可见版本按 `major × 1,000,000 + minor × 1,000 + patch` 唯一换算，每段必须小于 `1000`；例如 `0.1.0` 对应 `1000`。该内部版本必须严格高于已发布 APK，确保固定签名客户端能够覆盖升级。

2. 完成本次改动需要的构建、类型检查和测试；检查工作区、提交范围后，用显式路径提交并推送。

3. 在干净提交上构建生产不可变包：

   ```bash
   npm run build:release
   ```

   记录 `.artifacts/releases/orf-<release-id>.tar.gz`、同名 SHA-256、`release.json` 中的版本和提交哈希。后续生产切换必须使用这一份已验证产物，不能在客户端构建后临时重打脏包。

4. 构建客户端私有 Draft：

   ```bash
   npm run release:clients -- --tag "$TAG" --notes "$NOTES" --watch
   ```

5. 确认 GitHub Release 仍为 `isDraft: true`，且含两个文件：

   ```text
   ORF-${VERSION}-win11-x64-setup.exe
   ORF-v${VERSION}-android.apk
   ```

   此时不得执行 `--publish-staged` 或 `--broadcast-only`。Draft 资产没有写入 ORF 主更新源，普通客户端无法发现该版本。

## 3. 切换生产 Web 和后端

1. 若源码机不是 `.8`，把第 2 节生成的 `.artifacts/releases/orf-<release-id>.tar.gz` 和同名 SHA-256 文件通过 SSH 标准流式传到 `.8`；不要使用 SCP。

2. 在 `.8` 上使用完整激活脚本：

   ```bash
   cd /home/xue/code/ORF
   deploy/current-host/activate-release.sh /path/to/orf-<release-id>.tar.gz
   ```

   脚本必须完成归档校验、迁移、`releases/current` 原子切换、生产后端重启、`public-gateway` 强制重建，以及两层健康检查。不能用 `orf restart` 代替生产激活；`orf restart` 只恢复当前已经激活的生产 release，不会校验新归档、执行迁移或切换 `releases/current`。

   当前宿主优先使用 `orf-backend-production.service`。如果 WSL/Codex 环境没有 user systemd bus 或没有该 user unit，激活脚本必须自动走 detached production fallback；fallback 需要使用 Linux 临时目录，例如 `TMPDIR=/tmp`，不能继承 Windows 盘上的 `TMPDIR`，否则 `tsx` IPC 可能报 `ENOTSUP`。

3. 若需要手工核对，确认：

   ```text
   releases/current  → 新目录
   releases/previous → 切换前目录
   ```

   ```bash
   systemctl --user show orf-backend-production.service --property=ActiveState,SubState,MainPID,WorkingDirectory
   cat ~/.local/share/orf-production/data/backend-production.manual.pid
   docker inspect orf-public-gateway-1
   ```

   user systemd 可用时核对 systemd 的 `MainPID`；fallback 模式下核对
   `backend-production.manual.pid`。无论哪种方式，都必须确认后端进程
   `/proc/<pid>/cwd` 解析到 `releases/current` 指向的新 release，命令行为
   `server.mjs` 且不是 `tsx`。`public-gateway` 必须重建，因为 Docker 在创建容器时解析 `releases/current/web` 的软链接；只重启后端不会切换公网 Web。

## 4. 生产验收

在 `.8` 上确认：

```bash
curl --fail --silent --show-error http://127.0.0.1:8787/health
curl --fail --silent --show-error --insecure https://orf-xueyu.duckdns.org:8443/ -o /tmp/orf-release-index.html
docker ps --filter name=orf-public-gateway-1
```

必须同时核对：

1. `releases/current/release.json` 的 `applicationVersion` 等于 `VERSION`。
2. `gitCommit` 等于 `TAG` 指向的提交且 `gitDirty=false`。
3. 后端健康。
4. 公网网关健康。
5. 公网首页字节与 `releases/current/web/index.html` 完全一致。
6. 后端进程运行目录解析到当前 release，命令为生产编译产物 `server.mjs`。
7. 如果 `FEATURE_MARKER` 不为空，从公网新 JS/CSS 中确认标识存在。

任一项失败都不能公开客户端版本，也不能写主更新源。

## 5. 公开客户端并写入主更新源

生产验收通过后，在 `.8` 的干净工作区运行：

```bash
npm run release:clients -- --tag "$TAG" --publish-staged
```

该命令会再次自动校验当前生产 release 的版本、提交、后端健康、公网健康和首页字节，然后按顺序：

1. 把 GitHub Draft 改为公开 Release。
2. 下载并校验 Win11/Android 资产。
3. 上传两个客户端文件到 ORF 主更新源。
4. 最后写入该版本发布清单。

确认 GitHub Release 已公开且含两个文件，并检查 `ORF_CLIENT_UPDATE_ASSET_DIR/${VERSION}` 中两个文件大小正确。主更新源完成条件仍是：两个上传成功、文件大小正确、发布清单写入成功。

普通功能发布不必完整从公网下载两个大安装包。仅当客户端下载路由、nginx、域名、TLS 或访问控制变更/排障时，才做公网大文件下载检查。

## 6. 广播更新

公开和主更新源同步都成功后再运行：

```bash
npm run release:clients -- --tag "$TAG" --broadcast-only
```

广播接口为：

```text
POST /api/client-updates/broadcast-release
{"version":"${VERSION}"}
```

记录版本、tag、提交、私有 Draft 构建结果、GitHub Release、两个 SHA-256、生产 release id 和广播返回的 SSE 即时触达数。

客户端进程不会因为远端 Web 切换而自动刷新已经加载的 SPA。上述顺序保证用户收到客户端版本后，安装重启加载的一定是已验收的新生产 Web；已经打开且不更新客户端的用户会在下次完整重启客户端时加载新 Web。

## 7. 失败处理

- 客户端 Draft 构建失败：停止，不切生产、不公开 Release、不写主更新源、不广播。
- 生产不可变包构建或 SHA-256 校验失败：停止，不切生产、不公开客户端。
- 后端健康、8443 首页、新版 JS 或首页字节验收失败：切回 `releases/previous`，重启后端并重建 `public-gateway`；Draft 保持私有。
- `--publish-staged` 在公开 GitHub Release 后同步主更新源失败：修复原因后原命令可幂等重试；未写入发布清单前不得广播。
- 广播失败：版本仍可由客户端启动或定期检查发现；记录错误后单独补发。

发布流程禁止恢复为“先写主更新源、后切生产”。

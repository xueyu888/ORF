# ORF 生产发布执行手册

用户说“发布新版本”时，按以下顺序执行：

```text
提交代码 → GitHub 构建 exe/apk → 写入 ORF 主更新源
→ 切换生产 Web/后端/网关 → 验收 → 广播更新
```

## 1. 连接与输入

生产机：

```bash
ssh -p 6322 xue@199.199.199.8
```

每次先确定：

```text
VERSION=根 package.json 的版本，例如 0.0.121
TAG=v${VERSION}
NOTES=本次中文更新说明
FEATURE_MARKER=本次网页改动的稳定 JS 标识；没有网页改动时留空
```

源码可以在 `.13`、`.8` 或其他机器。源码所在机器负责提交和构建生产运行包；GitHub Actions 固定负责构建 Win11 安装器和 Android APK。

## 2. 提交与客户端包

1. 在源码机更新根 `package.json` 版本，运行：

   ```bash
   npm run client:sync-versions
   ```

2. 完成本次改动需要的构建、类型检查和测试；检查工作区、提交范围后，用显式路径提交并推送。

3. 发布客户端包：

   ```bash
   npm run release:clients -- --tag "$TAG" --notes "$NOTES" --watch --no-broadcast
   ```

4. 确认 GitHub Release 已发布且含两个文件：

   ```text
   ORF-${VERSION}-win11-x64-setup.exe
   ORF-v${VERSION}-android.apk
   ```

5. 在能同时访问 GitHub 与 `.8` 的发布控制机下载这两个文件，计算 SHA-256。

   - 如果控制机不是 `.8`，通过 SSH 标准流式传输到 `.8`；不要使用 SCP。
   - 在 `.8` 再算一次 SHA-256，两个结果必须一致。
   - `.8` 从 GitHub 下载卡住时，改由 `.13` 下载再传入 `.8`。

## 3. 写入 ORF 主更新源

在 `.8` 上：

1. 读取 `/home/xue/.config/orf/orf.env`。
2. 向本机发布接口上传 Win11 安装器，确认 HTTP 200。
3. 上传 Android APK，确认 HTTP 200。
4. 检查 `ORF_CLIENT_UPDATE_ASSET_DIR/${VERSION}` 中两个文件大小正确。
5. 最后写入该版本发布清单，确认 HTTP 200。

主更新源完成条件：两个上传成功、文件大小正确、发布清单写入成功。

普通功能发布不必完整从公网下载两个大安装包。仅当客户端下载路由、nginx、域名、TLS 或访问控制变更/排障时，才做公网大文件下载检查。

## 4. 切换生产 Web 和后端

1. 在源码机运行：

   ```bash
   npm run build:release
   ```

2. 若源码机不是 `.8`，把 `.artifacts/releases/orf-<release-id>.tar.gz` 和同名 SHA-256 文件通过 SSH 流式传到 `.8`。

3. 在 `.8` 上：校验归档 SHA-256、`release.json` 中的版本和提交哈希；解压到新的不可变 `releases/<release-id>` 目录。

4. 原子切换：

   ```text
   releases/current  → 新目录
   releases/previous → 切换前目录
   ```

5. 重启后端并确认状态：

   ```bash
   systemctl --user restart orf-backend-production.service
   systemctl --user show orf-backend-production.service --property=ActiveState,SubState,MainPID,WorkingDirectory
   ```

6. 重建公网网关。当前正确的编排目录是 `/home/xue/code/ORF`；执行前仍先确认它有 `ory/.runtime/ory.env`。

   ```bash
   cd /home/xue/code/ORF
   ORF_WEB_RELEASE_DIR=/home/xue/.local/share/orf-production/releases/current/web \
     docker compose -f docker-compose.ory.yml -f docker-compose.minio.yml -f docker-compose.public.yml \
     up -d --no-deps --force-recreate public-gateway
   ```

## 5. 验收与广播

在 `.8` 上确认：

```bash
curl --fail --silent --show-error http://127.0.0.1:8787/health
curl --fail --silent --show-error --insecure https://orf-xueyu.duckdns.org:8443/ -o /tmp/orf-release-index.html
docker ps --filter name=orf-public-gateway-1
```

如果 `FEATURE_MARKER` 不为空：从新发布目录找到包含该标识的 JS 文件，再从 8443 拉取同一个文件并确认标识存在。

验收通过后，使用 `.8` 上配置的广播接口调用：

```text
POST /api/client-updates/broadcast-release
{"version":"${VERSION}"}
```

记录版本、tag、提交、GitHub Release、两个 SHA-256、生产 release id 和广播返回的 SSE 即时触达数。

## 6. 失败处理

- GitHub Actions 失败：停止，不写主更新源、不切生产目录、不广播。
- 文件 SHA-256 不一致：重新传输，不写发布清单。
- 主更新源写入失败：停止，不广播。
- 后端健康、8443 首页或新版 JS 验收失败：切回 `releases/previous`，重启后端并重建 `public-gateway`。
- 广播失败：版本仍可由客户端启动或定期检查发现；记录错误后单独补发。

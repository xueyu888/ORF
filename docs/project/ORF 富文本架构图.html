修复前的问题

  • 评论和反馈直接把 Markdown body 塞进编辑框。
  • 用户会看到 orf-user、orf-attachment 这种系统语言。
  • 新建反馈用 body.includes(...) 判断 pending 附件引用。
  • 附件缺失兜底还可能把原 token 渲染出来。

修复后的样子

  • 页面只拿 Draft，不直接解析 token。
  • 用户编辑区只显示 @名字、附件名、普通 Markdown。
  • 保存时由 Draft 模型统一序列化成后端 body。
  • 展示、通知、搜索预览都通过统一投影，不泄漏系统 token。
模块 只负责什么 不负责什么
Tokens ORF 内部 token 的编码、解析、匹配。 不处理 UI，不决定评论或聊天业务规则。
Draft 存储态 body 和编辑态 text/ref 的互转，以及删除、修改后的引用 reconcile。 不上传文件，不发请求，不渲染页面布局。
DraftEditor 把 Draft 接到输入体验，保证用户看不到 token。 不定义 token 语法，不决定后端存储。
Adapter 聊天、评论、反馈各自的业务差异和副作用边界。 不复制 token 正则，不维护另一套 Draft 模型。
Backend 保存 body，解析 token，发送通知，绑定附件。 不关心前端编辑器如何隐藏 token。

一句话结论：token 是系统语言，Draft 是编辑语言，Viewer 是展示语言，Adapter 是业务语言，body 是存储语言。 当前 issue 的根因就是评论和反馈缺少 Draft 这一层。

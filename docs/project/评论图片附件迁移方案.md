# 评论图片附件迁移方案

本文档记录 ORF 评论从纯文本扩展到图片附件的历史迁移方案。当前评论附件已经扩展为通用文件附件；具体后端契约见 [评论组件 - 后端.md](../backend/评论组件%20-%20后端.md)，对象存储契约见 [对象存储 - 后端.md](../backend/对象存储%20-%20后端.md)，前端交互见 [评论组件 - 前端.md](../frontend/评论组件%20-%20前端.md)。

## 1. 当前状态

1. 评论正文保存轻量文本和 `orf-attachment:{attachmentId}` 引用。
2. `CommentMessage` 返回 `attachments: CommentAttachment[]`。
3. PostgreSQL 保存 `comment_attachments` 元数据。
4. 附件文件进入 S3-compatible 对象存储；本地开发和本地服务器使用 MinIO。
5. 浏览器通过 ORF 后端鉴权读取附件，不直接访问 bucket。
6. 当前版本支持通用文件附件：图片内联展示，Markdown/PDF/安全文本可打开预览，其他文件只能下载。

## 2. 目标架构

1. 附件文件进入 S3-compatible 对象存储；本地开发和本地服务器先用 MinIO。
2. PostgreSQL 保存附件元数据、评论绑定关系和权限边界。
3. 评论正文只保存 `orf-attachment:{attachmentId}` 这种稳定引用，不保存 base64、对象存储 URL 或 public URL。
4. 浏览器读取图片必须经过 ORF 后端鉴权，bucket 保持私有。
5. 后端通过统一 `ObjectStorage` 适配层访问对象存储，评论业务不直接依赖 MinIO SDK。

## 3. 第一阶段：环境和文档

1. 增加 `docker-compose.minio.yml`，提供本地 MinIO 和 bucket 初始化。
2. 增加 `OBJECT_STORAGE_*` 和 `MINIO_*` 环境变量说明。
3. 补齐评论前端、评论后端、对象存储和迁移方案文档。

验收：

```bash
docker compose -f docker-compose.minio.yml config
npm run storage:dev
curl -f http://127.0.0.1:9000/minio/health/live
```

## 4. 第二阶段：后端能力

1. 新增对象存储配置读取和 `ObjectStorage` 适配层。
2. 新增 `comment_attachments` 表和 Drizzle migration。
3. 新增附件上传接口和附件内容读取接口。
4. 创建或编辑评论时解析正文 token，绑定或解绑附件。
5. 删除评论时同步删除附件元数据和对象。
6. 增加 pending 附件过期清理函数，后续可接入定时任务。

验收：

1. 上传权限和读取权限与评论目标对象一致。
2. 超大文件、跨对象引用都会被拒绝；Markdown/PDF/安全文本允许预览，其他非图片文件按下载处理。
3. 评论删除或编辑移除图片后，对象存储没有遗留文件。

## 5. 第三阶段：前端能力

1. `CommentComposer` 支持粘贴附件上传。
2. `CommentComposer` 支持点击图片按钮选择本地图片。
3. 上传成功后在光标处插入 `![文件名](orf-attachment:{id})`。
4. 评论正文渲染支持附件 token，并用后端返回的预览或下载 URL 展示附件。
5. 上传失败不清空输入框。
6. 第一版不做拖拽和非图片附件；当前版本已经扩展为支持拖放和通用文件附件。

验收：

1. 粘贴或选择图片后能看到上传状态，并在发送后看到图片展示。
2. 刷新页面后图片仍可展示。
3. 无权限用户不能读取附件内容。

## 6. WSL 到本地服务器迁移

迁移状态分两类：

1. PostgreSQL：评论消息和附件元数据。
2. MinIO bucket：附件文件内容。

迁移步骤：

1. 在本地服务器准备 PostgreSQL、MinIO 和 ORF `.env`。
2. 在 WSL 导出 PostgreSQL。
3. 在本地服务器恢复 PostgreSQL。
4. 使用 `mc mirror` 或等价工具同步 `orf-comment-attachments` bucket。
5. 更新 ORF `.env` 的 `DATABASE_URL`、`OBJECT_STORAGE_ENDPOINT`、账号和 bucket。
6. 启动 ORF 后端，验证评论列表、图片读取和权限。

评论正文只引用附件 ID，所以迁移后不需要批量改历史评论正文。

## 7. 回滚

1. 第一阶段只涉及文档和 MinIO 本地环境，可以直接停止 `npm run storage:down`。
2. 第二阶段上线前保留数据库备份；如需回滚，先停写评论，再恢复 PostgreSQL 和 MinIO bucket。
3. 第三阶段前端可以通过功能开关隐藏粘贴上传入口，但后端仍应能读取已有附件。

## 8. 风险

| 风险 | 处理方式 |
| --- | --- |
| bucket 被误设 public | compose 初始化为 private，部署检查 bucket policy。 |
| 评论正文和附件绑定不一致 | 后端以正文 token 为准，统一在创建和编辑事务内绑定。 |
| pending 附件堆积 | 设置 `expires_at` 并定期清理 DB 和对象。 |
| MinIO 迁移失败 | 迁移前同时备份 PostgreSQL 和 bucket；验收通过后再切流量。 |
| 未来换存储实现 | 业务代码只依赖 `ObjectStorage` 适配层。 |

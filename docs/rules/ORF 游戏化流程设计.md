# ORF 悬赏指标流程设计


## 目标

本文档定义 ORF 悬赏指标流程的业务口径和页面术语。

ORF 中的 `Result` 在页面层表达为“悬赏指标”。用户通过悬赏大厅查看、申请挑战、接受挑战、重估、执行、提交战利品并获得结算。

该设计的目标不是把 ORF 做成娱乐系统，而是用少量页面化表达增强悬赏指标流转的参与感、确定性和反馈闭环。

ORF 的系统宗旨是让系统和 AI 承接更多信息处理，减少管理员在简单、重复信息上的判断和整理成本，让管理员专注于全局把控和关键决策。

## 核心原则

1. 悬赏指标不是普通任务，任务必须挂在悬赏指标下面。
2. 悬赏指标必须可执行、可量化、可验证。
3. 难度在发布悬赏指标时公开，不由挑战者自评。
4. 挑战者可以重估悬赏指标合理性。
5. 只有重估导致悬赏指标内容变化时，难度才可以调整。
6. 主线悬赏指标必须有人负责。
7. 支线悬赏指标可以无人挑战。
8. 成员提出的候选悬赏指标被采纳后，提出人获得优先挑战权。
9. 奖励结算基于难度和完成结果，不奖励单纯忙碌。

## 术语口径

代码、接口和数据库使用数据模型术语；页面文案、用户操作和产品说明使用页面术语。除非能表达明确业务差异，否则不新增别名。

| 数据模型 / ORF 语义 | 页面术语 | 说明 |
| --- | --- | --- |
| Objective | 目标 | 当前阶段要改变的方向 |
| Result | 悬赏指标 | 可执行、可量化、可验证的结果口径 |
| Task | 任务 | 悬赏指标下面的具体执行动作 |
| TaskChecklistItem | 子任务 | 任务下面的最小勾选项 |
| 关键悬赏指标 | 主线悬赏指标 | 必须完成，直接支撑目标达成 |
| 可选悬赏指标 | 支线悬赏指标 | 可选完成，用于优化、探索或额外收益 |
| 悬赏指标列表 | 悬赏大厅 | 用户查看和参与悬赏指标的入口 |
| 候选悬赏指标 | 候选悬赏指标 | 成员提出、等待指挥官采纳的悬赏指标草案 |
| 申请负责 | 申请挑战 | 成员表达希望负责该悬赏指标，需要指挥官确认 |

| 验收 | 验收 | 根据验收标准判断结果是否有效 |
| 积分计算 | 奖励结算 | 根据难度和完成结果计算积分 |

权限口径：指挥官是产品流程称呼，权限上等同管理员，不单独建立“指挥官”角色。负责人只用于悬赏指标，表示当前挑战者；目标不设置负责人语义。

## 悬赏指标来源

### 指挥官定义悬赏指标

指挥官已经知道要什么结果时，可以直接定义悬赏指标。

流程：

```text
指挥官定义悬赏指标
→ 设置等级、最终截止时间、验收标准
→ 发布到悬赏大厅
→ 成员申请挑战
→ 指挥官确认挑战者
→ 挑战者接受挑战
→ 进入悬赏指标确认期
```

规则：

- 指挥官定义的悬赏指标发布后进入可挑战状态。
- 成员申请挑战后，必须由指挥官或发布者确认挑战者。
- 挑战者接受后才开始计算确认期。

### 成员提出候选悬赏指标

成员发现价值并把目标拆成可验收结果时，可以提交候选悬赏指标。

流程：

```text
成员提交候选悬赏指标
→ 指挥官采纳
→ 发布到悬赏大厅
→ 提出人获得优先挑战权
→ 提出人接受或放弃
```

提出人优先挑战规则：

```text
接受：成为挑战者
放弃：进入公共池
超时：视为放弃
放弃后：提出人不能再次挑战该悬赏指标
```

优先挑战期默认 2 小时。优先期只用于让提出人确认是否亲自挑战，不使用最终截止时间比例计算。

进入公共池后：

```text
其他成员申请挑战
→ 指挥官确认挑战者
→ 挑战者接受挑战
→ 进入悬赏指标确认期
```

## 悬赏指标类型

### 主线悬赏指标

主线悬赏指标是必须完成的悬赏指标，直接支撑目标达成。

规则：

- 发布后进入悬赏大厅。
- 成员可以点击“申请挑战”。
- 指挥官或发布者确认挑战者。
- 如果无人挑战，进入征召。
- 征召后由指挥官指定待接受挑战者。
- 只有被指定成员看到征召并接受挑战后，才成为挑战者。
- 被征召的挑战者仍然可以重估悬赏指标合理性。

### 支线悬赏指标

支线悬赏指标是可选悬赏指标，用于探索、优化、改进或额外收益。

规则：

- 发布后进入悬赏大厅。
- 成员可以点击“申请挑战”。
- 指挥官或发布者确认挑战者。
- 无人挑战时可以继续挂起、过期关闭或后续重新发布。
- 支线悬赏指标不进入征召。

## 核心流程

```text
悬赏指标来源
├─ 指挥官定义悬赏指标
│  → 发布到悬赏大厅
│  → 成员申请挑战
│  → 指挥官确认挑战者
│
└─ 成员提出候选悬赏指标
   → 指挥官采纳
   → 发布到悬赏大厅
   → 提出人优先挑战
   → 提出人接受或放弃
   → 放弃或超时后进入公共池
   → 其他成员申请挑战
   → 指挥官确认挑战者

挑战者接受挑战
→ 悬赏指标确认期
→ 悬赏指标冻结
→ 按悬赏指标执行
→ 提交战利品
→ 指挥官验收
→ 系统结算
```

## 最小状态口径

| 状态 | 进入条件 | 主要操作 |
| --- | --- | --- |
| 候选中 | 成员提交候选悬赏指标，尚未被采纳 | 指挥官采纳或拒绝 |
| 优先挑战中 | 候选悬赏指标被采纳，提出人仍在优先期内 | 提出人接受或放弃 |
| 可申请 | 指挥官发布，或优先期放弃 / 超时进入公共池 | 成员申请挑战 |
| 申请中 | 成员已申请挑战，等待确认 | 指挥官确认挑战者 |
| 征召中 | 主线悬赏指标无人挑战，指挥官指定待接受挑战者 | 被指定成员接受挑战 |
| 确认期 | 挑战者接受挑战后 | 确认通过、发起重估、放弃或超时 |
| 已冻结 | 确认通过后 | 按冻结后的悬赏指标执行 |
| 待验收 | 挑战者提交战利品后 | 指挥官验收 |
| 已结算 | 验收完成并完成奖励结算 | 查看结算结果 |
| 已关闭 | 悬赏指标被关闭或放弃后不再开放 | 无 |

`申请挑战` 只表达意愿，不产生挑战者；`接受挑战` 才会写入挑战者并启动确认期。

## 确认期规则

指挥官定义每个悬赏指标的最终截止时间。

挑战者接受挑战后，系统计算悬赏指标确认截止时间：

```text
剩余时间 = 最终截止时间 - 接受挑战时间
原始确认期 = 剩余时间 × 30%
确认期 = clamp(roundToHalfDay(原始确认期), 0.5 天, 9 天)
确认截止时间 = 接受挑战时间 + 确认期
```

其中：

- `roundToHalfDay(x)` 表示以半天为单位四舍五入。
- 确认期最短半天，最长 9 天。
- 如果最终截止时间距离接受挑战时间不足半天，不允许开始挑战，必须由指挥官延长最终截止时间或关闭悬赏指标。

确认期只做一件事：确认悬赏指标。

确认期内可以产生以下结果：

| 结果 | 后续状态 |
| --- | --- |
| 确认通过 | 悬赏指标冻结，挑战者按悬赏指标要求执行 |
| 发起重估 | 指挥官审批后更新悬赏指标，再冻结 |
| 主动放弃 | 0 分，悬赏指标进入公共池或关闭 |
| 超时未确认 | 视为放弃，悬赏指标进入公共池或关闭 |

## 结果规则

| 结果 | 结算口径 |
| --- | --- |
| 达到悬赏指标要求 | 完成 |
| 未达到悬赏指标要求 | 未完成 |
| 有效证伪 | 按证伪规则结算 |
| 主动放弃 | 0 分 |

# ORF 项目归属边界决策草案

## 文档状态

本文档是 issue #39 的决策草案，不是已生效业务契约。

当前仓库仍以 `Objective -> Result / Task / Feedback / Settlement` 为核心业务链。`team_id` 只表示底层默认作用域和存储隔离，不是项目，也不能直接复用为 Project。

在用户明确决策前，不能把本文档中的任一方案实现为代码、接口、迁移、权限或 UI 契约。

## 当前事实

- `Objective` 是悬赏、挑战、战利品和积分结算的核心对象。
- `Result` 是目标下的验收指标和计分基础。
- `Task` 是目标下的执行行动项，不归属于 `Result`。
- `Feedback` 绑定目标和指标，但不推进悬赏目标状态机。
- `pointLedger` 是公开积分结果，排行榜只读取后端结算后的积分流水。
- 当前产品明确不支持多团队；运行时只有一个默认作用域。
- 数据库中的 `teams`、`team_members` 和各表 `team_id` 只表达底层 scope，不表达项目管理语义。
- 当前没有 `projects`、`project_id`、`projectId` 或项目切换入口。

## 核心问题

ORF 是否必须引入 Project，取决于用户是否需要一个独立于默认作用域、独立于 Objective 生命周期的业务归属边界。

如果 ORF 只服务一个连续业务流，目标、反馈、统计和消息都可以保持在默认作用域内，Project 不是绝对必要。

如果用户需要把目标、挑战、反馈、统计、归档和消息按多个业务单元稳定分隔，那么 Project 应成为一级业务容器，不能用标题、标签、周期或 `team_id` 临时代替。

## 不引入 Project 的方案

### 适用条件

- ORF 只服务一个默认业务工作流。
- 用户主要按周期、状态、成员、难度或关键词查找目标。
- 统计榜单本来就应该是全局榜单。
- 反馈收件箱本来就是全局反馈池。
- 归档只需要按目标状态或周期处理，不需要项目级封存。
- 不需要项目级成员、项目级角色或项目级可见性。

### 用户体验

- AppShell 不出现项目切换器。
- 悬赏大厅继续展示默认作用域内公开目标。
- 我的挑战继续按“我的 / 全部”、周期、成员和状态过滤。
- 反馈继续按可见目标过滤。
- 统计继续读取默认作用域内公开 `pointLedger`。
- 归档通过目标状态、周期或后续明确的归档规则完成。

### 优点

- 不引入新业务实体，系统更简单。
- 不改变现有读模型、权限模型、状态机和结算模型。
- 不需要迁移旧数据到默认项目。
- 不会产生“当前项目上下文”和已有页面状态之间的新耦合。

### 风险

- 目标、反馈、统计和消息长期仍在默认作用域内混合。
- 如果后续出现多个业务单元，用户只能靠周期、标题或人工约定区分。
- 如果未来又补 Project，需要再迁移现有目标并重定义统计口径。
- 标题、标签或周期一旦被拿来模拟项目，就会形成隐式事实源。

## 最小 Project 方案

### 适用条件

- 用户需要明确知道目标属于哪个业务项目。
- 悬赏大厅、我的挑战、反馈和统计需要按项目切换或筛选。
- 项目归档要能稳定隐藏一组目标，但历史目标、战利品、评论和积分仍可追溯。
- 第一版不需要项目级成员、项目级角色或项目私有权限。

### 业务状态链

```text
Project
-> Objective
-> Result / Task / Feedback / Loot / TrialReview / AlignmentRequest / Comment
-> pointLedger / Notification
```

不变量：

- `Project` 是目标业务归属的唯一事实源。
- `Objective.projectId` 是目标所属项目的唯一持久字段。
- `Result`、`Task`、`Feedback`、战利品、评论、消息和积分不各自维护独立项目事实，必须从 `Objective.projectId` 派生。
- `team_id` 继续只做默认作用域和存储隔离，不进入项目业务口径。
- 旧数据必须迁入一个默认项目，不能留下无项目目标参与新读模型。

### 用户体验

- AppShell 提供当前项目显示和切换入口。
- 新建目标默认落入当前项目。
- 悬赏大厅默认展示当前项目公开目标。
- 我的挑战默认展示当前项目内目标，并保留“我的 / 全部”角色范围。
- 反馈收件箱默认展示当前项目内反馈。
- 统计页明确展示当前项目榜单，或提供“全部项目”筛选项。
- 消息显示项目标签；点击消息进入目标时同步切到对应项目上下文。
- 管理员可以创建、重命名、归档和恢复项目。

### 优点

- 业务归属边界清晰。
- 项目、目标、指标、任务、反馈、积分和消息形成单向契约链。
- 不把 `team_id` 和 Project 混用。
- 不引入项目级权限时，第一版复杂度可控。

### 风险

- 读模型、缓存失效、前端状态和页面筛选都要增加项目上下文。
- 统计口径必须重新明确，否则项目榜单和全局榜单会冲突。
- 消息跳转必须能从目标反推项目，否则用户可能进入错误上下文。
- 归档项目的可读、可写和可统计范围需要提前定清楚。

## Project + 项目成员权限方案

### 适用条件

- 不同项目之间需要数据隔离。
- 普通成员只能看到自己所属项目。
- 项目内存在项目管理员、项目成员、只读成员等角色。
- 项目级权限和默认作用域权限需要组合。

### 代价

该方案会改变权限边界、用户可见性、消息投递、评论 mention、统计口径、测试数据隔离和旧数据迁移策略。

除非已经明确需要项目私有性或项目角色，否则不建议作为第一阶段。

## 是否有绝对必要

Project 没有绝对必要。

当前系统在没有 Project 的情况下仍然自洽：`Objective` 承载挑战状态机，`Result` 承载验收和计分基础，`Task` 承载行动项，`pointLedger` 承载公开积分结果。只要用户接受“默认作用域内只有一个业务工作流”，系统可以继续不引入 Project。

Project 变得必要的条件不是“项目管理工具通常有项目”，而是 ORF 自己出现稳定的业务边界需求：

- 目标必须按业务项目归属，而不是只按周期或状态归类。
- 反馈必须能落到项目上下文中。
- 统计必须能按项目解释。
- 归档必须能封存一组目标和相关记录。
- 消息必须能告诉用户它属于哪个业务项目。
- 后续需要项目级成员、项目级角色或项目级可见性。

如果这些需求暂时不成立，不做 Project 是更简单的方案。

## 建议的阶段策略

### 阶段 0：先不做 Project

继续保持当前模型，只补充筛选、归档或统计说明。适合还不能确认 Project 是否必要的阶段。

### 阶段 1：最小 Project 容器

只引入项目归属，不引入项目级权限：

- 新增 `Project` 模型。
- 给 `Objective` 增加必填 `projectId`。
- 迁移旧目标到默认项目。
- 页面和 API 读取以当前项目为上下文。
- 下游对象项目归属从目标派生。

### 阶段 2：项目成员和权限

只有在确认需要项目私有边界后才进入：

- 新增项目成员关系。
- 定义项目角色和默认作用域角色的组合规则。
- 重写读模型可见性、消息投递和评论 mention 边界。
- 扩展测试覆盖项目隔离。

## 需要用户决策的问题

1. ORF 是否会长期只有一个业务工作流？如果是，是否可以继续不引入 Project？
2. 用户查找目标时，主要需要按周期/状态/成员筛选，还是必须先选项目？
3. 统计榜单应该是全局榜单，还是项目内榜单，还是全局榜单加项目筛选？
4. 反馈收件箱应该是全局反馈池，还是每个项目独立反馈池？
5. 历史目标归档是否只按目标状态和周期就够，还是必须按项目整体归档？
6. 项目归档后，历史战利品、评论、反馈、消息和积分是否仍可读？
7. 普通成员是否能看到所有项目，还是只能看到自己参与或被授权的项目？
8. 第一版 Project 是否只做归属容器，不做项目成员和项目权限？
9. 旧数据是否全部迁入一个默认项目？
10. AppShell 是否需要常驻项目切换器，还是只在相关页面提供项目筛选？

## 暂不实现的内容

- 不把 `team_id` 改名或复用为 Project。
- 不用标题、标签、周期或 reason 文本模拟项目事实源。
- 不在未决前新增项目级权限。
- 不在未决前改变积分结算公式。
- 不在未决前改变匿名互评、本地结算服务或公开 `pointLedger` 的事实源边界。

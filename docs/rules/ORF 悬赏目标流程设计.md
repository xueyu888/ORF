# ORF 悬赏目标流程设计

## 核心口径

- 挑战对象是 `Objective`，页面称为“悬赏目标”。
- `Result` 是悬赏指标，只作为目标的验收口径和计分基。
- 挑战者绑定到 `Objective.challengers`，不绑定到 `Result`。
- 一个目标可以有多个挑战者；一个目标可以包含多个悬赏指标。
- 目标冻结后，默认目标下所有悬赏指标一起冻结。
- 任务和子任务只表示执行动作，不自动推导验收、完成或结算。

## 流程价值

悬赏目标流程不是娱乐化包装，也不是传统派任务流程。它的作用是把成员的主动贡献、目标验收和积分结算放进同一条清晰链路。

- 悬赏大厅提供主动发现目标和申请挑战的入口。
- 确认期用于提前暴露目标、指标、验收标准和截止时间的问题。
- 目标冻结保证执行期间口径稳定，减少事后争议。
- 战利品要求成员用证据证明指标完成或有效证伪。
- 目标级互评让积分分配基于协作贡献，而不是指标负责人或任务数量。
- 指挥官只处理确认、验收、征召、异常和分歧，避免陷入日常信息搬运。

## 术语

| 模型 | 页面术语 | 说明 |
| --- | --- | --- |
| `Objective` | 悬赏目标 / 目标 | 挑战对象和积分分配对象 |
| `Result` | 悬赏指标 | 目标下的验收口径和计分基 |
| `Task` | 任务 | 支撑悬赏指标的执行动作 |
| `TaskChecklistItem` | 子任务 | 任务下的勾选项 |
| `Objective.challengers` | 挑战者 | 已接受并参与目标挑战的成员 |
| 交付证据 | 战利品 | 证明目标下指标完成或有效证伪的材料 |

指挥官是产品称呼，权限上按管理员处理。

## 流程

```text
创建或采纳悬赏目标
→ 拆出悬赏指标
→ 发布到悬赏大厅
→ 成员申请挑战 / 指挥官征召
→ 指挥官确认挑战者
→ 挑战者接受
→ 目标确认期
→ 目标冻结
→ 执行任务
→ 提交目标战利品
→ 指挥官验收目标
→ 目标级积分结算
```

成员提出候选悬赏目标后，必须由指挥官采纳后才能进入悬赏大厅。

## 状态

| 状态 | 进入条件 | 主要操作 |
| --- | --- | --- |
| 候选中 | 成员提交候选目标 | 采纳 / 拒绝 |
| 可申请 | 目标已发布 | 申请挑战 |
| 申请中 | 成员已申请 | 确认挑战者 |
| 征召中 | 指挥官指定成员 | 接受挑战 |
| 确认期 | 挑战者接受后 | 确认 / 重估 / 放弃 |
| 已冻结 | 目标确认通过 | 执行任务 |
| 待验收 | 已提交战利品 | 验收 |
| 已结算 | 验收和积分结算完成 | 查看结果 |
| 已关闭 | 目标关闭或放弃 | 无 |

`申请挑战` 只表达意愿；`接受挑战` 才写入 `Objective.challengers`。

## 确认期

```text
剩余时间 = 目标最终截止时间 - 接受挑战时间
原始确认期 = 剩余时间 × 30%
确认期 = clamp(roundToHalfDay(原始确认期), 0.5 天, 9 天)
确认截止时间 = 接受挑战时间 + 确认期
```

确认期只确认目标和指标口径是否成立。可调整目标、指标、验收标准、截止时间和难度等级。

确认期内可提出重估；确认通过后目标冻结。

## 征召

- 征召发生在目标层级。
- 当前阶段，被征召成员必须接受挑战。
- 被征召成员接受后成为目标挑战者。
- 被征召成员可在确认期内提出重估。
- 不存在指标级征召。

## 战利品

战利品提交发生在目标层级。提交页必须提醒：战利品用于证明目标下悬赏指标已经完成或被有效证伪。

战利品至少说明：

- 哪些悬赏指标已完成。
- 每个已完成指标对应的证据。
- 如果是证伪，证伪依据和影响范围。

## 积分口径

Objective 分积分，Result 不分积分。

目标总分由目标下已验收悬赏指标的不确定性分相加得到。个人积分只在目标结算后，按目标挑战者之间的匿名互评贡献比例分配。

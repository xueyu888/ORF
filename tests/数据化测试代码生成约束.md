# 结构化测试代码生成约束

## 1. 目标

本文档用于约束测试用例最终生成的测试代码。

核心目标不是把测试用例文档改写成 JSON、YAML 或数据库表，而是让生成出来的测试代码保留清晰的状态变化结构：

```text
B -> Setup -> S0 -> Action -> S1 -> Clean -> B
```

也就是说，测试代码不能只是一串连续的 `await` 调用，而应该能直接看出：

```text
测试从什么基准状态开始；
如何构造 Action 前状态；
Action 前状态是什么；
执行了什么业务动作；
Action 后状态是什么；
如何清理并回到基准状态。
```

---

## 2. 核心原则

测试代码必须显式区分两类内容：

```text
状态：B、S0、S1
动作：Setup、Action、Clean
```

其中：

* B：测试开始前和 Clean 后都必须满足的基准状态。
* Setup：把 B 构造成 S0。
* S0：Action 发生前必须满足的状态。
* Action：本用例真正要验证的业务动作。
* S1：Action 发生后系统应该进入的目标状态。
* Clean：清理本次测试影响，使系统回到 B。

状态和动作不能混在一起。

状态函数中可以使用 `expect`、`expect.poll`、API 查询、数据库查询、浏览器状态读取等方式确认状态成立。

---

## 3. 生成代码必须按结构分文件

生成测试代码时，不应该把所有内容都写进一个 `.spec.ts` 文件。

代码结构应当体现：

```text
B -> Setup -> S0 -> Action -> S1 -> Clean -> B
```

推荐按用例或业务场景分文件，例如：

```text
login/
├── login.spec.ts      # 测试入口，组织主流程
├── login.states.ts    # B、S0、S1
├── login.actions.ts   # Setup、Action、Clean
├── login.context.ts   # 需要共享的内容, 不要让测试邮箱、密码、用户角色、SetupState 这些东西散落在多个文件里
└── login.helpers.ts   # 底层实现, 不要在状态和动作文件里塞太多 API / Prisma / cookie / storage 实现细节
```

## 4. 命名规范

代码中推荐使用以下命名：

```ts
async function B(ctx: TestContext) {}
async function setup(ctx: TestContext): Promise<SetupState> {}
async function S0(ctx: TestContext, setupState: SetupState) {}
async function action(ctx: TestContext, setupState: SetupState): Promise<ActionResult> {}
async function S1(ctx: TestContext, setupState: SetupState, actionResult: ActionResult) {}
async function clean(ctx: TestContext, setupState: SetupState) {}
```

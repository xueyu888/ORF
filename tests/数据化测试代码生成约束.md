# 数据化测试代码生成约束

## 1. 目的

本文档用于约束如何根据 `数据化测试用例模板.md` 生成统一的数据化测试代码。

生成后的测试代码必须遵循统一状态模型：

```text
B -> Setup -> S0 -> Action -> S1 -> Clean -> B
```

生成后的测试用例代码只声明结构化数据，不手写执行流程，也不直接调用 Playwright、DB、API 或 Ory。

职责分层：

- case：由测试用例文档生成，只声明用例元信息、阶段、步骤和参数，描述“要做什么”。
- runner：统一执行 `B -> Setup -> S0 -> Action -> S1 -> Clean -> B`，负责流程顺序、异常处理和清理保证。
- operator：实现每个步骤的具体能力，负责调用 Playwright、DB、API、Ory 或 Mock。
- reporter：记录执行结果，负责生成阶段结果、错误信息、截图附件和测试报告。

## 3. Case 生成约束

### 3.1 case 文件介绍

`xxx.case.ts` 由人工编写的测试用例文档生成，只声明数据：

```ts
export const mloginSuccessCase = {
  id: "auth.login.success",
  title: "普通成员可以使用正确邮箱和密码登录 ORF",
  model: STATE_CASE_MODEL,
  tags: ["auth", "login", "happy-path"],
  data: {
    email: "orf-login-e2e@orf.local",
    password: "OrfLoginE2E!2026",
  },
  B: { description: "xxx", assertions: [] },
  Setup: { description: "xxx", steps: [] },
  S0: { description: "xxx", assertions: [] },
  Action: { description: "xxx", steps: [] },
  S1: { description: "xxx", assertions: [] },
  Clean: { description: "xxx", steps: [] },
} satisfies StateCaseSpec<MloginCaseData>;
```

`case.ts` 中不得直接导入状态函数或动作函数。

### 3.2 文档到 case 的映射

从测试用例文档生成 `case.ts` 时，必须遵守：

- 文档中的 B、Setup、S0、Action、S1、Clean 分别映射为 `B`、`Setup`、`S0`、`Action`、`S1`、`Clean` 数据块。
- 文档中的每条 `[playwright]`、`[api]`、`[prisma]`、`[mock]` 条目生成一个 `StepSpec`。
- `id` 和 `title` 从人类可读条目中提炼，保持报告可读。
- `operator` 根据执行手段和语义选择已有算子；没有合适算子时，在 `xxx.operators.ts` 中新增算子。
- `data` 只放生成代码确实需要复用的稳定测试输入；不要因为生成结构需要，反向要求测试用例文档单独列数据字典。

### 3.3 case 的数据结构

`types.ts` 必须提供 `StateCaseSpec` 作为所有 `case.ts` 共享的数据化 schema：

```ts
export type StateCaseSpec<TData extends Record<string, unknown>> = {
  id: string;
  title: string;
  model: "B -> Setup -> S0 -> Action -> S1 -> Clean -> B";
  tags?: string[];
  data: TData;
  B: StateBlock;
  Setup: ActionBlock;
  S0: StateBlock;
  Action: ActionBlock;
  S1: StateBlock;
  Clean: ActionBlock;
};

export type StateBlock = {
  description: string;
  assertions: StepSpec[];
};

export type ActionBlock = {
  description: string;
  steps: StepSpec[];
};

export type StepSpec = {
  id: string;
  title: string;
  operator: string;
  params?: Record<string, unknown>;
};
```

### 3.4 Step 约束

所有步骤必须使用统一格式：

```ts
{
  id: "fill.email",
  title: "输入邮箱",
  operator: "page.fill",
  params: {
    label: "Email",
    valueFrom: "data.email",
  },
}
```

约定：

- `xxxFrom` 在 runner 中解析为 `xxx`。
- `data.xxx` 读取用例固定数据。
- `runtime.xxx` 读取前面步骤保存的运行时结果。
- `saveAs` 用于保存算子返回值到 `runtime`。

## 4. Runner 约束

### 4.1 runner 执行顺序

`runStateCase` 必须固定执行：

```text
B.assertions[]
Setup.steps[]
S0.assertions[]
Action.steps[]
S1.assertions[]
Clean.steps[]
B.assertions[]
```

Clean 必须在 `finally` 语义下执行；Clean 后必须重新执行 B，并在报告中记录为 `B after Clean`。

### 4.2 spec 接入

`xxx.spec.ts` 只接入 Playwright：

```ts
test(mloginSuccessCase.title, async ({ context, page }, testInfo) => {
  const ctx: TestContext = { context, page };

  await runStateCase(mloginSuccessCase, ctx, {
    operators: mloginOperators,
    testInfo,
  });
});
```

`.spec.ts` 不得直接执行业务步骤。

## 5. Operator 约束

### 5.1 operator 注册表

`xxx.operators.ts` 放算子注册表：

```ts
export const mloginOperators = {
  "page.goto": pageGoto,
  "page.fill": pageFill,
  "api.health.ok": apiHealthOk,
  "db.ready": dbReady,
} satisfies OperatorRegistry<TestContext, MloginCaseData>;
```

### 5.2 operator 实现边界

operator 负责具体实现，可以调用：

```text
Playwright
DB helper
API helper
Ory helper
Mock helper
```

operator 不负责编排 B、Setup、S0、Action、S1、Clean 的整体流程。

### 5.3 context 和 helpers

`xxx.context.ts` 放：

```text
TestContext
CaseData
共享常量
外部结果类型
```

`xxx.helpers.ts` 放底层能力：

```text
数据库读写
API 请求
cookie/storage 读取
Ory 操作
关闭连接
```

helper 不表达测试流程。

## 6. Reporter 约束

### 6.1 报告产物

每次执行 Playwright 测试后必须自动生成报告：

```text
test-reports/
└── 2026年5月18日14时38分59秒/
    ├── summary.md
    └── result.json
```

### 6.2 阶段记录

runner 至少记录这些阶段：

```text
B
Setup
S0
Action
S1
Clean
B after Clean
```

每个阶段至少记录：

```text
阶段名
执行结果
耗时
错误信息
```

失败用例应保留失败阶段、错误信息、阶段结果和截图附件。

## 7. 一句话约束

测试用例是数据。

执行顺序归 runner。

具体能力归 operator。

结果留痕归 reporter。

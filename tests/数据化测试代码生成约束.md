# 结构化测试代码生成约束

## 1. 目标

本文档用于约束测试用例最终生成的测试代码。

核心目标是让测试代码严格遵循统一状态模型：

```text
B -> Setup -> S0 -> Action -> S1 -> Clean -> B
```

测试用例本身只声明状态和动作，不手写执行流程。

执行流程由通用执行器统一控制。

---

## 2. 核心原则

测试代码必须显式区分两类内容：

```text
状态：B、S0、S1
动作：Setup、Action、Clean
```

其中：

- B：测试开始前和 Clean 后都必须满足的基准状态。
- Setup：把 B 构造成 S0。
- S0：Action 发生前必须满足的状态。
- Action：本用例真正要验证的业务动作。
- S1：Action 发生后系统进入的目标状态。
- Clean：清理本次测试影响，使系统回到 B。

状态和动作不能混在一起。

---

## 3. 生成代码必须使用通用执行器

测试流程不能直接写在 `.spec.ts` 中。

不推荐：

```ts
await B(ctx);

const setupState = await setup(ctx);
await S0(ctx, setupState);

const actionResult = await action(ctx, setupState);
await S1(ctx, setupState, actionResult);

await clean(ctx, setupState);
await B(ctx);
```

必须改为：

```ts
await runStateCase(loginSuccessCase, ctx);
```

执行顺序由 `runStateCase` 固定。

## 5. 通用类型

`state-case.types.ts`：

```ts
export type StateCase<TContext, TSetupState, TActionResult> = {
  id: string;
  title: string;

  B: (ctx: TContext) => Promise<void>;

  setup: (ctx: TContext) => Promise<TSetupState>;

  S0: (ctx: TContext, setupState: TSetupState) => Promise<void>;

  action: (
    ctx: TContext,
    setupState: TSetupState,
  ) => Promise<TActionResult>;

  S1: (
    ctx: TContext,
    setupState: TSetupState,
    actionResult: TActionResult,
  ) => Promise<void>;

  clean: (
    ctx: TContext,
    setupState: TSetupState,
  ) => Promise<void>;
};
```

---

## 6. 通用执行器

`state-case.runner.ts`：

```ts
import type { StateCase } from "./state-case.types";

export async function runStateCase<TContext, TSetupState, TActionResult>(
  testCase: StateCase<TContext, TSetupState, TActionResult>,
  ctx: TContext,
) {
  let setupState: TSetupState | null = null;

  await testCase.B(ctx);

  try {
    setupState = await testCase.setup(ctx);

    await testCase.S0(ctx, setupState);

    const actionResult = await testCase.action(ctx, setupState);

    await testCase.S1(ctx, setupState, actionResult);
  } finally {
    if (setupState) {
      await testCase.clean(ctx, setupState);
    }

    await testCase.B(ctx);
  }
}
```

## 7. 用例声明文件

`login.case.ts` 只声明用例结构。

```ts
import type { StateCase } from "../../_framework/state-case.types";
import { action, clean, setup } from "./login.actions";
import { B, S0, S1 } from "./login.states";
import type {
  ActionResult,
  SetupState,
  TestContext,
} from "./login.context";

export const loginSuccessCase: StateCase<
  TestContext,
  SetupState,
  ActionResult
> = {
  id: "auth.login.success",
  title: "普通成员可以使用正确邮箱和密码登录 ORF",

  B,
  setup,
  S0,
  action,
  S1,
  clean,
};
```

## 8. 测试入口文件

`login.spec.ts` 只作为 Playwright 测试入口。

```ts
import { test } from "@playwright/test";
import { runStateCase } from "../../_framework/state-case.runner";
import { loginSuccessCase } from "./login.case";
import { closeLoginTestDb } from "./login.helpers";
import type { TestContext } from "./login.context";

test.describe("登录测试用例", () => {
  test.afterAll(async () => {
    await closeLoginTestDb();
  });

  test(loginSuccessCase.title, async ({ context, page }) => {
    const ctx: TestContext = { context, page };

    await runStateCase(loginSuccessCase, ctx);
  });
});
```

`.spec.ts` 中不得直接调用：

```text
B
setup
S0
action
S1
clean
```

---

## 9. 状态文件

`login.states.ts` 只放状态断言。

推荐命名：

```ts
export async function B(ctx: TestContext) {}

export async function S0(
  ctx: TestContext,
  setupState: SetupState,
) {}

export async function S1(
  ctx: TestContext,
  setupState: SetupState,
  actionResult: ActionResult,
) {}
```

状态函数只确认状态成立，不负责制造状态。

---

## 10. 动作文件

`login.actions.ts` 只放状态迁移动作。

推荐命名：

```ts
export async function setup(
  ctx: TestContext,
): Promise<SetupState> {}

export async function action(
  ctx: TestContext,
  setupState: SetupState,
): Promise<ActionResult> {}

export async function clean(
  ctx: TestContext,
  setupState: SetupState,
): Promise<void> {}
```

动作函数负责改变状态，不负责核心状态断言。

---

## 11. 上下文文件

`login.context.ts` 放共享常量和类型。

例如：

```text
TEST_EMAIL
TEST_PASSWORD
TEST_USER_ID
TEST_TEAM_ID
TestContext
SetupState
ActionResult
```

测试数据、状态类型、动作结果类型不得散落在多个文件中。

---

## 12. Helper 文件

`login.helpers.ts` 放底层实现。

例如：

```text
数据库操作
API 请求
cookie 查询
storage 查询
session 查询
health check
关闭数据库连接
```

helper 中不表达测试流程。

---

## 13. 生成代码约束

生成代码时必须满足：

```text
1. 必须有 state-case.types.ts
2. 必须有 state-case.runner.ts
3. 每个用例必须有 xxx.case.ts
4. xxx.case.ts 必须声明 StateCase
5. xxx.spec.ts 只能调用 runStateCase
6. B、S0、S1 必须放在 states.ts
7. setup、action、clean 必须放在 actions.ts
8. SetupState、ActionResult 必须放在 context.ts
9. 底层 DB / API / cookie / storage 操作必须放在 helpers.ts
10. Clean 必须由 runner 在 finally 中执行
11. Clean 后必须重新执行 B
```

---

## 14. 最终结构

```text
case.ts
声明测试用例由哪些状态和动作组成。

spec.ts
接入 Playwright，只调用 runStateCase。

runner.ts
固定执行 B -> Setup -> S0 -> Action -> S1 -> Clean -> B。

states.ts
放 B、S0、S1。

actions.ts
放 setup、action、clean。

context.ts
放共享常量和类型。

helpers.ts
放底层实现。
```

---

## 15. 一句话约束

测试用例不直接编排流程。

测试用例只声明：

```text
B
Setup
S0
Action
S1
Clean
```

实际流程统一由 `runStateCase` 执行。


**测试是在特定目的下，选择系统的某些对象或属性，构造条件并观察结果，再根据某种判断标准产生质量信息的活动。**

**测试是在明确假设和边界之后，通过观察系统在选定条件下的行为，降低我们对失败区域、失败概率和失败影响的未知程度。**

拆开就是：

**特定目的**：为什么测
**对象或属性**：测什么
**构造条件并观察**：怎么测
**判断标准**：如何知道结果对不对
**质量信息**：测试产出什么


# 为什么测

第一，测试是因为“能实现”不等于“符合预期”。
第二，测试是因为“主流程能跑”不等于“真实场景可用”。
第三，测试是因为“我们觉得没问题”不等于“有证据可以承担风险”。

实现出来的东西和真正可接受的东西之间存在不确定性。
因此需要用**证据**缩小不确定性，判断系统是否达到目标场景下的**可接受质量**。

但是，测试本身不是质量的全部来源，它是质量判断的证据来源。

## 不确定性

测试中的不确定性，指的是：在给定系统边界和判断标准的前提下，我们对系统在各种条件下是否满足期望的未知程度。

不确定性不是“系统本身神秘”，而是“我们不知道”

我们不知道它在所有重要条件下会不会符合预期。

所以测试中的不确定性更接近一种**认知不确定性**：
我们不知道系统在哪些条件下会成功，在哪些条件下会失败，也不知道这些失败发生的概率和后果有多大。

这和“随机性”不完全一样。
比如一个函数对某个边界输入必然报错，这个错误不是随机的；只是测试之前我们不知道它会报错。测试发现它之后，不确定性下降了。

必须先定义边界，否则不确定性无法讨论。
不确定性一定是相对于某个模型、边界、假设和目标而言的。
没有边界，就无法量化；边界越清晰，越能量化。

## 如何定义不确定性

可以这样定义测试中的不确定性

假设我们有一个系统 S。

它会在很多条件下运行。每一个条件可以看成一个组合：

`条件 = 输入 + 系统状态 + 用户操作 + 数据状态 + 环境 + 外部依赖 + 时间因素`

我们把所有可能条件的集合叫做条件空间 C。

然后我们还有一个判断标准 Q，表示：

在条件 c 下，系统行为是否符合期望？

那么系统中真正的问题区域可以理解为：

`失败区域 = 所有会导致 Q 不成立的条件`

测试前，我们不知道失败区域在哪里、范围多大、严重程度如何。

所以测试中的不确定性可以定义为：

**我们对条件空间中失败区域的位置、大小、触发概率和影响程度的未知。**

这句话我觉得很重要。

因为它把“不确定性”说清楚了：

位置：哪些场景会失败？
大小：失败场景占整个空间多少？
概率：这些场景在真实使用中多常出现？
影响：失败后果有多严重？
可检测性：我们是否容易观察到失败？

测试就是通过选择条件、执行系统、观察结果，逐步缩小这种未知。

### 不确定性可以拆成几种

为了后面讨论“为什么测试”，我建议把不确定性分成几类。

需求不确定性

我们到底要什么？

比如“导出报表要快”，多快算快？
“用户不能越权”，哪些角色算越权？
“下单失败要可恢复”，恢复到什么状态？

如果期望本身不清楚，测试就很难判断对错。

实现不确定性

代码是否真的实现了预期？
这是最传统的测试对象。比如逻辑错误、边界错误、状态错误、并发错误、异常处理错误。
输入空间不确定性
用户和外部系统会给我们什么输入？
比如空值、超长字符串、非法枚举、重复请求、乱序事件、老版本数据、脏数据。

状态空间不确定性

系统内部会处于哪些状态？
很多 bug 不是某个输入单独造成的，而是“某个输入 + 某个历史状态”造成的。
比如订单状态：
待支付 → 已支付 → 已发货 → 已完成
如果出现：
已取消订单又收到支付成功回调
系统应该怎么办？这就是状态空间的不确定性。

环境不确定性

系统依赖的环境是否稳定？
例如网络抖动、缓存失效、数据库慢查询、第三方接口超时、时区变化、权限配置差异。
即使你默认 PC 不坏，软件运行环境本身仍然可能有很多变化。

判定不确定性

我们如何知道结果是对的？
这点经常被忽略。
有些测试很容易判断：
1 + 1 应该等于 2
但有些测试很难判断：
推荐结果是否合理？
搜索排序是否更好？
页面是否足够易用？
风控是否误杀过多？

如果 oracle，也就是判断标准不清楚，那么测试结果本身也有不确定性。

### 所以“不确定性”可以成为测试理论的核心

我觉得可以把测试重新定义成：

**测试是在明确假设和边界之后，通过观察系统在选定条件下的行为，降低我们对失败区域、失败概率和失败影响的未知程度。**

这比“测试是发现 bug”更底层。

因为发现 bug 只是降低不确定性的一种方式。

测试通过后，也是在降低不确定性：
这个区域我们观察过，暂时没有发现失败。

测试失败后，也是在降低不确定性：
这个区域确实存在失败。

测试设计，本质上是在选择：
我们应该优先探索哪些未知区域？

测试策略，本质上是在决定：
哪些不确定性最值得被降低？

测试停止，本质上是在判断：
剩余不确定性是否已经可以接受？

# 测什么

前面提到：**测试是在明确假设和边界之后，通过观察系统在选定条件下的行为，降低我们对失败区域、失败概率和失败影响的未知程度。**

关键部分是：

**观察系统在选定条件下的行为。**

所以，测试并不是观察一个抽象的“系统”，而是观察：

**某个系统对象，在某些条件下，表现出什么行为。**

`失败区域`到底是什么？

如果我们说：

测试是为了降低对失败区域的未知。

那就要问：失败区域存在于哪里？

**它不是漂浮在系统里的某个抽象东西。失败区域存在于条件空间里。**

可以这样表示：

`条件空间 C = 输入 + 状态 + 环境 + 依赖 + 操作序列 + 数据条件`

某些条件下系统表现正确，某些条件下系统表现错误。

所以失败区域可以定义成：

`失败区域 F = { c ∈ C | 系统在条件 c 下的行为不符合期望 }`

翻译成普通话就是：
失败区域，就是所有“系统在这些条件下会出错”的场景集合。

更结构化地说，测试对象不是单纯的“功能点”，而是：
某个系统对象，在某个条件下，是否满足某种期望。

可以表示为：

`测试对象 = 系统对象 × 条件空间 × 质量期望`

一个测试对象可以被描述成一个待验证命题：

`在条件 C 下，系统 S 应该表现出行为 B，并满足标准 Q。`

例如：

在用户输入错误密码 5 次后，
登录系统应该锁定账号，
并在 15 分钟内禁止继续登录。

这里面包含四个东西：

| 元素 | 含义 | 示例 | 
| --- | --- | --- |
| S | 被测对象 | 登录系统 |
| C | 触发条件 | 错误密码连续输入 5 次 |
| B | 期望行为 | 锁定账号 |
| Q | 判断标准 | 15 分钟内禁止登录 |

所以“测试什么”可以精炼成：

`测试 = 验证 S 在 C 下是否产生 B，并满足 Q`

# 怎么测

**针对关键不确定性，选择合适的条件、方法和判断标准，观察系统行为，并更新我们对系统可信程度的认知。**

更精炼一点：

**如何测 = 把不确定性转化为可执行、可观察、可判断的实验。**

前面我们说：

测试什么 = 系统 S 在条件 C 下是否满足期望 Q

那么“如何测”就是：

```
构造条件 C
执行系统 S
观察实际行为 A
对比期望 Q
判断通过 / 失败
更新不确定性
```

也就是：

`如何测试 = 构造条件 + 执行观察 + 结果判定 + 反馈修正`

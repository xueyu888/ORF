# 测试的本质：以不确定性为核心的工程活动

## 1. 核心定义

测试是在明确假设和边界之后，选择承载关键不确定性的系统行为，构造条件并观察实际结果，再依据判定标准判断其是否满足期望，最终产出关于缺陷、覆盖、风险、置信度和决策的质量信息。

更简洁地说：

> 测试不是为了证明系统绝对正确，而是为了用证据降低系统是否可接受的不确定性。

测试本身并不直接创造质量。质量来自需求、设计、实现、架构、交互、运维等多个环节。测试的核心价值在于生产质量证据，帮助判断系统在什么条件下可信、什么条件下不可信、还有哪些未知仍然存在。

---

## 2. 为什么测试

测试的根本原因是：

> 系统从“被实现出来”到“可被接受使用”之间存在不确定性。

软件实现完成，并不意味着它已经满足真实使用场景下的要求。一个系统可能能运行，但并不好用；可能主流程能跑通，但异常场景不可控；可能看起来正常，但在并发、边界、异常输入、依赖失败或环境变化下暴露问题。

因此，测试的目的不是单纯寻找 bug，而是降低以下不确定性：

1. 系统是否符合业务预期；
2. 系统是否在关键场景下行为正确；
3. 系统是否在异常条件下仍然可控；
4. 系统是否满足性能、安全、稳定性、易用性等质量要求；
5. 系统剩余风险是否可以被接受；
6. 当前证据是否足以支持发布、回滚、修复、延期或补测等工程决策。

所以，“为什么测试”可以概括为：

> 因为系统是否可接受存在不确定性，测试通过证据降低这种不确定性，并支持风险判断与工程决策。

---

## 3. 测试中的不确定性

测试中的不确定性，指的是：

> 在给定系统边界和判断标准的前提下，对系统在各种条件下是否满足期望的未知程度。

这种不确定性不是指系统本身随机或神秘，而是指人对系统行为的认知不充分。系统可能在某些条件下必然失败，只是在测试之前尚未被发现。

因此，测试中的不确定性主要表现为：

1. 不知道系统在哪些条件下会失败；
2. 不知道失败区域有多大；
3. 不知道失败发生的概率有多高；
4. 不知道失败造成的影响有多严重；
5. 不知道已有证据是否足以支撑当前决策。

可以将系统运行条件表示为：

```text
条件空间 C = 输入 + 状态 + 环境 + 依赖 + 操作序列 + 数据条件
```

失败区域可以表示为：

```text
失败区域 F = { c ∈ C | 系统在条件 c 下的行为不符合期望 }
```

也就是说，失败区域就是所有“系统在这些条件下会出错”的场景集合。

测试的作用，就是通过选取条件、执行系统、观察行为和判断结果，逐步降低对失败区域、失败概率和失败影响的未知程度。

---

## 4. 测试什么

“测试什么”不是简单地列功能点，而是选择哪些系统行为值得被观察和判断。

测试对象可以表示为：

```text
测试对象 = 系统对象 S × 条件 C × 期望 Q
```

也可以表达成一个行为命题：

```text
系统 S 在条件 C 下是否满足期望 Q
```

例如：

```text
登录系统在用户连续输错密码 5 次后，是否锁定账号 15 分钟。
支付系统在收到重复支付回调时，是否只生成一条支付流水。
订单系统在已取消订单收到支付成功回调时，是否保持状态一致。
导出系统在导出 10 万行数据时，是否在 30 秒内完成。
权限系统在用户越权访问资源时，是否正确拒绝。
```

因此，“测试什么”可以概括为：

> 测试承载关键不确定性的系统行为。

进一步说，就是在给定边界和假设下，选择那些高风险、高复杂度、高暴露度、高影响度、认知不足的行为命题进行测试。

### 4.1 按不确定性类型划分测试对象

| 编号 | 不确定性类型   | 核心问题           | 典型测试对象                  |
| -- | -------- | -------------- | ----------------------- |
| 1  | 需求不确定性   | 需求和规则是否被正确理解？  | 业务规则、验收标准、异常规则          |
| 2  | 实现不确定性   | 代码是否正确实现了预期？   | 函数、接口、算法、分支逻辑           |
| 3  | 输入不确定性   | 系统会遇到哪些输入？     | 空值、非法值、边界值、脏数据、重复请求     |
| 4  | 状态不确定性   | 系统在不同状态下是否正确？  | 状态流转、历史数据、并发状态、异常恢复     |
| 5  | 依赖不确定性   | 外部系统或模块交互是否可靠？ | API、数据库、缓存、消息队列、第三方服务   |
| 6  | 环境不确定性   | 环境变化后系统是否仍然可靠？ | 浏览器、操作系统、网络、配置、权限、时区    |
| 7  | 质量属性不确定性 | 功能之外是否足够好？     | 性能、安全、稳定性、易用性、可恢复性、可观测性 |

---

## 5. 如何测试

“如何测试”是从“测试什么”自然推导出来的。

既然测试对象是：

```text
系统 S 在条件 C 下是否满足期望 Q
```

那么测试过程就是：

```text
构造条件 C
执行系统 S
观察实际行为 A
对比期望 Q
判断通过或失败
更新不确定性
```

所以，“如何测试”可以定义为：

> 针对已识别的关键不确定性，构造能暴露差异的条件，观察系统行为，并用明确标准判断结果，从而降低系统剩余未知。

更简洁地说：

> 如何测试 = 把不确定性转化为可执行、可观察、可判断的实验。

### 5.1 测试不是从工具出发，而是从不确定性出发

测试方法不应该先问“要不要写自动化测试”“要不要做接口测试”“要不要压测”，而应该先问：

```text
当前面对的是哪类不确定性？
这种不确定性适合用什么方式降低？
```

不同的不确定性，对应不同的测试方式。

| 不确定性类型   | 主要测试方法                              |
| -------- | ----------------------------------- |
| 需求不确定性   | 需求评审、示例化需求、验收标准、原型评审、BDD            |
| 实现不确定性   | 单元测试、接口测试、集成测试、代码审查、静态分析、回归测试       |
| 输入不确定性   | 等价类划分、边界值分析、异常输入测试、组合测试、Fuzz 测试     |
| 状态不确定性   | 状态转换测试、场景测试、模型测试、并发测试、恢复测试          |
| 依赖不确定性   | 契约测试、集成测试、Mock、Stub、故障注入、消息一致性测试    |
| 环境不确定性   | 兼容性测试、配置测试、弱网测试、部署验证、时区测试、容灾测试      |
| 质量属性不确定性 | 性能测试、安全测试、稳定性测试、可用性测试、可恢复性测试、可观测性验证 |

### 5.2 测试的一般过程

可以将测试过程整理为 8 步：

1. **明确边界和假设**
   确定哪些因素纳入测试，哪些因素暂时默认成立。例如默认硬件不故障，但网络延迟、第三方超时、重复请求纳入测试范围。

2. **识别不确定性**
   找出系统中主要未知，包括需求、实现、输入、状态、依赖、环境和质量属性等方面。

3. **转成行为命题**
   把模糊的不确定性转化为可测试表达：系统 S 在条件 C 下是否满足期望 Q。

4. **按风险排序**
   根据失败概率、失败影响和未知程度决定测试优先级。

5. **选择测试方法**
   针对不同不确定性选择合适方法，而不是机械套用某类测试工具。

6. **构造条件并执行**
   准备输入、数据、状态、环境、依赖行为、操作顺序、并发条件等，执行测试。

7. **观察和判定**
   观察接口响应、页面表现、数据库状态、缓存、消息、日志、链路追踪、监控指标等，并依据判定标准判断结果。

8. **更新不确定性**
   通过测试结果更新对系统风险和可信度的判断。失败说明该区域存在确定问题；通过说明在当前条件下未发现问题；无法判断说明判定标准或观察手段不足。

可以浓缩为：

```text
如何测 = 建模 → 取样 → 观察 → 判定 → 更新
```

## 6. 如何知道结果对不对

测试必须有判定标准。没有判定标准，测试结果就无法可靠解释。

判定标准就是行为命题中的 Q：

```text
系统 S 在条件 C 下是否满足期望 Q
```

结果是否正确，取决于实际行为是否满足事先定义的期望和约束。

判定标准可以来自：

| 来源     | 示例                 |
| ------ | ------------------ |
| 需求文档   | 订单取消后不能继续支付        |
| 业务规则   | 金额计算必须符合优惠规则       |
| 产品预期   | 错误提示应让用户知道如何修正     |
| 技术契约   | 接口返回码、字段、幂等规则      |
| 法规规范   | 隐私、审计、合规要求         |
| 历史行为   | 旧版本能力不能被破坏         |
| 系统不变量  | 金额不能为负，库存不能超卖      |
| 用户体验标准 | 页面响应不能明显卡顿         |
| 性能指标   | 95% 请求应在 300ms 内完成 |
| 安全原则   | 越权访问必须被拒绝          |

判定标准可以表示为：

```text
预期行为 + 可观察结果 + 判断规则
```

例如：

```text
用户连续输错密码 5 次后，账号应被锁定 15 分钟。
```

执行测试后，如果账号被锁定且锁定时长符合要求，则结果正确；如果没有锁定、锁定时长错误、提示错误或仍可继续登录，则结果不正确。

如果期望本身模糊，测试就无法稳定判断。例如：

```text
导出报表要快。
```

这不是一个可判定标准。它需要转化为：

```text
导出 10 万行报表应在 30 秒内完成。
```

所以，判定标准越清楚，测试越有效；判定标准越模糊，测试越容易退化为主观体验。

## 7. 测试产出什么

测试的直接产出不是质量本身，而是关于质量的信息。

测试不能保证系统没有问题，但可以说明：

```text
哪些地方已经观察过
哪些地方符合预期
哪些地方不符合预期
哪些风险已经暴露
哪些不确定性已经降低
哪些未知仍然存在
```

测试产出主要包括 5 类。

### 7.1 缺陷信息

说明系统在什么条件下失败、失败表现是什么、是否可复现、影响范围多大、严重程度如何。

例如：

```text
已取消订单收到支付成功回调时，订单状态被错误改为已支付。
```

### 7.2 覆盖信息

说明测试已经观察过哪些区域，还有哪些区域没有观察。

包括：

```text
需求覆盖
接口覆盖
输入类别覆盖
状态覆盖
异常路径覆盖
环境覆盖
风险点覆盖
```

覆盖信息回答的是：

> 已经看过哪里？还有哪里没看？

### 7.3 风险信息

说明哪些风险已经被验证，哪些风险已经暴露，哪些风险仍然未知，哪些风险可以接受，哪些风险必须处理。

例如：

```text
重复支付回调已验证通过，幂等风险降低。
订单取消与支付成功并发冲突未覆盖，仍有高风险。
```

### 7.4 置信信息

测试通过后增加的是有边界的信心，而不是绝对保证。

例如：

```text
在当前测试条件下，核心下单链路表现符合预期。
```

这里的关键是“在当前测试条件下”。测试结论必须带有边界，不应被解释为系统在所有情况下都没有问题。

### 7.5 决策信息

测试最终要服务工程决策，例如：

```text
能不能发布
要不要回滚
哪些问题必须修
哪些问题可以延期
是否需要补测
是否需要降级方案
是否需要加强监控
```

因此，测试最终产出可以概括为：

> 支持决策的质量证据。

## 8. 风险与优先级

测试资源总是有限的，所以测试不应该平均分配，而应该按照风险和不确定性分配。

一个简单的优先级模型是：

```text
测试优先级 = 失败概率 × 失败影响 × 未知程度
```

也可以使用工程打分模型：

```text
不确定性优先级 = 模糊度 + 复杂度 + 暴露度 + 影响度 + 历史问题
```

| 维度   | 含义           | 分数高说明         |
| ---- | ------------ | ------------- |
| 模糊度  | 需求或规则是否清楚    | 越不清楚，越需要测试或澄清 |
| 复杂度  | 逻辑、状态、分支是否复杂 | 越复杂，越容易出错     |
| 暴露度  | 用户或系统调用频率    | 越常用，影响面越大     |
| 影响度  | 出错后果是否严重     | 后果越严重，优先级越高   |
| 历史问题 | 过去是否经常出问题    | 越常出问题，越需要重点测试 |

测试应优先覆盖高不确定性、高复杂度、高暴露度、高影响度和高历史问题区域。

---

## 9. 总体模型

完整的测试模型可以整理为：

```text
为什么测试：
因为系统是否可接受存在不确定性。

测试什么：
测试承载关键不确定性的系统行为。

如何测试：
针对这些不确定性设计观察和实验，用证据降低未知。

如何知道结果对不对：
依据明确的期望、约束和判定标准。

测试产出什么：
产出缺陷、覆盖、风险、置信度和决策所需的质量信息。
```

进一步压缩为：

```text
测试 = 在明确边界下，对关键行为命题进行实验、观察和判定，以降低质量不确定性并支持工程决策。
```

最终结论：

> 测试的本质不是证明系统没有问题，而是在有限资源下，用有目的的观察和判断，降低关键不确定性，暴露不可接受风险，并为系统是否足够可用、好用、可靠和可发布提供证据。
